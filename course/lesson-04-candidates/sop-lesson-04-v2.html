Why it is built this way the choices Ray makes without explaining them
Why the bot has to live on the internet at all
  • Slack does not run your code. When somebody tags your bot, Slack sends a web request out to an address you gave it, and waits for an answer.
  • Your laptop has no public address and is usually asleep. So the code needs a home on the internet that is awake and reachable at all times.
Why Vercel
  • Vercel is a hosting service. It gives your code a public web address for free, which is exactly the thing Slack needs.
  • It deploys straight from GitHub. You push code, it goes live. No server to set up, no files to upload.
  • Claude Code knows Vercel well, so it can create and deploy the project without you learning the tool.
  • This is Ray's choice, not a rule. Any host with a public address would work. But every later lesson assumes Vercel, so swapping it out is your own project.
What a serverless function is, and why the bot is one
  • A serverless function is one piece of code that runs only when a request arrives, then stops. There is still a server underneath. Vercel owns it and starts your code on demand, which is why you never think about it.
  • Here it is a single file, api/slack/events.js. Slack calls it, it checks the secret, it posts a number, it exits.
  • Why that fits: your bot is idle almost all day. A function costs nothing while idle and has nothing to maintain, unlike a machine you keep running.
  • Later Slack expects an acknowledgement within about three seconds, and Vercel functions have a time limit of their own. Both matter once an AI is thinking. Lesson 05 answers Slack immediately and keeps working afterwards, and Ray raises the limit in vercel.json.
  • Later The cloud sandbox in lesson 05 is not a workaround for that time limit. It exists because Claude Code needs a real machine with files and tools, and a function has neither.
Why a private GitHub repository, and what it is really for
  • It is what Vercel deploys from. Vercel watches the repository, and every push becomes a new live version. Without it there is no automatic deploy.
  • It is your history and your undo. Each lesson adds a commit, so you can look back or roll back. Ray's own repository is tagged once per lesson for exactly this reason.
  • Private, because it is your bot's insides. The code, the bot's name, and later on the memory, skills and rules you write. The secrets themselves never go in here, only into Vercel.
  • Later Do not confuse this with lesson 08, “Connecting to GitHub”. That lesson gives the agent access to your other repositories. This one is where the agent's own code lives.
Why there are two secrets and not one
  • Two separate conversations happen. Slack calls you, and you call Slack. Each direction needs its own proof of identity.
  • The signing secret protects the first direction. Slack signs what it sends you and your code checks the signature, so a stranger cannot pretend to be Slack.
  • The bot token protects the second. Your code sends it with every reply, which is how Slack knows the message is really from your bot.
  • Once you see it as two directions, the two boxes in Vercel stop being something to memorise.
What happens when you tag the bot the two seconds between your message and the reply

This picture grows with the course. Later lessons add rows here rather than replacing it, and mark the rows they added, so by lesson 17 this is the whole system on one screen.

  1. You,
    in Slack
    Post @Joestar hello in a channel.
  2. Slack
    Wraps your message up and posts it to your web address. It signs the parcel with your signing secret first, then waits for an answer.
  3. Vercel
    Wakes up api/slack/events.js for this one request. It hands the code the two secrets as environment variables. Nothing was running until now.
  4. Your code
    Recomputes the signature and compares. Not a match, it replies “not allowed” and stops. A match, it reads the message.
  5. Your code
    Picks a random number and asks Slack to post it in the thread. This second call carries the bot token. It is the only place the reply text is decided, and the exact spot lesson 05 will change.
  6. Slack
    Posts the reply as Joestar, and your code answers “all good” and exits. Total elapsed time, a second or two. Nothing of yours is left running.
The one thing worth carrying forward
  • Steps 2 and 5 are the two directions that explain the two secrets. why two secrets
  • Later Slack gives you roughly three seconds to answer step 2, and it resends the message if you are slow. Fine for a random number, a real problem once an AI is thinking about your reply. Lesson 05 reorders this so the answer comes first.

Phase B · Register the app with Slack

3 Start creating the Slack app from a manifest
  • Go to api.slack.com/apps, then Create New App, then From a manifest.
  • Choose your test workspace, then Next. Leave this browser tab open. It is now asking you for a manifest.
What is a manifest
A short text file that describes the app to Slack: its name, what it is allowed to read, what it is allowed to post, and where Slack should send events. You can edit it and upload it again at any time, and later lessons do exactly that as the bot gains abilities.
4 Ask Claude for the manifest and paste it into Slack
Paste this exactlyGive me a manifest for the Slack API.
  • Claude writes slack-manifest.json in your project. Open it and copy the whole thing.
  • Back in the Slack tab, paste it into the box and press Next.
  • The review screen lists two permissions, app_mentions:read and chat:write. That is correct for now. Press Create.
  • The manifest contains a guessed web address, because nothing has been deployed yet. Slack accepts it anyway and you replace it in step 9. Expect this, it is not a mistake.
What a permission like chat:write means
Slack calls these scopes. Each one is a single narrow permission. app_mentions:read means “may see messages that mention me”, and chat:write means “may post messages”. Your bot gets nothing it has not asked for, which is why later features need the manifest changed and the app installed again.

Phase D · Connect the two halves and test

9 Point Slack at that address and wait for the green tick

What the green tick is actually testing
The moment you paste the address, Slack sends it a one-off message containing a random string and expects your code to send that same string straight back. That handshake is the only thing the tick means. It proves the address exists, the deploy is live and your code is answering.

What Claude wrote for you five files, and the shape of the one that matters
The five files
api/slack/events.js the whole bot, about 100 lines slack-manifest.json what you pasted into Slack in step 4 .env.example the names of the secrets, values left blank package.json tells Vercel this is a Node project .gitignore keeps your real secrets and downloads out of git
  • The path api/slack/events.js is not arbitrary. On Vercel, any file under api/ automatically becomes a function at the matching web address. That is where the /api/slack/events in your endpoint comes from.
What the bot file does, top to bottom
  • Reads the two secrets. If either is missing it gives up straight away and logs why. This is the error you get if step 6 or 7 was skipped.
  • Reads the message exactly as sent. The signature covers the precise characters Slack sent, so the code must not tidy them up first. Claude left a comment in the file saying so.
  • Checks the signature. It rebuilds the signature from the timestamp and the message, compares it, and refuses anything more than five minutes old so an old captured request cannot be replayed.
  • Answers the green-tick handshake. The one-off challenge from step 9 is echoed back here.
  • Ignores repeats. If Slack marks the message as a resend, the code says “all good” and does nothing, otherwise one slow attempt would produce two numbers.
  • Handles the mention. If it is a real mention from a person, pick a number and post it. The reply goes into the existing thread if there is one, otherwise it starts a thread on your message.
  • Says “all good” and exits. Slack is satisfied and stops.
The four-part shape, and why it is worth remembering
  • Every later version of this bot keeps the same skeleton: check, ignore repeats, handle, answer. New lessons only change what happens inside “handle”.
  • So when something breaks in lesson 12, the first three questions are always identical. Are the secrets set, is the signature passing, is Slack resending. Knowing this file makes those checks a minute's work instead of an evening's.
Where you would change it the seams, for when you want it to be yours
Reply with something other than a number
  • One place only: the “handle the mention” part of the bot file. Everything before it and after it stays exactly as it is.
  • This is precisely the seam lesson 05 uses to drop Claude Code in.
Change the range of the random number
  • No code change at all. Add RANDOM_MIN and RANDOM_MAX to Vercel's environment variables and deploy again. They default to 1 and 100.
Answer direct messages, not only mentions
  • Three places, in this order. The manifest needs the permission to read direct messages and to receive the direct-message event, then you upload the manifest again on the Slack app page.
  • Install the app again, because the permissions changed. That produces a new bot token, which has to be pasted into Vercel again.
  • In the bot file, the check for a mention has to accept the direct-message type too.
  • The general rule, worth keeping: anything new you want the bot to see or do is a manifest change, then a reinstall, then a code change, in that order.
Rename the bot
  • The display name lives in the manifest. Edit it and upload it again on the Slack app page. No code change and no deploy.
When it goes wrong look up your symptom
No green tick in step 9
  • The deploy may not be live yet. Open the Vercel project and check that the most recent deployment actually finished.
  • Or the signing secret is missing or wrong. Vercel's function logs tell you which: a missing secret and a wrong one produce different errors.
  • Fix it, then paste the address again. Slack re-sends the handshake every time you paste.
Green tick, but the bot never replies
  • The bot is not in the channel. Run /invite @Joestar first.
  • The bot token is missing, or it is an old one from before you installed the app again. Copy it again from Install App and save it in Vercel.
  • Vercel's function logs will name Slack's own reason for refusing the message.
Two replies to one mention
  • Slack resent the message because the first attempt was slow, and the resend was not ignored. Ray's code does check for this, so it only shows up if that check got lost in a later edit.
An error about a missing value
  • One of the two environment variables is not set for the environment that is actually deployed. Both must be on Production.
Two things that surprised Ray, so expect them
  • He saved the bot token to every environment by mistake, noticed, and re-saved it as Production only.
  • The manifest carried a made-up web address because Vercel had not deployed yet. Slack let him create the app regardless, and he set the real address later in step 9.

Look up a word the eight terms this lesson introduces
Slack app
  • Slack's word for anything that plugs into a workspace. Your bot is one app.
  • It is registered on api.slack.com, separately from the workspace itself.
Manifest
  • A short text file describing the app: its name, what it may read, what events it wants, and where to send them. Step 4. You can edit and re-upload it any time.
Scope
  • One narrow permission. app_mentions:read is “may see messages that mention me”. chat:write is “may post”. Later features add more.
Bot token
  • A long string starting xoxb- that proves to Slack a request is from your bot. Your code sends it with every reply. Step 7. Treat it as a password.
Signing secret
  • A different string that Slack uses to sign everything it sends you. Your code recomputes the signature and rejects anything that does not match. Step 6. It stops strangers impersonating Slack.
Environment variable
  • A named value the hosting platform hands your code when it runs, so secrets stay out of the code and out of GitHub. Vercel's page is called Environment Variables. Steps 6 and 7.
Endpoint
  • The public web address that receives Slack's requests. Here it is /api/slack/events on your Vercel domain. Step 8.
Serverless function
  • Code that runs only when a request arrives and then stops, on a machine somebody else maintains. Your whole bot is one of these. the longer answer
