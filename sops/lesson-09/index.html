SLACK AGENTS · CHAPTER "0 TO 1" · LESSON 09

Dogfood the bot: change it by asking it

From here, improvements to the bot are made through the bot. You describe a change in Slack, it opens a pull request against its own repository, and you review it. The point is not convenience — it is that you feel every rough edge yourself, immediately.

Ray's video: 3 min 00 s This page: 45–90 min At the end: a bot that improves itself, one PR at a time

What you'll have at the end

Two requests, two machines, two pull requests, no coordination. The parallelism is free because nothing is shared — a consequence of the throwaway-sandbox design from lesson 05.

  • A development channel whose topic names the repository, so you stop repeating it.
  • Changes to the bot arriving as pull requests you review and merge.
  • Parallel work — several requests at once, each isolated.
  • A felt list of what is annoying about your own bot, which is the actual product of this lesson.

Who this is for, and what it assumes

You finished lesson 08, so the bot can open pull requests, and you have seen GitHub refuse a push to a protected branch.

This lesson has less new machinery than any so far. Most of the work is judgement: what to ask for, how much to ask for at once, and when to stop asking through Slack and open your laptop.

Why this lesson exists

Ray's argument is short and worth taking seriously: "it's really important to start dogfooding our own agent so we can identify bottlenecks and problems." Nothing reveals that the placeholder is uninformative, or that the bot cannot find your repository, quite like needing it to work while you are away from your desk.

It is the difference between a chef who eats in their own dining room and one who never leaves the kitchen. You can inspect a dish for a long time without noticing it arrives cold.

How this page is laid out

  1. Part 1 · Understand what you're building UNDERSTAND Why each request gets its own machine, what the bot can and cannot do to its own code, and when to stop asking through Slack. ~15 min.
  2. Part 2 · Build it DO NOW Six steps: a channel, a topic, a first request, a parallel second one, a review, and a manifest follow-up. 45–90 min.

Before you begin

This lesson points the bot at the repository that holds the bot. On this project that repository is nojzac/2026-09-07-slack-agent, and it is private on a free GitHub plan — where, as lesson 08 proved by testing, a branch ruleset does not enforce and does not say so. Installing the App there as-is would give an unattended bot unprotected write access to its own source, on a repo where a push to main is a production deploy.

There are only three honest ways through, and the choice has to be made before step 1:
OptionWhat it costs
Make the repo public for the courseThe ruleset enforces, so the bot is properly constrained. But everything becomes world-readable — including docs/secrets.md, and TRAPS.md's frank list of where this system is weak. Public repos are forked and cached, so it is not cleanly reversible.
GitHub ProAbout $4/month. Private repo, real protection, no exposure. The straightforward answer, declined here for the duration of the course.
Dogfood without write accessThe bot reads the repo and proposes changes as text; you apply them. Keeps everything private and still surfaces the bottlenecks, which is the actual point of the lesson — but you lose the pull requests.
Whatever you choose, decide it deliberately. The failure mode is installing the App on a private repo because the lesson said to, and believing the branch protection listed in the UI. That belief is the dangerous part, not the access.

  • A channel the bot is in. Ray hits "you mentioned joestar, but they're not in this channel" on his very first try in a new channel.
PART 1

Understand what you're building

No new machinery. Three things worth understanding before you start asking a bot to edit itself.

Why you can run several requests at onceOne sandbox per top-level message, and nothing shared between them.

UNDERSTAND

Ask for two changes in two separate messages and both run at the same time, in different machines, neither aware of the other. That falls out of decisions already made rather than anything added here:

Decision, and where it came fromWhat it buys you now
A throwaway sandbox per run (lesson 05)Two runs cannot corrupt each other's working directory
Transcript replay rather than a live session (lesson 07)No shared state to lock, so no queue and no conflict
A token minted per request (lesson 08)Each machine carries its own credential, expiring separately
This is the payoff for the stateless design. Every earlier lesson chose "no store, no session, no queue" and paid a price for it — transcript replay costs a Slack API call every turn. Parallelism is what that bought: it needs no work here because there is nothing to coordinate.
Two parallel requests touching the same files will produce two conflicting pull requests. Nothing prevents it — the isolation is between sandboxes, not between branches. Git will tell you at merge time rather than at request time, which is late. Split work by area, not by convenience.

What happens when a bot edits its own codeA broken change cannot deploy itself — provided you keep the gates you already have.

UNDERSTAND

Asking a program to modify itself sounds alarming and mostly is not, because of gates built in earlier lessons that have nothing to do with this one:

GateStops
Branch ruleset — PR + 1 approval (08)The bot merging its own work
workflows permission withheld (08)It rewriting CI to get around the tests
Tests gate the deploy (04)A broken change reaching production even after you merge
You read the diffEverything the above misses
It can draft an amendment to its own rules; it cannot ratify one. The approval is yours and the deploy is gated by tests — those two facts are what make self-modification ordinary rather than exciting.
The failure this design does not cover is a plausible, passing, wrong change. Tests that pass and a diff that reads well can still be a change you did not want — and the bot is unusually persuasive about its own work, because it writes the PR description too. Read the diff, not the summary of the diff.

When to stop asking through SlackDogfooding is a habit, not a rule. Knowing where it stops is part of the lesson.

UNDERSTAND

Ray: use Slack by default, and "only if you really need to, should you be switching back into Claude Code running locally." The honest boundary, based on what this project has already hit:

Ask through SlackOpen your laptop
A contained change in one or two filesAnything touching the event handler's guards
A change you can describe in two sentencesAnything needing a template rebuild — the bot cannot rebuild the machine it is running on
Work you are happy to review as a diffAnything involving a credential; the bot must never be asked to handle one
Several independent things at onceDebugging that needs a probe, a log, or a reply from the live bot
The bot cannot verify itself end to end. It can change the code and open a PR, but the deployed thing it would have to test is itself, and the sandbox dies before the deploy happens. Anything whose correctness depends on a real Slack round trip still needs docs/verifying.md and a human.
PART 2

Build it

Six steps. Two are Slack setup, three are asking the bot for things, and one is the review that makes the rest safe.

Step 1 of 6 — Create the development channel and invite the botA room for work on the bot itself, separate from testing it.

DO NOW

  1. Create #joestar-dev.

    Where: Slack → channel list → + → Create a channel

  2. Invite the bot: /invite @joestar.

    Ray forgets this and the lesson stops immediately — Slack answers "you mentioned joestar, but they're not in this channel". A bot only receives mentions in channels it is a member of. Same trap as lesson 06, in a new room.

  3. Know what this channel is for.

    You now have three, and keeping them apart is what stops each becoming noise:

    ChannelFor
    #bot-smokebin/smoke's scripted probes
    #joestar-testTesting that the bot works
    #joestar-devChanging what the bot does
    Adding the bot to a channel widens what it hears. Since lesson 07 it receives every message in every channel it is in, not just mentions. That is fine and expected — the three loop guards handle it — but the channel list is the access list, and it just got longer.
CHECKPOINT#joestar-dev exists and joestar is in its member list.

Step 2 of 6 — Put the repository in the channel topicSo you stop naming it in every message — and so the bot can find it without asking.

DO NOW

  1. Set the topic to the repository.

    Where: the channel name at the top → Edit next to Topic

    Ray's convention, and it is a good one: the topic of a development channel is the repo it is about — nojzac/2026-09-07-slack-agent.

  2. Understand that the bot cannot read it yet.

    The topic is just text to a human until the code fetches it. Making the bot use it is the first dogfooding request, in step 3 — which is the point: the lesson's first change is one that makes the lesson itself easier.

    It needs a scope it may not have. Reading a channel topic means conversations.info, which needs channels:read (and groups:read for private channels). Neither is in the current manifest — so expect the bot to tell you it needs a manifest change, which is exactly what step 6 is for.
CHECKPOINTThe channel header shows the repository, and you have noticed that nothing in the bot reads it yet.

Step 3 of 6 — Make the first requestAsk for a contained change, and ask for a pull request by name.

DO NOW

  1. Ask, in #joestar-dev:

    @joestar Update the agent so that for every channel it is in, it
loads the channel topic and treats it as the GitHub repo for that
channel — so you don't have to work out which repo I mean. The topic
is set on this channel already. When you're done, open a PR and tell
me where it is.

    Three things make that a good request, and they generalise: it describes an outcome rather than an implementation, it says where to find an example, and it names the deliverable (a PR) so the work ends somewhere you can see.

  2. Watch for 👀, then leave it alone.

    The reaction means the guards passed and a sandbox is booting. A GitHub change takes minutes, not seconds — cloning, reading, editing, pushing.

  3. Expect it to hit the missing scope.

    Reading a channel topic needs channels:read, which the manifest does not grant. A good answer says so rather than silently writing code that cannot work. That is a real result, not a failure — note what it tells you and carry on to step 4.

CHECKPOINTA pull request exists, opened by the App, and you can see what it changed.

Step 4 of 6 — Kick off a second request in parallelThe point of the isolation. Two machines, two branches, no coordination.

DO NOW

  1. Without waiting for the first, post a second top-level message:

    @joestar Instead of just showing "thinking…", show how long it has
been working for and the most recent tool call it made, updating as
it goes. Search the Claude Code docs online for how to get tool-call
information out of a headless run. Open a PR when you're done.
    It must be a new top-level message, not a thread reply. A reply continues the same conversation and queues behind it; a new message starts a new sandbox. This is the one place where the difference between the two — invisible in lesson 07 — becomes the whole feature.

  2. Pick a second task that touches different files.

    These two are a good pair: one changes how the repo is discovered, the other changes the placeholder. If both edited events.js heavily you would get two conflicting PRs and find out at merge time.

CHECKPOINTTwo threads, both reacted to, eventually two separate pull requests. Neither mentions the other.
Where this differs from Ray. Ray's second request produces a PR whose link he cannot click, because the bot appended a stray asterisk to the URL. Worth knowing as a symptom: that is a mrkdwn conversion bug of exactly the kind lesson 07's converter exists to prevent. If you see it here, it is a real bug in your own code and a good third dogfooding request.

Step 5 of 6 — Review the pull requests properlyThe step that makes every other step safe. Read the diff, not the description.

DO NOW

  1. Open Files changed, not the summary.

    The bot wrote the PR description as well as the code, so the description is evidence of what it intended, not of what it did. They usually agree. The cases that matter are the ones where they do not.

  2. Check the things this project has been bitten by.

    • Are the three loop guards intact? bot_id, subtype === 'bot_message', user === BOT_USER_ID. Losing one is an unbounded spend, and it fails silently.
    • Is the dedup still splitting on files rather than event type?
    • Did it add a dependency? This function has died once already from one (TRAPS.md, lesson 05).
    • Are there new tests? A behaviour change with no test is how the next regression gets in.
    • Does anything touch a credential? Nothing should.

  3. Merge, and let CI deploy.

    Merging to main runs test.yml, which tests and then deploys. So a merge is a deploy here, with the tests as the gate.

    Then verify in Slack. The tests do not prove Slack still delivers, and the bot cannot check that for you — it would have to test itself after its own sandbox has died. Follow docs/verifying.md: mention it, and confirm 👀, an answer, and ✅.
CHECKPOINTA merged PR, a green Actions run, and a real mention answered in Slack afterwards.

Step 6 of 6 — Ask for the updated manifest, then apply itNew features usually need new permissions, and the bot cannot grant itself any.

DO NOW

  1. Ask, as a thread reply on the relevant PR's conversation:

    Give me the updated manifest I need going forwards. Write it to a
file and send it here, and list what changed and why each addition
is needed.

    Asking for a file rather than a message is deliberate — it arrives as an attachment you can open and paste from, which is what lesson 07's upload path was built for.

  2. Read what it is asking for, and why.

    Do not paste a manifest you have not read. A manifest is a permissions request, and this one was written by the thing being granted the permissions. For the channel-topic feature the honest answer is channels:read — if anything broader appears, ask why before saving.

  3. Apply it: paste, save, reinstall.

    Same sequence as lesson 07's step 3 — paste into the App Manifest editor, Save Changes, then reinstall, because new scopes do not exist until a fresh install.

    Check whether the token rotated. Run bin/preflight. It reads the required scopes out of slack-app-manifest.yml, so it will tick the new one — and it tells you whether the bot token still works without anyone reading it. Lesson 07's step 4 has the branch to follow if it did rotate.

  4. Update slack-app-manifest.yml in the repo too.

    The file is the source of truth and bin/preflight now reads it. A manifest in Slack that disagrees with the one in git means the next preflight checks the wrong list.

CHECKPOINTbin/preflight ticks every scope in the manifest, and the new feature works when you try it in #joestar-dev.
The loop is closed. You can now describe a change from your phone, review it, merge it, and watch it deploy — and the bot is the thing that made the change.

How to phrase a request, what not to merge, the failure table, and what this page could not check.

How to phrase a requestThe difference between a useful PR and a plausible one is mostly in the asking.

REFERENCE
DoInstead of
"Show how long it has been working and the last tool call""Make the placeholder better"
"Open a PR and tell me where it is"Leaving the deliverable unsaid
"The topic is set on this channel already"Making it hunt for an example
"Search the docs online for how to do X"Assuming it knows a current API
"Tell me if you need a permission I don't have"Letting it write code that cannot work
One area per requestThree unrelated changes in one message
Say what you want to be true, not which lines to edit. It reads the code before changing it; describing the outcome leaves room for it to find the right place, and you review the diff anyway.

What to refuse to mergeSix things worth a "no" regardless of how good the rest of the diff looks.

REFERENCE
  • Any change that removes or loosens one of the three loop guards.
  • Dedup rewritten to split on event type rather than on files.
  • A new dependency on the Vercel function, without a stated reason.
  • Anything that reads, logs, or moves a credential.
  • Anything touching .github/workflows/ — the App cannot, so a diff containing it means something odd happened.
  • A behaviour change with no test, where the behaviour could regress silently.
The persuasive-and-wrong case is the one to watch. Tests pass, the diff reads well, the description is confident, and the change is not what you wanted. Nothing in this design catches that except reading it.
