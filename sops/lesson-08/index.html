SLACK AGENTS · CHAPTER "0 TO 1" · LESSON 08

Give the bot GitHub access, without giving it the keys

Ask joestar in Slack to fix something and it clones the repo, branches, commits, pushes and opens a pull request. It does that with a token minted fresh for each request that dies in an hour — and it never holds the credential that mints tokens.

Ray's video: 6 min 09 s This page: 2–3 hours At the end: a bot that opens pull requests

What you'll have at the end

The bot cannot merge this. It cannot push to the default branch. It cannot touch .github/workflows/. Everything it did here is a proposal a human approves.

  • A GitHub App installed on repositories you choose by name — not on your account.
  • A token minted per request, valid one hour, that expires long before anyone could reuse it.
  • The private key in the Vercel function only. The thing that mints tokens never enters the sandbox.
  • Branch rulesets that make the default branch refuse force-pushes and deletions regardless of what the bot is told to do.

Who this is for, and what it assumes

You finished lesson 07, so the bot holds a conversation, reads files and reacts in a thread.

This lesson assumes you own or administer the repositories you are about to grant access to, and that you can add environment variables in Vercel. It does not assume you have made a GitHub App before.

It is the longest lesson so far, and most of that time is browser work and reading a diff — not waiting on code.

Why this lesson exists

Up to now the worst a broken bot could do was post nonsense in a channel. From this lesson on it can write to repositories. That is the whole point — and it is why this page spends its first section on the threat model rather than on clicking through GitHub's settings.

How this page is laid out

  1. Part 1 · Understand what you're building UNDERSTAND The threat model, why a GitHub App rather than a token, where the private key lives, and what actually holds the line. Read this one properly. ~25 min.
  2. Part 2 · Build it DO NOW Eight steps: create the App, install it narrowly, mint a key, protect the branches, store three variables, run the prompt, rebuild the sandbox, verify. 2–3 hours.
  3. Part 3 · Keep for later REFERENCE The prompt verbatim, the failure table, the done checklist, and what this page could not verify.

Before you begin

  • Lesson 07 finished and verified. Run bin/preflight; it should report all seven Slack scopes.
  • A repository you are willing to let a bot write to. Pick one deliberately — this is the blast radius, and it is set by the install, not by the code.
  • Admin rights on it, to add a branch ruleset.
  • A repository where rulesets are actually available. Verified on this account: a private repo on the free plan cannot have them — the API answers 403 — "Upgrade to GitHub Pro or make this repository public to enable this feature." Rulesets are free on public repos. Check before you choose, because step 4 is not optional.
  • Somewhere safe for a .pem file. GitHub shows the private key once, at generation, and cannot show it again.
Read Part 1 before clicking anything in GitHub. The permissions you grant and the repositories you pick are the security model. The code cannot make a bad choice there safe, and undoing it later means regenerating keys and reinstalling.
PART 1

Understand what you're building

One uncomfortable idea, stated plainly, and then four design decisions that follow from it.

What you are actually grantingAnyone who can mention the bot can run code on your repositories. Design from there.

UNDERSTAND

The sandbox runs Claude Code with --dangerously-skip-permissions. That is not an oversight — it is what lets the bot work unattended. But combined with this lesson it means:

Anyone who can @joestar can run arbitrary prompts, and therefore arbitrary code, against whatever GitHub access the bot holds. In a workspace where that is only you, the risk is your own mistakes. In a shared workspace it is everyone in it. The channel membership list is the access control list.

So the useful question is not "how do we stop the model misbehaving?" It is: when the model does something wrong, what refuses it? There are only two honest answers, and neither of them is the prompt.

LayerStopsWorth
Telling the model what not to doAn agent that was going to comply anywaySaves it minutes discovering walls by hitting them. Not a control.
A hook inside the sandboxA careless git push --forceDefence in depth. Defeatable by G=push; git $G --force.
Permissions you never grantedAnything outside them, including by injected codeThis is the real boundary.
Branch rulesetsForce-push and deletion on the default branchEnforced by GitHub, not by you.
It is the difference between a rule and a lock. Telling a contractor not to go into the server room is a rule. Not giving them a key to the server room is a lock. The prompt and the hook are rules; the App's permissions and the branch ruleset are locks. This lesson is about spending your effort on the locks.
Why the sandbox being throwaway does not help here

Everything the bot does inside the sandbox is erased when the run ends, which is why there is no point adding a general dangerous-command denylist — rm -rf in a container that is about to be destroyed costs nothing. But a push leaves the sandbox before the sandbox dies. The throwaway property protects the machine; it protects nothing on GitHub.

Why a GitHub App, not a personal access tokenThe fast way gives the bot your identity. The slow way gives it an hour of narrow capability.

UNDERSTAND

Ray names both routes and takes the safer one. The difference is worth stating precisely, because the fast one is genuinely five minutes' work and it is tempting.

Personal access tokenGitHub App
Acts asYou. Commits carry your nameIts own identity, joestar-bot[bot]
ReachesEverything you can reach, typicallyOnly repositories you selected at install
Lives forUntil you remember to revoke itOne hour, minted per request
If it leaksYour whole account, until noticedThose repos, for the rest of the hour
Audit trailIndistinguishable from your own workAttributable to the bot
Where this differs from Ray. In the video Ray reaches the install screen, says you can pick some repositories or all of them, and clicks through. His own written brief says selected repositories only, and gives the reason: that selection is your blast radius. This page follows the brief. It is one click either way and it is the single most consequential click in the lesson.

The two permissions you deliberately withholdEach one would turn a compromised prompt into something much worse.

UNDERSTAND

Four permissions go on. Two stay off on purpose, and the reasons are worth understanding rather than copying.

PermissionLevelWhy
ContentsRead and writeClone, commit, push
Pull requestsRead and writeOpen and comment on PRs
MetadataRead-onlyMandatory, selected for you
IssuesRead-only, optionalOnly if it should read issues
WorkflowsNo accessWould let injected code rewrite CI — and CI holds secrets. A bot that can edit .github/workflows/ can print your Actions secrets to a log.
AdministrationNo accessWould let it remove the branch protection that is the other half of this design.
These two are not paranoia — they are the escalation paths. Every other control here assumes the bot cannot rewrite CI and cannot disable branch protection. Grant either and the rest of the lesson stops meaning anything.
Withholding administration is why the lock works. A lock whose key is in a drawer marked "lock settings" is decoration. Branch protection only protects you if the thing being protected against cannot turn it off.

What branch rulesets actually cover, and the gap they leaveThey protect the default branch. Every other branch stays writable — which is why there is one hook.

UNDERSTAND

A ruleset on the default branch requires a pull request with an approval, blocks force pushes, and restricts deletions. GitHub enforces it; nothing in the sandbox can talk it out of that.

But it covers that branch. With contents: write the bot can still force-push over, or delete, any other branch in the repository — including someone else's work in progress. That is the one destructive capability this design permits, and it is the reason for the single hook in the sandbox rather than none.

One narrow hook, not a denylist. The hook blocks destructive push refspecs — --force, --delete, a leading +, --mirror, --prune, colon-delete. It does not try to police shell commands generally. A denylist that catches the obvious cases and misses the rest is worse than none, because it reads as protection while X=$GH_TOKEN walks straight past it.
Whether the hook fires at all is genuinely unknown here. The bot runs Claude with --dangerously-skip-permissions. The documentation says PreToolUse hooks run regardless of permission mode; there are open reports claiming that flag skips the hook layer entirely. This cannot be settled by reading — it has to be tested, and step 8 tests it. Treat the hook as a nudge whatever the result.

Two traps hide in that table. GITHUB_APP_PRIVATE_KEY holds base64, not raw PEM — the name does not say so, and pasting a raw .pem there produces error:1E08010C:DECODER routines::unsupported, an error that points at nothing. And git does not read GH_TOKEN; only gh does. Git needs a credential helper, which is its own step.
PART 2

Build it

Eight steps. Five are browser work in GitHub and Vercel; one runs a prompt; one rebuilds the sandbox image; one verifies. The browser work is the security model, so it comes first.

Step 1 of 8 — Create the GitHub AppIts name becomes the commit author. The webhook toggle matters more than it looks.

DO NOW

  1. Open the new-App form.

    Where: GitHub → Settings → Developer settings → GitHub Apps → New GitHub App — github.com/settings/apps

    If the repositories belong to an organisation, create it there instead: github.com/organizations/<ORG>/settings/apps. An org-owned App survives you leaving; a personal one does not.

  2. Name it.

    The name must be unique across all of GitHub, so joestar-bot may be taken. Whatever you choose becomes the commit author, suffixed: joestar-bot[bot]. Pick something you will be happy to see in a blame view.

  3. Homepage URL: anything.

    Required, never used. Your repository URL is fine. Include the https:// — Ray forgets it in the video and the form rejects it.

  4. Untick Active under Webhook.

    This is not cosmetic. You are calling GitHub's API, not receiving events from it. Leave the webhook active with no endpoint and GitHub keeps attempting deliveries and retrying the failures — noise that looks like a problem later and is not.
CHECKPOINTThe form is filled in, the webhook is off, and you have not yet pressed Create — permissions come first, on the same page.

Step 2 of 8 — Set permissions and install on selected repositoriesThe most consequential clicks in the lesson. This is where the blast radius is set.

DO NOW

  1. Set exactly these four, and leave everything else at "No access".

    PermissionLevel
    ContentsRead and write
    Pull requestsRead and write
    MetadataRead-only (selected for you)
    IssuesRead-only — only if it should read issues
    Do not grant Workflows or Administration. Workflows lets injected code rewrite CI, and CI holds secrets. Administration lets it remove the branch protection you are about to add. See Part 1 — these are the escalation paths, not a style preference.

  2. "Where can this GitHub App be installed?" → Only on this account.

  3. Create the App, and note the App ID.

    Where: the General tab, after creation

  4. Install it — on selected repositories only.

    Where: left sidebar → Install App → Install next to your account

    Choose Only select repositories and pick them by name.

    This selection is the blast radius for writes. Not the prompt, not the hook, not the model's judgement. Everything the bot can ever change on GitHub is decided here, and the only way to shrink it later is to come back and change it.
    Reads are wider than your selection, and GitHub says so on the screen. Verified: under both options the small print reads "Also includes public repositories (read-only)." So the App can read public repositories you never selected. That is not an escalation in the usual sense — public repositories are world-readable anyway, and it is read-only, so nothing destructive follows from it. What it does mean is that the bot can pull content from repositories you did not choose, which is a prompt-injection surface: text it reads can try to instruct it. The same is true of the open internet, since E2B allows outbound network.

    Ray's brief calls the selection your blast radius without qualification. That is right about writes and overstated about reads.
    Where this differs from Ray. In the video Ray says you can choose some repos or all of them, and clicks straight through. His own written brief says selected repositories only, and gives this reason. Follow the brief.
    Do not choose the bot's own repository for this. Two reasons, and the first is specific to this project. A push to main here is a production deploy — so a bot that can push to main can deploy itself, unreviewed, at the request of anyone who can post in Slack. And this repo holds the bot's own loop guards, signature verification and secrets rules; pointing it at its own source for a first test is the worst possible place to discover the credential helper does not work.
    Use a throwaway repo for this lesson. Create one with nothing but a README, and decide about real repositories afterwards, when you have seen what the bot actually does.
    The flip-back has a cost we only found by testing it. Making a protected repo private again silently disables the ruleset. The identical push to main was refused with GH013 while public and accepted minutes later once private — same token, same branch, no warning, and the ruleset still listed in the UI. A control that evaporates when an unrelated setting changes is worse than no control, because the written security model still claims it is there.
    What was decided here: nojzac/joestar-sandbox — a throwaway holding nothing but a README — stays public for the duration of the course. That keeps a real, enforcing branch ruleset for free, which is the whole point of having a test repository: you want to watch the lock refuse. Verified after flipping back: ruleset active, push to main refused with GH013.

    The rule that comes with that decision: nothing real goes in this repo. Everything in it is world-readable, and the bot writes to it unattended.

    For a private repo the bot can write to and that is genuinely protected, the honest options are GitHub Pro or nothing — see TRAPS.md.

  5. Grab the Installation ID from the URL you land on.

    https://github.com/settings/installations/1234567
                                            ^^^^^^^ this number

    For an org: github.com/organizations/<ORG>/settings/installations/1234567.

    This is not the App ID. Two different numbers, both numeric, and swapping them produces a 404 at token-minting time with no hint as to which one is wrong.
CHECKPOINTYou have two numbers written down — App ID and Installation ID — and the install page lists only the repositories you intended.

Step 3 of 8 — Generate the private key and base64 itGitHub shows this once. Encode it before it goes anywhere near an environment variable.

DO NOW

  1. Generate the key.

    Where: the App's General tab → scroll to Private keys → Generate a private key

    A .pem downloads. GitHub cannot show it to you again. If you lose it, generate a new one and delete the old.

  2. Base64 it to a single line.

    base64 -i ~/Downloads/joestar-bot.*.private-key.pem | tr -d '\n' | pbcopy

    The tr is not optional decoration: GNU base64 wraps at 76 characters by default, and the wrapping breaks the decode at the other end. The .pem is multiline, and multiline values get mangled often enough on the way into environment variables that removing the ambiguity is worth one command.

    This is a secret and it is now on your clipboard. Do not paste it into a chat, a file, a commit, or this page. It goes into exactly two places, in step 5.
CHECKPOINTA single-line base64 string is on your clipboard, and the .pem is somewhere you can find it again.

Step 4 of 8 — Protect the default branchThe half of the design GitHub enforces for you. Do it before the bot can push, not after.

DO NOW
Check this is available before you get here. Verified on this account: rulesets are not available on a private repository on the free plan. The API answers 403 with "Upgrade to GitHub Pro or make this repository public to enable this feature", and the Settings page hides the option. They are free on public repositories.

Ray's brief says to add a ruleset and does not mention that it depends on your plan and the repository's visibility. If you cannot add one, you have three honest options — use a public repo, pay for Pro, or proceed without the lock and know that contents: write then means the bot can push directly to your default branch. Do not pretend the third is the same as the first.

  1. Add a ruleset on each repository you installed the App on.

    Where: repo → Settings → Rules → Rulesets → New branch ruleset

    Target the default branch, and set:

    • Require a pull request before merging, with 1 approval
    • Block force pushes
    • Restrict deletions
    • An empty bypass list — a bypass list containing your App undoes the whole thing

  2. Understand what it does not cover.

    Every branch that is not the default stays fully writable, including force-push and delete. That gap is why there is one hook in the sandbox — see Part 1.

CHECKPOINTThe default branch refuses a direct push, force-push and deletion, and the ruleset's bypass list is empty.
Where this differs from Ray. The video does not do this step at all; his written brief requires it. Without it, contents: write means the bot can push straight to your default branch, and the pull-request workflow the whole lesson describes is a convention the bot is free to ignore.

  3. Remember what the name does not say.

    GITHUB_APP_PRIVATE_KEY holds base64, not PEM. The code must decode it before signing, and that deserves a comment where it happens:

    // Stored base64-encoded to survive multiline env var handling.
const privateKey = Buffer.from(
  process.env.GITHUB_APP_PRIVATE_KEY,
  'base64',
).toString('utf8');

    If the decoded value does not start with -----BEGIN, the code should throw saying so — otherwise the failure surfaces as error:1E08010C:DECODER routines::unsupported, which names nothing.

The fifteen-line sandbox probe, and why it is the best debugging tool here

When the bot misbehaves, the first question is "is it my code or is it the machine?" — and that is answerable in a minute:

// keep it OUTSIDE the repo so it does not show up in git status
import { Sandbox } from '<repo>/joestar-agent/node_modules/e2b/dist/index.mjs';

const sb = await Sandbox.create('joestar-claude', { timeoutMs: 120_000 });
try {
  const r = await sb.commands.run('gh --version', { envs: { HOME: '/home/user' } });
  console.log(r.exitCode, r.stdout, r.stderr);
} finally {
  await sb.kill();   // always — a live sandbox is a billed sandbox
}

Run it with bin/with-secrets node /tmp/probe.mjs. Two snags: a script outside the repo cannot resolve e2b, hence the absolute import path; and an abandoned sandbox keeps running and keeps costing, hence the finally.

Do not check a command's result through a pipe. git push origin main 2>&1 | tail -2 reports tail's exit code, which is 0 whether or not the push was refused — so the check passes against a repository with no protection at all. This was written, run, and believed here for about a minute before the output text contradicted it. Read the command's own exit status.

The full prompt text 
# Give the sandboxed Claude Code agent short-lived GitHub access

This repo is a Slack bot: a Vercel function receives a Slack event, boots a throwaway E2B sandbox, and runs Claude Code inside it with `--dangerously-skip-permissions`.

READ the existing code first — `api/slack/events.js`, `lib/claude-sandbox.js`, `lib/slack.js`, `e2b/template.js`, and the README — before changing anything. Match the existing style and comment density.

## Goal

Let the agent do real GitHub work in response to a Slack message — clone a repo, branch, commit, push, open a PR, read issues — using a token minted fresh per request that expires in 1 hour.

## Threat model (assume this, don't soften it)

Anyone who can @mention the bot can run arbitrary prompts AND arbitrary code inside the sandbox. Guardrails inside the sandbox are defence-in-depth only; the boundary that actually holds is what GitHub itself refuses to do. Design accordingly, and don't write comments claiming more safety than the design provides.

## Set this up yourself before starting (it is not code)

Create a GitHub App, install it on **selected repositories only**, and generate a private key:

- Permissions: `contents` read+write, `pull_requests` read+write, `metadata` read. Deliberately NOT `workflows` (would let injected code rewrite CI and escalate into Actions secrets) and NOT `administration` (would let it remove branch protection).
- Add a ruleset on each default branch: PR required with 1 approval, force pushes blocked, deletions restricted, empty bypass list.
- Base64-encode the `.pem` to a single line before putting it in Vercel — multiline env vars do not survive the round trip cleanly:

      base64 -i your-app.private-key.pem | tr -d '\n' | pbcopy

Three env vars in Vercel:

| Var                      | Contents                                                                      |
| ------------------------ | ----------------------------------------------------------------------------- |
| `GITHUB_APP_ID`          | numeric App ID                                                                |
| `GITHUB_INSTALLATION_ID` | numeric installation ID (the number at the end of the install's settings URL) |
| `GITHUB_APP_PRIVATE_KEY` | the App's `.pem`, **base64-encoded, single line**                             |

## 0. The sandbox has no `gh`

`e2b/template.js` installs `curl`, `git`, `ripgrep`, and the Claude CLI — that's all. The GitHub CLI is not there, and it is not in the base image's default apt sources either, so `aptInstall(["gh"])` may not resolve. Add it via GitHub's own apt repo with `runCmd(..., { user: "root" })`, or install the release `.deb` directly.

**None of this works until you re-run `npm run template:build`.** The README already documents how a stale template of the same name silently shadows a new one — you will hit that here if you skip the rebuild. ## 1. Mint the installation token in the Vercel function

Put this in a new `lib/github.js`. It runs in the **function**, never in the sandbox — the App private key must not enter the sandbox. That separation is the entire point: the sandbox holds an expiring capability, not the thing that mints capabilities.

**Decode the key first.** Despite the variable name, the value is base64, not raw PEM:

    // Stored base64-encoded to survive multiline env var handling.
    const privateKey = Buffer.from(
      process.env.GITHUB_APP_PRIVATE_KEY,
      "base64",
    ).toString("utf8");

If the decoded value doesn't start with `-----BEGIN`, throw with a message saying the variable is expected to be base64. Otherwise you get an opaque OpenSSL `error:1E08010C:DECODER routines::unsupported` that points at nothing.

**Sign an RS256 JWT** with exactly three claims — `{ iat, exp, iss }`:

- `iat` ~60 seconds in the past, to absorb clock skew. GitHub rejects future-dated JWTs.
- `exp` no more than 10 minutes out. Use 9 to leave yourself margin.
- `iss` the App ID. (GitHub's docs now recommend the App's *client ID* here and treat the numeric App ID as the older form. Both work; the numeric ID is what the env var above holds, so use it — just know why the docs look different.)

Prefer Node's built-in `node:crypto` (`createSign("RSA-SHA256")` plus base64url encoding) over adding a JWT dependency. This repo has already been bitten once by an ESM-only package breaking Vercel's bundler; a ~15-line signer avoids repeating that. If you judge a library is genuinely worth it, say why before adding it.

**Exchange it** for an installation token:

    POST https://api.github.com/app/installations/{GITHUB_INSTALLATION_ID}/access_tokens
    Authorization: Bearer <jwt>
    Accept: application/vnd.github+json
    X-GitHub-Api-Version: 2022-11-28

That version header is not the newest — GitHub's REST API is date-versioned and the current release is `2026-03-10`. `2022-11-28` is still supported (through **10 March 2028**) and is what an unversioned request defaults to, so pinning it is a deliberate, stable choice, not a stale one. Pin it explicitly with a comment saying so; don't silently omit the header and inherit whatever the default becomes later. Check the current table at docs.github.com/en/rest/about-the-rest-api/api-versions yourself rather than trusting this brief — it will age.

The response gives `{ token, expires_at }`, one hour out. That lifetime is fixed and cannot be extended, which is fine — the sandbox lives minutes.

**Never log the token**, and never parse or assume its format or length. On a non-2xx, surface GitHub's own `message` field plus the status: `401` means a bad JWT or a skewed clock, `404` means the wrong installation ID.

**Fail soft.** If minting fails, the bot must still answer non-GitHub questions. Run without the token and have the Slack reply say GitHub access is unavailable — don't take the whole request down. Distinguish *not configured* (no GitHub App set up at all — stay silent, the feature is simply off) from *configured but broken* (say so in the reply). Otherwise every student without a GitHub App gets a scary warning on every message.

**Decide eager vs lazy minting and justify it.** Lazy means only minting when the request looks GitHub-shaped — which in practice means keyword-sniffing the prompt. Before choosing that, consider the threaded follow-up "now open a PR for that", which contains no keyword at all. Also consider where minting sits: it runs after the Slack ack, inside `waitUntil`, on a path that already takes minutes. Whatever you choose, say why. If you cache the token across warm invocations, say explicitly what that means for the "fresh per request" story.

## 2. Get it into the sandbox

- Pass it per command via `sandbox.commands.run(cmd, { envs: { ... } })`. Passing envs at `Sandbox.create` does **not** reach spawned processes — that lesson is already load-bearing for the Claude OAuth token. Do not regress it.
- Set `GH_TOKEN` (the `gh` CLI reads it automatically; no `gh auth login` needed, which matters because that command wants an interactive TTY).
- Also set `HISTFILE=/dev/null` so nothing lands in shell history.
- Everything Claude spawns inherits these. That's required for `git` and `gh` to work, and it means any code the model runs can read the token. Comment it honestly; don't pretend the env var is compartmentalised.

## 3. Let git use it without leaking it

- **`git` does not read `GH_TOKEN`.** It needs a credential helper. Two candidates: `gh auth setup-git`, or an inline helper configured yourself. `gh auth setup-git` is known to behave differently when auth comes from an env var rather than stored credentials, so **test both in a real sandbox and ship the one that actually works.** Don't assume, and don't ship the untested one.
- The inline form to test looks like this — note that what lands on disk is the literal string `$GH_TOKEN`, expanded only when git runs the helper:

      git config --global credential.https://github.com.helper \
        '!f() { echo username=x-access-token; echo "password=$GH_TOKEN"; }; f'

- **Do not embed the token in the remote URL** (`https://x-access-token:TOKEN@github.com/...`). It persists in `.git/config` in plaintext for anything later in the run to read.
- Do not pass the token as a command-line argument — it's visible in `ps`.
- `git commit` fails outright without `user.name` / `user.email`. Set them from env vars; the exact values don't matter for this task.
- Confirm `HOME` is the same for your setup command and for the `claude` command, or `--global` config written by one won't be seen by the other.

## 4. In-sandbox guardrail: one narrow PreToolUse hook

Add exactly one hook, and be honest in its comments about what it does and doesn't do.

**What it blocks:** destructive `git push` refspecs — `--force`, `-f`, `--force-with-lease`, `--delete`, `-d`, a leading `+` in a refspec, and colon-delete (`git push origin :branch`). Consider `--mirror` and `--prune` too: both delete remote refs, so they belong to the same capability. Exit code 2, with a stderr message the model will read: "Force-push and branch deletion are disabled. Push a new branch and open a PR instead."

**Why only this:** the branch ruleset protects the default branch only, so `contents: write` can still force-push over or delete any other branch. That's the one destructive capability GitHub permits and nobody wants. Everything else is either already refused by GitHub (protected main, `.github/workflows/`) or unenforceable by string-matching (token exfiltration via `curl`/`python`/`nc`/an attacker-controlled remote — `X=$GH_TOKEN` alone defeats any pattern you write).

Do NOT add a general dangerous-command denylist. The sandbox is a throwaway container killed after every run; `rm -rf` inside it costs nothing, and a denylist that stops the obvious cases while missing the non-obvious ones is worse than none because it reads as protection.

**Implementation notes:**

- Config schema is `"hooks": { "PreToolUse": [ { "matcher": "Bash", "hooks": [ { "type": "command", "command": "..." } ] } ] }`. Write it to the sandbox user's settings file (`~/.claude/settings.json`), and add *only* the `hooks` key — this repo has already been burned by a baked-in `apiKeyHelper` in that same file overriding `CLAUDE_CODE_OAUTH_TOKEN`.
- The hook receives tool input as **JSON on stdin** — parse it. Do not expect template arguments.
- There's no `jq` in the image, but there is Node. Write the hook in Node and keep its source as an exported string in a module rather than a file read at runtime, so Vercel's bundler can't leave it behind.
- Exit 2 blocks and feeds stderr back to the model; exit 1 does not block. The docs also describe an exit-0-plus-JSON form — pick one mechanism, not both, because JSON is ignored on exit 2.
- **Verify empirically whether the hook fires at all under `--dangerously-skip-permissions`, and report what you observe.** The docs say PreToolUse runs before the permission prompt for every tool, and the hook payload can carry `permission_mode: "bypassPermissions"`, which implies it does fire. But there are open reports claiming the flag skips the hook layer entirely, and older ones where the hook fired asynchronously and the command ran anyway. This cannot be settled by reading. Test it, state the version you tested on, and treat the hook as a nudge either way.
- One thing that *is* documented and worth knowing: `permissions.deny` rules apply in **every** mode including `bypassPermissions` (only `allow` rules become no-ops there). So if the hook proves inert, a single narrow deny rule is the documented fallback — same one guard, not a denylist. Propose it, don't add it unasked.
- Comment plainly that the hook is defeatable — an alias, a shell function, indirection like `G=push; git $G --force`, or invoking `git-receive-pack` directly all walk straight past a string match. It prevents an agent's bad decision, not an attacker's.

## Gotchas to handle or document

- `gh pr create` fails unless the branch is already pushed to the remote.
- Get the PR base branch right; don't assume `main` — read the repo's actual default branch.
- GitHub secret-scanning push protection will block a push containing a token.
- An expired token returns `401` — fail loudly and legibly rather than mysteriously.
- E2B allows outbound network by default, so token exfiltration via `curl` is possible. Note this limitation honestly rather than implying it's solved.
- Tell the model in its prompt what it can and cannot do (branch-and-PR only, no force-push, no `.github/workflows/`, token dies in an hour). Otherwise it burns minutes rediscovering the walls by hitting them.
