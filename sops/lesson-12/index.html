SLACK AGENTS · CHAPTER "0 TO 1" · LESSON 12

Give the bot a database it can ruin

Lesson 11 let the bot film what it built. But a recording of a broken flow is still a recording — and most flows worth filming touch a database the sandbox does not have. This lesson puts Postgres and Redis on the machine so it can seed data, run the flow, and check the rows afterwards. The interesting question is not how to install them. It is what "a database" should mean for a bot anyone in the workspace can talk to.

Ray's video: 6 min 47 s This page: 60–100 min At the end: a sandbox that can seed, query and film its own work

What you'll have at the end

Two more services on a machine that already had a browser — and one decision, made once, about which database the bot is allowed to know exists.

  • Postgres and Redis in the sandbox image, available to every run with nothing to install.
  • A measured answer to what they cost per message, which is not the answer you would guess.
  • The bot told it has them, the same way lesson 11 told it about the browser.
  • A written line between a throwaway database and a real one.

Who this is for, and what it assumes

You finished lesson 11, so the sandbox has Chromium, files come back through a single-use upload URL, and you have rebuilt the E2B template at least once — that command is needed again here.

No new credential. No new account. This lesson is two lines of template and one decision, and the decision is the part worth your time.

Why this lesson exists

This is the last lesson that adds to the machine. From 13 onward the course stops giving the bot new powers and starts shaping how it uses the ones it has.

The gap this closes. A browser can click through a signup form. It cannot tell you whether the row landed, whether the second account collided with the first, or whether the queue drained. Without state, "verified" means "the page rendered" — which is exactly the class of bug that survives a demo and dies in production.

  2. Part 2 · Build it DO NOW Seven steps: one decision, a request, a review, a build you run yourself, a merge, a three-way live test, and the briefing — then a record of what happened when they were run. 60–100 min.
  3. Part 3 · Keep for later REFERENCE The template written out, the failure table, what this page verified, and where everything lives.

Before you begin

Do not give the bot your real database. Ray mentions that his own application runs on a hosted Postgres, and the natural next thought — the one that makes this feature feel properly useful — is to hand the bot that connection string so it can verify against real data.

The rule you wrote in lesson 10 already decides this: a capability is addable only if handing it to any workspace member would be acceptable. A production database fails that test, and does not pass it by being read-only. What this lesson installs is an empty local Postgres that dies with the machine — and that is not a limitation to work around, it is the thing that makes the feature safe to have at all.
  • Lesson 11 finished, and you have run bin/with-secrets node e2b/build.mjs once.
  • Twenty minutes where a production deploy is fine — the template build ships the moment it completes, as it did last lesson.
  • No new accounts or keys. If a step asks you for one, something has gone wrong.
PART 1

Understand what you're building

Four things: why lesson 11's browser proves less than it looks like it proves, what a service in the image actually costs per message, why the bot cannot do this job itself, and where the line sits between a database it may ruin and one it must never see.

What a browser alone can and cannot proveA recording of a broken flow is still a recording. The camera does not know.

UNDERSTAND

Lesson 11 ended with a video of a counter going up, and that felt like proof. It was proof of something narrow: the page rendered and responded to clicks. Most changes worth reviewing are not like that.

The changeWhat a browser seesWhat is actually in question
"Signup now rejects duplicate emails"A form, an error messageWhether a second row was written anyway
"Invites expire after 7 days"A page saying expiredWhether the old rows were ever aged, or just hidden
"Orders move to the fulfilment queue"A success toastWhether anything reached the queue
"Admins can see other users' drafts"A list with items in itWhether it is their items — which needs four accounts to exist first
A film of a rehearsal. The browser records the performance faithfully and has no opinion about whether the stage was set. Seeding the database is setting the stage; reading the rows back afterwards is checking that anything actually moved.
The last row is the one that changes what is possible. "Four accounts exist, in this configuration" is not something a browser can arrange by clicking — it is minutes of signup flow, or one SQL statement. Ray makes exactly this point: with a database on the machine, Claude can seed the state a test needs and then verify against it.

And why Redis comes along

Ray adds Redis in the same breath, without saying why, and it is worth a sentence: the things applications put in Redis — sessions, queues, rate limits, caches — are precisely the things that behave correctly on a first click and wrongly on the second. They are invisible to a browser and awkward to assert on without the server in front of you.

You may not need it. Nothing in this repository uses Redis today. Adding it is a bet that your applications do, which for Ray is true. Step 1 asks you to make that call deliberately rather than by copying.

What a service in the image costs per messageMeasured before the change. The answer is not the one lesson 11's reasoning suggests.

UNDERSTAND

Lesson 11 established a rule that sounded general: a fresh sandbox per message turns every install into a per-message cost, so put it in the image. Applied here that suggests Postgres and Redis in the image will make every message slower, and that the cost is the price of the feature.

That reasoning is half right, and the half that is wrong matters. Measured on this project's image immediately before this lesson:

MeasurementMedian of 3
Sandbox.create() returns519 ms
First command actually runs696 ms total
E2B boots from a snapshot, not from a container pull. That is why a sandbox carrying Node, git, the GitHub CLI, Claude Code, Playwright and a 114 MB Chromium starts in about half a second. Adding files to the image is close to free at boot. The lesson-11 rule was about avoiding a download per run, and it still holds — but it never implied that a bigger image boots more slowly, and here it plainly does not.

So the cost is not the installing. It is the running:

QuestionWhere the cost lands
Are the binaries on disk?Image size. Nearly free, per the numbers above
Is a server process up and accepting connections?Per message, every message — a database has to initialise a data directory and reach a ready state before anything can connect
Does every run need it?Most do not. "What is 2 + 2?" pays the same startup as a four-account seeding test
Which makes "always on or on demand" the real design question, and it is one the video does not raise. Ray has the services running in the sandbox. The alternative is that they are installed but idle, started by the model in the runs that need them — a second or two on those runs, nothing on the rest. Step 1 asks you to choose, and step 4 measures the result so the choice is not a guess.
Measure before, not after. The numbers above exist because they were taken while the old image was still the live one. After the change there is nothing to compare against, and "it feels about the same" is not a finding.

Why the bot cannot do this one itselfRay gives a reason, corrects it mid-video, and the real answer is better than either.

UNDERSTAND

This is the first lesson since 09 where the work does not go to the bot in Slack. Ray switches to his local Claude Code and explains why:

Ray: "it's much better to do this locally because we're going to be building the image as well, and our actual sandbox doesn't have enough memory and capacity to build a sandbox image."

Then, later in the same video: "I was actually a little bit wrong earlier because I said the build happens locally for the template image, but it actually happens on e2b.dev's own cloud system."

The second statement voids the first. The build runs on E2B's builders wherever you type the command — which is visible in the build log, where every step is executed remotely. Memory is not the constraint.

The real reason is a credential, and it is one this project created on purpose. E2B_API_KEY reaches two places: the Vercel function, which uses it to create sandboxes, and e2b/build.mjs, which uses it to build images. It is never passed into a sandbox. So the bot cannot build a template however much memory it has — it has no way to authenticate to E2B.

That boundary is the same shape as two you already have. The GitHub App's private key stays in the function and only a one-hour installation token crosses. The Slack token stays in the function and only a single-use upload URL crosses. Here, nothing crosses at all: the ability to create sandboxes is deliberately not a thing that sandboxes have. An agent that could mint its own machines would be an agent whose spending has no ceiling.

Which leaves a split you have already used once. Lesson 11 ran exactly this way without anyone naming it as a pattern:

JobWhoWhy
Edit e2b/template.mjs, open a pull requestThe botIt is code in a repository it can reach
Review the diffYouLesson 11 found two bugs here that the author could not see
Run the buildYouThe credential is yours, and the build is a production deploy
Test the result end to endThe botIt is the only party that can run inside the new image
So "does Ray dogfood this lesson" has two answers. The template change: no, he does it locally. The verification: yes, through Slack — and that half is the half that can only be done from inside.

Which database, and the one you must not connectThe feature is only safe because the data is worthless. Keep it that way.

UNDERSTAND

Everything above describes a Postgres that starts empty, holds only what a test puts in it, and is destroyed minutes later along with the machine. Every useful property of this lesson depends on that.

Sandbox Postgres (this lesson)Your real database
Contents at startNothingEverything
Worst case if the model runs DROP TABLEThe test fails. Try againThe obvious
Worst case if a web page the browser loaded tells it to exfiltrate rowsIt exfiltrates rows it wrote itself, thirty seconds agoThe obvious
Who effectively has accessAnyone who can message the bot — which is fineAnyone who can message the bot — which is not
The last row is the whole argument. There is no per-user or per-channel scoping in this design. A DATABASE_URL pointing at production is not a capability the bot has; it is a capability every member of the workspace has, mediated by a model that reads web pages for a living. Read-only does not fix it: "the bot can read customer data" and "anyone in the workspace can read customer data, by asking nicely" are the same sentence.
And you already wrote the rule. Lesson 10 put it in CLAUDE.md: a capability is addable only if handing its full power to any workspace member would be acceptable. This lesson is its first real test, because unlike a search engine, a production database is genuinely tempting — it is the difference between verifying against fixtures and verifying against reality.
If you need real data, the answer is a copy, not a connection. A restored snapshot with the sensitive columns scrubbed gives you realistic shapes and volumes, in a database that is still worthless. That is more work than pasting a connection string, which is precisely why the decision should be made now, calmly, and not at the moment a test is failing.
THE DECISION THIS PAGE MAKESPostgres and Redis go in the image, empty and local, and nothing in this project ever holds a connection string to a database that matters.
PART 2

Build it

Seven steps. The same shape as lesson 11 — decide, ask, review, build, merge, verify, brief — because that shape was found the hard way and it worked. A final section records what happened when these steps were actually run, on 2026-09-17.

Step 1 of 7 — Decide what goes in, and whether it runsTwo questions Ray answers by default. Both are cheap now and awkward later.

DO NOW

  1. Postgres, Redis, or both? Ray adds both. This page follows him, on the grounds that the lesson is about the pattern and the second service costs almost nothing once the first is there — but say why out loud, because "nothing here uses Redis today" is also a defensible answer.

  2. Running always, or started on demand? This is the one the video does not ask.

    Always runningStarted on demand
    Cost on a run that needs a databaseNothing extraA second or two to start
    Cost on a run that does notThe same startup, every message, foreverNothing
    What the model has to knowNothing — it is just thereOne line: "start it if you need it"
    Failure modeA slow boot nobody attributes to this lessonThe model forgets, and reports "no database" when there is one
    Recommendation: install always, start on demand, and make step 7's briefing carry the one line that prevents the failure mode. Most messages to this bot are questions, not database tests, and a cost paid on every message for the benefit of a few is the kind of thing that never gets revisited because nobody can see it.

  3. Write down the boot numbers you are about to change. On this project, immediately before the change: 519 ms median to create a sandbox, 696 ms to the first command running. Take your own if you have not.

    There is no way to take a "before" measurement after the build. The template name is the only handle, and the new image replaces the old one under it.
CHECKPOINTYou can say which services go in, whether they run by default, and what the machine's boot time was beforehand.

    Two departures from Ray, both deliberate. He has the services running in the sandbox; this installs them idle, for the reason in step 1.   2. Spell out the design, or the request times out.     Why a template change needs this and lesson 11's did not. Ray's agent went "back and forth a few times with e2b.dev because it kept failing… and then it basically realized it made a wrong assumption". Ours cannot iterate against the builder at all, so research it has no way to test is research it cannot finish. Hand it the decisions and it writes them correctly in a minute.
CHECKPOINTA pull request touching e2b/template.mjs and nothing else, plus a message naming the start commands.

Step 3 of 7 — Review the diffFive checks. The first two are where a database in a container usually goes wrong.

DO NOW

  1. Read it against this list.

    CheckWhat wrong looks like
    The data directory is initialised at build time, as the right userInitialised at run time, so every message pays for it; or initialised as root, so user cannot write to it and the server fails to start with a permissions error that names a path, not a cause

    Versions pinned, like everything else in the imageWhatever the distribution's default happens to be on the day of the next rebuild. versions.js exists now; use it

  2. Ask what would have gone red. A template change is hard to unit-test, so expect few or no new tests here — but say that explicitly rather than letting a passing suite imply coverage it does not have. Lesson 11 shipped "57/57 pass" on a change no test touched.

    The real test for this one is step 4. Which is a reason to do step 4 attentively, not a reason to skip the question.

  3. What the review found here. A subagent read PR #11 against that list; with no container runtime on the Mac there was no dry run, so this was reading only. Two findings, both fixed in one round:

    FindingFix

Step 4 of 7 — Build the image, and measure what it costYour credential, your production deploy. Then the numbers that tell you whether step 1 was right.

DO NOW

  1. Check out the branch and build.

    gh pr checkout N
bin/with-secrets node e2b/build.mjs
    Still a production deploy dressed as a local command. The image registers under joestar-claude, which every Sandbox.create() asks for, so the next message anyone sends the bot boots it. No review, no CI, no rollback — and this time the change is two server packages rather than a browser, so a template that fails to build leaves production on the old image while your branch says otherwise.

    Confirm a new build id, not merely an absence of errors.

    The template is whatever branch is checked out. The first attempt here finished in 14 seconds and looked like a triumphant cache hit. It had rebuilt the old image: the checkout was still on a docs branch, so e2b/build.mjs read a template.mjs with no database in it and registered that under joestar-claude. A fast build after a real change is the symptom.

  2. Expect this to fail at least once. Ray's did — repeatedly — and his agent could iterate against the builder directly. Yours cannot, so read the failing step, and take the error back to the thread in step 2 rather than patching template.mjs yourself. Here the second attempt, from main, took 1 min 11 s over 12 steps, initialised the cluster and stopped it cleanly, and needed no third — the install-time start problem the callout below predicts never appeared, because PR #11 dropped the cluster the package makes.

    Database packages are the classic case. Installing a database in a container image usually tries to start a service during installation, in an environment with no init system, and fails in a way that names neither. If the build dies inside the install step, that is the first thing to suspect.

  3. Measure the new image against the numbers from step 1. Boot a sandbox, time Sandbox.create() and the first command, then time starting each service to a ready state. Three questions:

    QuestionWhat the answer tells you
    Did boot time change?Whether "adding to the image is nearly free" survived contact with two servers
    How long to a usable database?What a test that needs one actually pays
    Does it work as user, with no sudo?The permissions trap from step 3, caught here rather than from a Slack thread
    Do this before Slack, as in lesson 11. Driving it by hand separates "the image is wrong" from "the model wrote a bad script" — two failures that look identical from a thread, and last lesson that separation is what found the real bug. It earned its keep again: both of this lesson's real defects were things only a boot could show, and neither was visible in the diff.

  4. What three boots said. Boot time held — 654 ms median to create against a 519 ms baseline, and 154 ms to the first command against 696 ms — on an image that had also gained Codex 0.154.0 (339 MB) from PR #12 in the same build. Postgres 15.19 was present and so was Codex. Then the two problems:

    What the boot showedRoot cause
    Redis was already running — pid 331, listening on 127.0.0.1:6379, on a machine that was supposed to start nothingThe sandbox boots /sbin/init, which honours the /etc/rc2.d/S01redis-server link and the systemd wants-link the package installs. Postgres only looked obedient because its cluster had been dropped
    pg_ctl -w start hung the SDK call for the full 60-second timeout, although the server came up and workedpg_ctl without -l hands the server the command's stdout and the server keeps it open, so the SDK never sees EOF and waits for a command that has already finished
    Both fixed in PR #19, and both cheap. The template now removes the rc links and the wants-links for both services, and the start command carries -l /home/user/pgdata/server.log. The rebuild took 21 s. Re-measured: nothing running on boot, Postgres ready in 1.3 s, Redis in 0.5 s, create 543 ms median, first command 150 ms.
    One thing seen and not explained. ss reports listeners on the sandbox's own 169.254.0.21 address for 5432 and 6379 with no owning process. That is consistent with E2B's port forwarding sitting outside the namespace, but it was not verified — treat it as an observation, not a fact.

Step 7 of 7 — Tell the model it has themThe lesson-11 step, repeated — and now load-bearing, because on-demand services have to be started by someone who knows they exist.

DO NOW

Lesson 11 added browserCapabilities() to the prompt the function builds, so the model is told about its browser on every run rather than discovering it. The same argument applies here, and one thing makes it stronger: if the services are installed but idle, a model that does not know they exist will report that it has no database — and be wrong, on a machine that has one.

Where this briefing ended up. By the time it was written, lesson 13 had replaced the prompt block with a persona file written into every sandbox, so the database briefing lives there rather than in a string the function assembles. It carries both start commands, and — after step 4 — the sentence "It takes about ten seconds; do not run it in the background." Same argument, better home.

  1. Ask for a capabilities block, in the same place and shape. It should carry the exact start commands, that the database is empty and local and dies with the machine, and that nothing in it should ever be treated as real data.

    Derive the facts, do not restate them. Lesson 11's review found the briefing hard-coding a cap that lived elsewhere, three hours after that cap changed. Anything with a version or a port in it belongs in versions.js and gets interpolated.

  2. Verify it the same way: in a channel whose topic names no repository. Nothing is cloned, so a correct answer can only have come through the prompt. Ask what database it has and how it would start it, and require it to answer without running anything.

CHECKPOINTIn a channel with no repo in its topic, the bot describes its database, names the start command, and says the data is throwaway.

REFERENCE

The lesson shipped in two pull requests: the template change, and a second one fixing what the first could not have known. Both defects were invisible in the diff and obvious on the first boot, which is the shape this lesson has to teach.

The request that researched instead of writing

The first attempt at step 2 left the bot to work out how Debian packages Postgres. It read for the full 255-second budget and pushed nothing. The retry handed it the design — major version, package names, symlink targets, the exact initdb line, the run-time environment — and it opened PR #11 in 75 seconds. For a template change, spell out the design. The bot cannot build the image, so it cannot test an assumption, so research is the one thing it should not be asked to do here.

A CLI is a binary on a path. A database is a binary, a data directory, a user who owns it, and a process that has to be running. Four things instead of one, and three of them are where it goes wrong.

IdeaWhy it is not just "install postgres"
Initialise the data directory at build timeA fresh cluster has to be created before a server can start. Do it in the image and starting is fast; do it at run time and every run that wants a database pays for it
Own it as the account that will use itThe build runs as root, the sandbox runs as user. This is the same trap Playwright set in lesson 11, in different clothes: the files exist and the wrong account owns them
Installing may try to start a serviceDatabase packages commonly start a server as part of installation, in an image build with no init system. That fails, and the error names neither the cause nor the fix
Nothing listens to the outsideThere is no outside. Local sockets or loopback only, no password, no exposed port — the machine has one occupant and lives five minutes
The build-time / run-time split is the through-line of these two lessons. Lesson 11 hit it with setEnvs, where a variable set at build time was gone at run time. Here it is data directories and processes. Same question each time: does this survive the snapshot, or does it have to happen again on every boot? Files do. Environment and processes do not.

What you seeWhat it usually is
A service is already running on a machine that starts nothing — redis-cli ping answers before you start anything, or ps shows a pid you did not createHit here. The sandbox boots /sbin/init, which runs the rc links and systemd wants-links the Debian packages install. Not writing a start command is not enough; the template has to delete those links
Starting Postgres never returns — the SDK call sits until its timeout, while psql from another command works fineHit here. pg_ctl without -l gives the started server the command's stdout, and the server holds it open, so the SDK waits for an EOF that never comes. Start it as pg_ctl -D "$PGDATA" -l /home/user/pgdata/server.log -w start, and never in the background
The build finishes suspiciously fast and the new packages are absentHit here. e2b/build.mjs reads whatever template.mjs is checked out. A 14-second build after a real change means you are on the wrong branch — and it has already republished the old image under the live name
The image build fails inside the install stepThe package tried to start a service during installation. Installing without triggering that, or accepting the failure and initialising by hand, is the usual fix
The server will not start, complaining about a directoryThe data directory is owned by root and the sandbox runs as user. Lesson 11's trap again
"database does not exist" on the first connectionA cluster was created but no database inside it, or not one named after the connecting user
Connection refused, immediately after starting the serverStarting is asynchronous. The command returns before the server accepts connections — wait for ready rather than sleeping a guess
Works by hand, fails from SlackThe model does not know the service needs starting. That is step 7, and it is why step 7 exists
Every message got slower and nobody noticed for a weekSomething starts on boot. Compare against the step 1 numbers
The bot says it has no databaseEither the briefing did not ship, or it shipped and the model is right and the image did not. Check by hand before believing either
