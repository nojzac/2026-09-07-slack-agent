SLACK AGENTS · CHAPTER "0 TO 1" · LESSON 15

Give the bot a memory that outlives its sandbox

Claude Code already has a memory feature. It writes notes, keeps an index, and curates the pile when it grows — and all of it lands on the machine the session ran on. That is fine for Ray, whose sandbox pauses and resumes. Here the machine is destroyed the moment the answer is posted, so the whole lesson is one question: where do the notes live between messages? The answer is a private git repository, cloned before claude starts and pushed after it finishes, whether or not the run worked.

Ray's video: 3 min 55 s This page: 60–90 min At the end: a bot that remembers, per channel, across sandboxes

What you'll have at the end

Three sandbox commands per message, two of them new in this lesson, and one private repository holding everything the bot has been told to keep.

  • A private repository, nojzac/joestar-memory, with one directory per Slack channel and a shared/ beside them.
  • Claude Code's own auto-memory pointed at that directory through ~/.claude/settings.json — no recall endpoint, no embeddings, no database.
  • A 25-second budget carved out of the claude command's time, only on runs that actually use memory.
  • Token minting that takes a list — topic repo plus memory repo — with every entry owner-checked before any network call.
  • One recorded exception to "no private repository gets App write access", taken deliberately on 2026-09-17.
  • AGENT_MEMORY_REPO in Vercel as the kill switch: unset it, redeploy, memory is off.

Who this is for, and what it assumes

You finished lesson 14, so the bot has a persona and a toolkit of skills that ship into every sandbox. You have a GitHub App from lesson 08 that mints an hour-long installation token per run, and you know from lesson 09 that main is protected and the bot opens pull requests rather than pushing. You can set a Vercel production environment variable and trigger a deploy. Nothing new is installed: this lesson adds no binary to the E2B image, so there is no template rebuild in it.

Why this lesson exists

A persona is what you told it once. Memory is what it worked out since — which is why memory, not the persona file, is the thing you have to be able to audit and revert.

The gap this closes. Up to here the bot starts every message with total amnesia. Correct it and the correction lasts until the reply is posted. A channel that has explained its deploy process forty times has been explaining it to forty different machines. This lesson is the first one where something the bot learns on Tuesday is still true on Wednesday.

Before you begin

This lesson breaks a rule you wrote in lesson 09, on purpose, and you need to agree to it first. The standing rule is no private repository gets contents: write from the App, because on GitHub's free plan a private repository's branch protection does not enforce and does not say so. The memory store has to be private and the bot has to write to it, so the rule cannot hold. It was taken as a recorded exception on 2026-09-17, not a revision: this one repository holds only the bot's own notes, and the bot writing its main is the design rather than a risk. Everything else still obeys the rule. If you are not willing to record that exception, stop here — there is no version of this feature without it.
  • A GitHub account that can create a private repository and change which repositories your App is installed on.
  • The Vercel project, so you can add a production environment variable and redeploy.
  • A test channel whose channel ID you can copy — right-click the channel, Copy link, and the ID is in the URL.
  • The knowledge that the premise is unverified. That Claude Code honours auto-memory at all in -p (headless) mode is the assumption this whole feature rests on, and step 6 is where you find out.
PART 1

Understand what you're building

Five things: why Ray's answer does not transfer, what the harness already does so you don't build it, where the time comes from, why the push sits where it does, and the access question a private store forces you to settle.

Why memory cannot live on the sandbox hereRay's sandbox pauses and wakes up again. Ours is destroyed after every single message.

UNDERSTAND

Ray's design and this one start from the same place — Claude Code's auto-memory writes markdown files to a directory — and diverge on one fact about the machine underneath.

Ray's runtimeThis runtime
The sandbox pauses between turns and resumes with its disk intactrunClaude calls sandbox.kill() in a finally block on every path. There is no next turn on this machine
So he writes memory under $HOME — not /tmp — and it is still there next timeUnder $HOME or /tmp makes no difference; both are gone
Git is a backup: the durable copy for when a box is finally recycledGit is the storage. The clone is a working copy that exists for about two minutes
A pull before the process starts, a push after it ends, bounded at about 40 sThe same two operations, bounded at 25 s — because they are not a background sync, they are on the critical path of a reply somebody is watching
A hotel room versus a locker. Ray checks into a room and leaves his things there overnight. This bot is issued a fresh room every time it walks in, so anything it wants tomorrow has to go back into the locker on the way out — and the walk to the locker has to fit inside the visit.
The upside of being forced into git. Because the store is a repository rather than a disk, every memory the bot writes is a commit: diffable, attributable, revertable. A memory that turns out to be wrong — or planted — is git revert, not an archaeology exercise. Ray makes the same point about his backup; here it is the only mode.

Auto-memory is a feature you configure, not one you buildTwo settings keys, one directory, and a deliberate refusal to write a recall step.

UNDERSTAND

Claude Code already loads a MEMORY.md index at session start, decides during the session what is worth keeping, writes topic files beside the index, and curates them when they grow. Ray's prompt is emphatic that this is the whole point: "Our job is only the git plumbing and one settings file."

{
  "hooks": { /* … whatever configureGitHub already wrote … */ },
  "autoMemoryEnabled": true,
  "autoMemoryDirectory": "/home/user/memory/channels/C0C2FES3UGJ"
}

That file is written at user scope — /home/user/.claude/settings.json — and it is merged, never replaced. mergeSettings exists as its own exported function for exactly that reason: the hooks block from lesson 08's push guard has to survive, and a shallow spread that can be unit-tested without booting a sandbox is cheaper than discovering in production that memory silently disabled the guard.

The directory is keyed by channel ID, never channel name

The path is channels/<channel id>/, using Slack's internal ID — C0C2FES3UGJ, not #joestar-dev. Names get renamed; IDs do not. events.js refuses anything that is not ^[A-Z0-9]+$ rather than sanitising it, so a strange channel value turns memory off for that run instead of writing into a path nobody intended.

Why "do not build a recall step" is the strongest instruction in Ray's prompt. Every obvious alternative — a memory skill, an embedding store, a database, "load the memories into the prompt" — is more code producing a worse copy of something the harness does for free, and each one has to be maintained against a harness that keeps improving underneath it. The temptation is real because the git plumbing feels too small to be the answer. It is the answer.

What the model is told, and only when memory actually came up

memoryBriefing appends four lines to the prompt — where memory lives, which directory is this channel's, that shared/ applies everywhere, and that anything it is asked to remember gets written as a markdown note that is pushed after the run. It is appended by runClaude rather than folded into buildPrompt, because runClaude is the only thing that knows whether the clone succeeded this time.

Where this departs from Ray. His prompt asks for a fuller disposition in --append-system-prompt — what is durable versus transient, the idioms "remember for this channel: …" and "what do you remember about this channel?", and recording corrections after being corrected. Ours is four plain lines in the prompt. His two-tier read/write rules for public versus private channels are also not built: shared/ exists as a directory and is mentioned in the briefing, but nothing enforces who may write to it.

Where the 25 seconds come fromMemory runs inside the same 285-second sandbox as everything else, so its time is taken from the model's.

UNDERSTAND

The sandbox gets the full timeoutMs. The claude command deliberately gets less, so it cannot run the machine out of clock before the work that has to happen after it:

const runTimeoutMs = Math.max(
  timeoutMs - UPLOAD_BUDGET_MS - (memoryRequested ? MEMORY_BUDGET_MS : 0),
  0,
);
ConstantValueWhat it pays for
timeoutMs285 000 msThe sandbox's whole life, near the 300 s function ceiling
UPLOAD_BUDGET_MS30 000 msStreaming output files to Slack — from lesson 11
MEMORY_BUDGET_MS25 000 msBoth memory commands, and only when memory is requested
MEMORY_SETUP_TIMEOUT_MS8 000 msShallow clone, branch check, mkdir -p
MEMORY_PUSH_TIMEOUT_MS12 000 msadd, commit, push
The arithmetic is checked at module load, not in a comment. claude.js throws at import time if 8 000 + 12 000 + 5 000 margin ever exceeds MEMORY_BUDGET_MS. Someone trimming the budget to buy the model five more seconds gets a loud failure on deploy instead of a memory push that starts and is cut off halfway — which is the failure that looks like everything working.
A run with no memory pays nothing. memoryRequested is Boolean(memoryRepo && githubToken), decided before the sandbox boots, and the subtraction is conditional on it. Turning memory off does not leave 25 seconds sitting unused.
Where this departs from Ray. His prompt bounds the whole sync at about 40 s and, when out of budget, returns a synthetic failure so callers take their ordinary "that step didn't work" branch. Here the two commands carry their own timeouts and the budget is 25 s, because it is subtracted from a model that already needed every second it had.

The push runs even when the run failsOne finally block, two variables hoisted out of the try, and a swallowed error.

UNDERSTAND

A crash mid-run is exactly the case where memory is most valuable and most easily lost: the model may have written its note before whatever went wrong. So the push sits in the same finally that kills the sandbox, ahead of the kill.

} finally {
  if (memoryActive) {
    try {
      await pushMemory(sandbox, { envs, channelId });
    } catch {
      console.warn('[memory] push failed');
    }
  }
  await sandbox.kill().catch(() => {});
}
Two small things in that block are load-bearing. envs and memoryActive are declared with let above the try, not inside it, because try { const x } does not leak x into finally — without the hoist the push has no credentials to push with. And the catch is bare: a memory failure must never replace the error the caller was about to see.
The ordering with uploads is deliberate. Output files are collected and streamed to Slack inside the try, while the sandbox is certainly alive. Memory is pushed in the finally, after them. Both happen before sandbox.kill(), which is the only hard deadline either of them has.

Best-effort, everywhere, on purpose

setUpMemory returns a boolean and never throws; pushMemory logs and returns and never throws. A missing repository, a missing token, a clone that times out, a push GitHub rejects — every one of those degrades to "no memory this run", the same way the GitHub setup and the Codex credential already did. A turn must never be lost to the feature that was supposed to make turns better.

The access decision: one private repository, and a token scoped to a listThe App now mints for two repositories at most, and a review caught the version that failed open.

UNDERSTAND

Before this lesson, each run minted an installation token scoped to one repository: the one named in the channel topic. Memory adds a second, so mintInstallationToken now takes a list:

const repos = [repo, memoryRepo].filter(Boolean);
const github = repos.length
  ? await tryMintInstallationToken({ repos })
  : { token: null, reason: null };

Every entry is checked against ^[\w.-]+\/[\w.-]+$ before any network call, and the owner half of every entry is checked against the installation's own account, looked up once from the API.

The first version failed open, and the failure was invisible. A malformed entry — a memory repository typed without an owner, say — was filtered out rather than refused. The caller's non-empty list looked honoured, but the function then minted for zero repositories, and GitHub reads zero repositories as every repository the App is installed on. A typo in an environment variable would have quietly widened the token instead of narrowing it. The fix is to throw: refusing to mint: invalid repo name "…", before the request. This is the same bug class as lesson 09's, caught earlier only because someone reviewed the diff.
A filter that lets everything through when it breaks. A door that opens when its lock jams is worse than a door with no lock, because you stop checking it. Any code that narrows access must fail closed — and "fail closed" here means refusing to mint at all rather than minting something broader.

Why a private repository gets App write access, this once

The standing rule from lesson 09: no private repository gets contents: write, because on the free plan a private repository's branch protection does not enforce and does not tell you so, which makes "private" mean "unprotected". The memory store cannot satisfy that rule — it must be private, because it holds whatever the workspace told the bot, and the bot must be able to write it, because that is the entire feature.

Recorded as an exception, dated, not as a revision. On 2026-09-17 this one repository was granted App write access, on the grounds that it holds only the bot's own notes and the bot writing its main is the design rather than a risk to be protected against. The rule still stands for everything else. The distinction matters: an exception you wrote down is something a later reader can weigh, while a rule quietly rewritten is a rule nobody will ever question again.
What keeps the blast radius small. The token expires in an hour, it is minted fresh per request with no caching, and it now reaches at most two repositories: the channel's topic repository and the memory store. A channel with neither gets no GitHub access at all — the list is the boundary, not a hint.
THE DECISION THIS PAGE MAKESUse Claude Code's own auto-memory, store it in one private git repository keyed by channel ID, pay 25 seconds of the model's time for it, push in a finally so a failed run still remembers, and record the private-repository write access as a dated exception rather than changing the rule.
PART 2

Build it

Six steps. Three are done by hand in a browser and cannot be delegated — creating the repository, installing the App on it, and setting the environment variable. Two are pull requests the bot writes. The last one is the test that decides whether any of it worked.

Step 1 of 6 — Create the private memory repositoryBy hand, in the browser. It is the durable half of the feature and nothing else creates it.

DO NOW

  1. Create a new repository named joestar-memory under your own account, and set it to Private. Here that is nojzac/joestar-memory.

  2. Leave it empty. No README, no .gitignore, no licence. An empty remote clones fine and leaves HEAD unborn; setUpMemory handles that by checking out main before the first commit, so initialising it yourself buys nothing.

    Where this departs from Ray. His prompt asks for a README.md explaining the layout and a .gitattributes with *.md merge=union, so two threads writing at once merge instead of conflicting. Neither is here. With a destroyed-per-run sandbox and a push every turn the window for a conflict is small, but it is not zero — adding the .gitattributes is a one-line improvement worth making.

  3. Write down the owner/repo slug. You will need it twice: once for the App installation, once for the Vercel variable, and they must match exactly.

CHECKPOINTAn empty private repository exists and you have its owner/repo slug. Nothing can push to it yet.

Step 2 of 6 — Install the GitHub App on that repositorySkip this and memory commits locally, pushes nothing, and reports no error anyone notices.

DO NOW

  1. Record the exception before you click. This is the step that breaks lesson 09's rule. Write the decision down where a future reader will find it — here it went into RESUME.md, dated 2026-09-17, as an exception rather than a change to the rule.

  2. Add the repository to the installation. GitHub → Settings → Applications → your App → Configure → Repository access, and add joestar-memory to the selected list. The installation ID does not change.

  3. Check the App's permissions include contents: write. It already does if the bot has been committing since lesson 08. Read access alone produces a clone that works and a push that fails.

This is the silent failure of the whole lesson. Ray flags it explicitly: if the App is not installed on the store repository, memory commits locally and never pushes, and nobody notices. Here the sandbox is destroyed afterwards, so the commit does not even survive to be found later — the only trace is one [memory] push failed line in the Vercel log, and everything in Slack looks perfect.
CHECKPOINTThe App's repository list contains both your sandbox/topic repository and the memory repository.

Step 3 of 6 — Ask for the runtime: clone before claude, push after itThe first pull request. Paste Ray's prompt, then hold the result against the constraints that differ here.

DO NOW

  2. Add the two facts that differ here, in your own words: the sandbox is destroyed after every message rather than paused, so the clone is a working copy and not a cache; and the memory commands run inside the same 285-second budget as the model, so the time has to be carved out explicitly and checked.

  3. Ask for the plan before the code. Ray's prompt says so and it is worth keeping — a plan that is wrong about the sandbox lifetime is cheap to correct and a merged implementation is not.

  4. Read the diff for the five things that matter: setUpMemory returning a boolean rather than throwing; mergeSettings preserving the hooks block; the briefing appended only when setup succeeded; pushMemory in the finally; and the budget constants with the module-load assertion.

    Where this departs from Ray. He asks Claude to implement, deploy, and end-to-end test in one instruction, and accepts the result. Here it was a pull request, reviewed, with tests — including one asserting the ordering of the finally push relative to sandbox.kill().

Step 4 of 6 — Widen token minting to a list, and make it fail closedThe second pull request. This is the one to review hardest; the first version failed open.

DO NOW

  1. Ask for repos alongside the existing repo, collapsing to a list internally, de-duplicated so a memory repository that happens to equal the topic repository is not sent twice.

  2. Insist on refusal, not filtering. A malformed entry must throw before the network call. State why in the request: GitHub treats an empty repository list as "every repository this App is installed on", so silently dropping a bad entry widens the token instead of narrowing it.

  3. Keep the owner check. Look up the installation's account once and compare it, case-insensitively, against the owner half of every entry. Without it, someone-else/joestar-memory would still mint a token for your repository of that name.

  4. Update events.js to validate both inputs and to log shape rather than value: [memory] off (invalid repo), [memory] off (invalid channel). An unset AGENT_MEMORY_REPO is not an error and logs nothing at that point.

CHECKPOINTmintInstallationToken throws on a malformed or foreign-owner entry, with a test proving it, and the logs never print the repository value on a rejection.

Step 5 of 6 — Set AGENT_MEMORY_REPO in Vercel and redeployOne environment variable, by hand, which is also the off switch.

DO NOW

  1. Vercel → the project → Settings → Environment Variables. Add AGENT_MEMORY_REPO with the value owner/repo — for example nojzac/joestar-memory — scoped to Production.

  2. Redeploy. Environment variables are read at run time, but the running deployment does not pick up a new one until it is replaced. Here a push to main runs the tests and deploys.

  3. Note that this is the kill switch. Unset the variable and redeploy, and every run takes the [memory] off branch: no clone, no settings keys, no push, and no time subtracted from the model.

The value is never in a file in this repository. It is not a secret — it is a repository name — but it lives with the secrets by the same route: 1Password and Vercel, set by hand, documented in joestar-agent/README.md as "Optional, Vercel only — unset = memory off".
CHECKPOINTA deployment is live with the variable set, and the logs for the next mention show a minted token scoped to two repositories rather than one.

Step 6 of 6 — Verify it liveFive checks, in this order. Until they pass, the feature is code that runs rather than a bot that remembers.

DO NOW

The premise under test is not the git plumbing — that is ordinary code with ordinary tests. It is whether Claude Code honours auto-memory at all when it is invoked headless with -p. Nothing above this line proves that.

  1. Tell it a distinctive fact. In #joestar-test, mention the bot and ask it to remember something no model would guess — a made-up phrase, a fake port number, a nonsense codename. Distinctive matters: a plausible fact can be produced by a model that remembers nothing at all.

  2. Check the log for [memory] push ok. In the Vercel function logs for that invocation. The three outcomes point at completely different problems, which is why they are three different lines — see the log table in Part 3.

  3. Check the commit landed in nojzac/joestar-memory: a commit named memory: <channel id> <timestamp>, authored by joestar, touching a file under channels/<channel id>/.

  4. Ask in a new thread in the same channel. A brand-new sandbox, a brand-new clone. If it answers with the fact, memory works end to end.

  5. Ask from a different channel. It should not know — memory is siloed per channel, and anything else means the directory is not keyed the way you think it is.

The clone command, in full

git clone --depth 1 'https://github.com/owner/repo' /home/user/memory &&
cd /home/user/memory &&
git rev-parse -q --verify HEAD >/dev/null || git checkout -b main &&
mkdir -p '/home/user/memory/channels/<channel id>' '/home/user/memory/shared'
The token is not in that string. The clone URL carries no credential. GH_TOKEN travels in the per-command envs, and the credential helper that lesson 08's configureGitHub already installed reads it from there when git actually needs it. A token in the URL would land in .git/config and in process listings.

The commit and push, in full

cd /home/user/memory && git add -A &&
git -c user.name=joestar -c user.email=joestar@users.noreply.github.com \
    commit -qm 'memory: <channel id> <ISO timestamp>' &&
b=$(git rev-parse --abbrev-ref HEAD) && git push -q origin "HEAD:$b"

add -A rather than commit -a, because a brand-new memory file is untracked and untracked is the common case here. The identity is passed at commit time rather than relying on repository configuration a differently-provisioned box may not have.

The gap this implementation still hasRay calls it "the single most important line in the whole feature", and it is not here.

REFERENCE

Ray's prompt is emphatic: on every failure path, write autoMemoryEnabled: false explicitly and delete autoMemoryDirectory, because the CLI default is on. A clone that fails and simply returns leaves the model happily writing memories into a local, per-sandbox directory that nothing ever syncs.

In this implementation setUpMemory writes settings.json only on the success path. On the off and setup failed paths the file keeps whatever configureGitHub wrote, which contains the hooks block and no autoMemoryEnabled key at all.

What that means here, stated carefully. The consequence Ray describes is a persistent sandbox filling up with unsynced notes. This sandbox is destroyed minutes later, so nothing accumulates and nothing is silently lost that would otherwise have been kept. What is lost is the signal: a failed run looks to the model exactly like a working one, so it may tell somebody it has remembered a thing it has not. Whether the default is on and what it does with no directory set is untested here. Writing the key explicitly on both failure paths is two lines and removes the question — it is the first change to make to this feature.

Other things Ray's prompt asks for that are not built

  • Two tiers. A shared directory readable by every channel and writable only from public ones. shared/ is created and mentioned in the briefing; nothing enforces it.
  • Conflict refusal. No check for .git/rebase-merge or unmerged XY codes before add -A. With a per-run clone and a push every turn this is unlikely rather than impossible.
  • Push-rejected retry. No pull --rebase --autostash and second attempt; a rejected push is logged and the commit dies with the sandbox.
  • A pull before the model starts. Not needed — a fresh --depth 1 clone per run is already the newest state.
  • A curation skill. A user-invoked "prune and reorganise this channel's memory" task. Ray suggests building it separately, after writing works. It has not been built.

Two traps this lesson producedBoth are about git rather than memory, and both cost a rebuild of work that already existed.

REFERENCE

Squash-merging a pull request that a later one was stacked on

Branch B was built on branch A. A was squash-merged into main, which rewrote its commits into one new commit with a different hash, and B immediately went CONFLICTING — every commit it inherited from A now looks like an unrelated change.

The fix is to merge main in — never rebase. A rebase rewrites the branch's history and needs a force-push, and the push guard from lesson 08 blocks force-pushes. After this, later requests were based on main rather than stacked on each other.

A merge performed by the bot dropped one side of the change

The memory runtime was written, then origin/main was merged into the branch by the bot. The merge commit resolved that conflict by taking the incoming side, and about 150 lines of memory runtime disappeared from claude.js — while the tests for it, in a file with no conflict, stayed. The repair was a commit whose message says exactly what happened: memory runtime restored from 81ffa73.

What makes this one dangerous. The merge succeeded, the branch was green on everything that still compiled, and the diff against main looked smaller rather than wrong. After any conflicted merge an agent performs, diff the merge result against both parents and check the file the branch exists to change is still changed. "It merged cleanly" is not a statement about whether your work survived.
