SLACK AGENTS · CHAPTER "USING YOUR AGENT" · LESSON 20

Delegate ownership, not tasks

Look back through your threads with the bot and one shape repeats: you notice a problem, you describe it, the bot fixes it, the thread goes quiet. Ray's point is that this makes you the trigger for every piece of work the agent ever does — so when you go on holiday, your agent goes on holiday. The alternative is to hand it a territory, a stream to watch, a standing mandate and a boundary, and stop typing.

Ray's video: 8 min 45 s This page: 25 min At the end: the four-part shape of an ownership prompt, and an honest answer about whether Joestar can hold one yet

What you'll have at the end

Ray's worked example, taken apart. Every ownership prompt is some variation on these four parts; drop the fourth and you have delegated more than you meant to.

  • The distinction, in a form you can apply — task prompts have an end state, ownership prompts do not.
  • The four parts of an ownership prompt, with the question to ask the agent before you write one.
  • A clear-eyed answer about this bot: Joestar cannot hold a standing mandate today, and the two missing pieces are named.
  • A shortlist of territories worth delegating first, chosen by how cheaply the result can be verified.

Who this is for, and what it assumes

You are using the bot daily and it works. You have merged pull requests it opened, it has a persona file (lesson 13), skills (lesson 14) and a memory repo (lesson 15). Nothing here needs new code to understand; it needs you to look honestly at who starts every run.

Why this lesson exists

Ray: "you tagging your agent and giving it a task is no different from you just using this as a glorified Claude Code inside of Slack."

The gap this closes. Parallel task delegation feels like leverage — several threads running at once, all of them yours. It is not leverage, it is a wider attention surface. The test is simple: if you stop typing for a week, what does the agent do?

Before you begin

Ownership is the most expensive idea in the chapter, and this bot cannot hold one yet. A standing mandate needs something that runs without a Slack message, and somewhere the mandate survives between runs. Joestar has neither: the Vercel function only wakes on a Slack event, and its sandbox is destroyed after every run. Part 1 names what would have to exist.
  • Your own thread history with the bot, which is the evidence this lesson turns on.
  • A willingness to delegate something you would rather keep, because the territories that stay yours are the ones where the pattern pays.
PART 1

Understand what you're building

The distinction, the prompt anatomy, the choice of territory, and what this particular bot lacks.

Task delegation and ownership delegationThe difference is whether the prompt has an end state.

UNDERSTAND

A task prompt names a defect and finishes when the defect is gone. An ownership prompt names a condition that must keep being true, attached to a stream of events that never stops arriving — so there is nothing for "done" to mean.

Hiring a contractor versus hiring a caretaker. The contractor fixes the leak you found and leaves; the same leak in a different room is a new job you have to notice and commission. The caretaker is responsible for the building being dry, and you find out about leaks because they tell you, not because the ceiling did.

Ray: "if you were to go on holiday, then your agent is doing nothing. And this is essentially the same as having an employee who's only working when you're standing right next to them."

The four parts of an ownership prompt, and what to put in eachTerritory, input stream, standing mandate, boundary — and the question that catches what you forgot.

UNDERSTAND

Ray's worked example carries all four in three sentences: "You own the payments module. Watch the payment-errors channel; when the same error shows up more than twice in a day, reproduce it, open a fix PR and post a summary in this thread. Anything that touches billing amounts or refunds — propose the change first and wait for my sign-off."

The boundary is the part people drop, and it is the part that makes the rest safe. Without it you have not said what the agent may not do alone, and "use your judgement" is not a boundary — it is the absence of one.

What can be owned

Kind of territoryExample mandate
A moduleYou own the payments module; errors seen twice get reproduced and fixed by PR
A quality barYou own test coverage; when a critical path drops below 80%, add tests and open a PR
A metricYou own homepage load time; check it daily with the browser and fix or report
A dependencyYou own the Stripe integration; when the changelog announces a breaking change, update it
An inboxYou own bug reports arriving by email; triage each one, reproduce, fix if it is not critical code
A relationshipYou own trial signups; watch for the ones not reaching the product's first real win
Ray's selection rule, worth adopting as written: delegate ownership where the result is easily verifiable. Code that runs or does not, a browser check that passes or fails, a backlog of past records the agent can grade itself against. Where verification is a matter of taste, keep the boundary tight and make it report rather than act.
The question Ray adds to every ownership prompt: "what do you need from me so you can appropriately take ownership over this? I will give you the required credentials or MCP servers if need be." Here that question has a different answer shape, because credentials do not get handed over on request — see the next section and lesson 21.
Keep the mandate in a public channel. Ray's reason is that teammates can see, refine and extend the agent's remit. The version of that here: a mandate in a public channel is a mandate somebody else can read before it surprises them.

Why Joestar cannot hold a standing mandate yetTwo missing pieces — a clock, and a place for the mandate to live.

UNDERSTAND

1 · Nothing wakes the bot but Slack

The whole agent is a Vercel function on a Slack event. No event, no run — and a mandate like "check the homepage daily" has no event at all. Something has to produce one: a scheduled GitHub Actions workflow or a Vercel cron posting into a channel, or the alert stream from lesson 19. Ray solves this with scheduled routines in his harness; here it does not exist, and building it is the real work of adopting this lesson.

2 · A prompt in a thread is not a mandate

The sandbox is destroyed after every run, and the only context a run has is the Slack thread, refetched and replayed as untrusted data. A message saying "from now on you own X" is a message in one thread that stops applying the moment the conversation moves elsewhere. A mandate has to live somewhere durable: the persona file from lesson 13, a skill in the toolkit, or the memory repo from lesson 15 — all of which reach every run by construction.

The boundary half, though, is already built. This bot proposes and a human merges: it has write access to one public sandbox repository and opens pull requests rather than pushing to main. Ray's "propose the change first and wait for my sign-off" is this bot's default for everything, which means the risk of over-delegation here is wasted runs rather than unreviewed changes.
So the honest ordering is: a durable home for the mandate, then a clock, then a mandate. Delegating ownership to an agent that only wakes when you speak to it is task delegation with more words.
WHAT PART 1 SETTLEDOwnership needs four things in the prompt and two things in the plumbing. Joestar has the boundary by default and neither of the other two.
PART 2

Decide

No code was written for this lesson. These are the four steps for when you have a stream and a clock.

Find one repeat, and turn it into a mandateStart from something that has already happened twice.

DO NOW

  1. Scroll your own threads for a problem you have delegated twice. Ray's example is being rate-limited by Sentry: fixed once, certain to recur, and he only found out by accident. A repeat is the cheapest evidence that a territory exists.

  2. Write the four parts out explicitly — territory, input stream, standing mandate, boundary — and read the mandate back asking "what did I just permit that I did not mean to permit?" If the answer is nothing, the boundary is probably missing rather than unnecessary.

  3. Ask the agent what it needs, then treat the answer as a proposal. "What do you need to take ownership of this?" is a good question with a bad default: here, credentials are not granted on request. Every item comes back as a pull request, reviewed against the CLAUDE.md capability rule, with any secret going to 1Password and Vercel and never to a file.

    Where this departs from Ray. He offers the agent credentials and MCP servers in the prompt itself. This workshop cannot: anything the bot can reach, every workspace member can reach through it. An MCP server that fails that test does not become acceptable because the agent said it would help.

  4. Put the mandate where every run reads it, and record it in RESUME.md. The persona file, a skill, or the memory repo — not a chat message. Then note in RESUME.md what the agent now owns, so the next person to read the repository learns it from the repository.

CHECKPOINTEither a mandate exists in a file every run loads, with all four parts and a line in RESUME.md — or RESUME.md records that ownership is deferred until the bot has a clock, and names what would provide one.
