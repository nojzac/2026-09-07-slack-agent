SLACK AGENTS · CHAPTER "0 TO 1" · LESSON 13

Give the bot a persona file it loads by itself

Every lesson so far added something to the machine. This one adds something to the model: a CLAUDE.md file that Claude Code reads on its own, before it reads your message. It is three minutes of video and one design decision — and the decision is not the one Ray makes, because this bot's sandbox does not survive a single turn.

Ray's video: 2 min 58 s This page: 30–50 min At the end: a persona file written into every sandbox, before claude starts

What you'll have at the end

One file, one write call, and a model that knows where it is standing before it reads a word from you.

  • A persona file in the sandbox's user root, ~/.claude/CLAUDE.md, loaded by Claude Code without anyone asking for it.
  • One batched sandbox.files.write in api/_lib/sandbox-files.js, called before claude spawns.
  • The machine's own facts in it — Node 24, Chromium, the two database servers that are installed but not running — so lesson 12's "start it if you need it" has somewhere to live.
  • A function that never throws, with a test proving it, because a broken persona must cost you a persona and not a reply.

Who this is for, and what it assumes

You finished lesson 12, so the sandbox has Chromium plus an idle Postgres and Redis, and you have the habit of asking the bot to change its own code and reviewing the pull request it opens. Nothing new is installed here and no credential is added: this lesson is one small module, one call site, and a decision about when the file gets written.

It is also the first lesson where the work you hand the bot is too big for a single run. That is worth more of your attention than the file itself.

Why this lesson exists

Lesson 12 was the last one that added to the machine. From here the course stops handing the bot new powers and starts telling it what it is.

The gap this closes. Everything the model knew about itself was arriving in the prompt, assembled per message by the function. That works, but it grows: every new fact about the machine becomes another line of prompt-building code, and none of it is the model's own to read. A persona file at the user root is the mechanism Claude Code already has for this, and it costs one write.

How this page is laid out

  1. Part 1 · Understand what you're building UNDERSTAND Where Claude Code looks for a CLAUDE.md and which of those places a sandbox has; why "write it once" is Ray's answer and cannot be ours; and what belongs in the file. ~15 min.
  2. Part 2 · Build it DO NOW Six steps: the decision, a request that was too big and had to be split, a review that found three things, a merge conflict, the merge itself, and a live check. 30–50 min.

Before you begin

A persona file is prompt, and prompt is a liability as well as a help. Whatever you write here is loaded into every run, including the ones where it is irrelevant, and a model will act on a stale fact in it more confidently than on no fact at all. The file in this lesson stays at nine short lines for that reason: who it is, what is on the machine, what is not running, and how long it has. Anything that changes more often than the image does belongs in code that derives it, not in a constant.
  • Lesson 12 finished and merged, so the image really does have the two database servers the persona file will claim it has.
  • A pull request you are willing to review properly. This one is small and still had three findings in it.
  • No new accounts or keys. If a step asks for one, something has gone wrong.
PART 1

Understand what you're building

Three things: where Claude Code looks for this file, why the moment you write it is a different question here than in the video, and what is worth putting in it.

Where Claude Code looks for a CLAUDE.mdThree scopes, and a sandbox that only has one of them.

UNDERSTAND

Claude Code loads context files by itself, before your prompt. Ray's video turns on discovering that not every place you can put one is a place it will be found from:

ScopeWhere the file sitsDoes this bot have it?
User~/.claude/CLAUDE.mdYes — the sandbox has a home directory, and nothing else claims it. This is where the lesson lands.
ProjectCLAUDE.md or AGENTS.md at the root of the directory you are working inNo. The sandbox starts empty. Nothing clones the agent's own repository into it, so its own AGENTS.md is simply not there.
NestedA CLAUDE.md deeper in a repository the bot clonesOnly when a repository is cloned, and only for the files being worked on.
How Ray found this. He added the persona line to the top of his repository's AGENTS.md (with CLAUDE.md symlinked to it), pushed, and asked the bot in Slack, verbatim: "is this loaded in your context window automatically?" It said no — nothing like that appeared in its context. He then took the screenshot to the claude-code-guide subagent with: "for some reason this claude.md file, AGENTS.md file is not being loaded in. Can you figure out why? Give me a few solutions here and I'll tell you which one to recommend." Of the options it returned he picked the third: write it to the user root. That is the same conclusion this page reaches, arrived at by asking rather than by reasoning about what the sandbox contains.
Ray also says the nested case is handled for you — that when the bot clones a repository, the CLAUDE.md files inside it are loaded automatically as it edits those files, so you need not think about them. That is stated in the video and untested here: this workshop has not run a task that clones a repository carrying its own CLAUDE.md and checked whether the model quoted it back. Treat it as a claim to verify the first time it matters.

Why Ray writes the file once and this bot writes it every runThe same requirement, a different machine lifetime, and therefore a different answer.

UNDERSTAND

Ray's sandbox belongs to a Slack thread. It is created with the thread, paused between turns, and resumed when someone replies — so there is a genuine "first turn of this box", and setup can hang on it. His code does exactly that: a lib/sandbox-memory.js holding the persona as a JavaScript string, written with sandbox.files.write only when isNew is true.

This bot has no such moment. The sandbox is created inside the request and destroyed when the run ends, and the Slack thread is replayed into the prompt each time instead of being resumed. There is no first turn to detect, because every turn is the first turn.

A hotel room, not a flat. Ray moves in and puts a note on the fridge; it is still there next week. This bot checks into a new room for every message and checks out before the reply is posted. The note has to go up with the luggage, every single time — and the cost of doing so is one write on a machine that is already being built from scratch anyway.

Where this page departs from Ray. The isNew gate is dropped, not reimplemented. Copying it here would give you a condition that is always true, which is worse than no condition: the next reader would spend time working out which branch runs. The gate is not a best practice, it is an optimisation for a machine that persists, and this one does not.

What belongs in the persona fileOne line of identity, and everything the model would otherwise have to find out by running commands.

UNDERSTAND

Ray's version is a single sentence of identity. This one keeps that as its first line and then spends the rest on the machine, because the machine is the thing the model cannot see until it has already wasted a turn looking:

What the file saysWhat it saves
Who it is, and that the answer lands in SlackEssays. "Be brief and concrete" is doing real work in a chat window.
Node 24, git, gh, Playwright with Chromium onlyA probe run, and an attempt to use Firefox or WebKit that fails halfway through a task.
Postgres 15 and Redis are installed but not running, with the exact start commandsThe failure lesson 12 chose to accept. On-demand services only work if whoever needs them knows they exist and how to start them.
The machine dies when the run endsWork left in /tmp and lost, and confident promises to "continue next time".
About four minutes per run; push partial workA run that spends its whole budget perfecting something nobody ever sees.
Every line in it answers a question the model would otherwise answer wrongly or expensively. That is the test for adding a line here — not "is this true", which is far too weak a bar for text injected into every single run.
The two start commands are exact for a reason. pg_ctl -o "-k /tmp -c listen_addresses=127.0.0.1" -w start and redis-server --daemonize yes --save "" --appendonly no --bind 127.0.0.1 are not decoration: they encode the socket directory and the loopback binding this image needs. A model improvising them gets a permissions error and concludes there is no database.
Why the file is a string constant in code, and not a file in the repository

A real toolkit/CLAUDE.md read from disk would be tidier to edit, and it is what lesson 14 does for skills. The persona stays a constant for one reason: it is the fallback. Every failure path in the module returns the persona entry alone, so the persona must be the one thing that cannot fail to be read — and a string in the bundle cannot go missing the way a file outside it can when a deployment's task root turns out not to be where you assumed.

THE DECISION THIS PAGE MAKESThe persona file is written to ~/.claude/CLAUDE.md on every run, from a constant in the function's code, in the same batched write that lesson 14's skills will use — and it can never fail the run.
PART 2

Build it

Six steps. The short lesson and the long pull request: the change is thirty lines, and the interesting part is everything that happened around it.

Step 1 of 6 — Decide when the file gets writtenThe only design question in the lesson, and it is settled by the sandbox's lifetime.

DO NOW

  1. Ask what persists. If your sandbox survives between turns, Ray's isNew gate is right and you should copy it. If it does not, the gate is dead code. For this bot the answer was settled in lesson 07: created per request, destroyed at the end, thread replayed into the prompt.

  2. Choose "every run", and say why in a comment. The reason is not obvious from the call site six months later, so it sits at the top of the module: there is no first turn to seed state on, so anything the sandbox should have must be written on every single one.

  3. Decide where in the run it goes. Before claude spawns — otherwise the file appears after the model has already read its context, which is a bug that looks exactly like the file not being written at all.

CHECKPOINTYou can state, in one sentence, why this bot does not gate the write on anything.

Step 2 of 6 — Ask the bot to build it, and split the work when it times outThe first request died at 255 seconds with nothing pushed. The fix is smaller requests, not a longer timeout.

DO NOW

Where: Slack → #joestar-dev → mention @joestar

  1. The request, made in #joestar-dev: write the persona file into every sandbox run, and — because lesson 14 is the same mechanism — build the skills loader that shares the write with it. One module, one call site, tests.

  2. It timed out at 255 seconds with nothing pushed. Not a crash and not a refusal: the run simply ended mid-work, and because nothing had been committed there was no partial result to look at. The four minutes are real, and a request that needs five gives you nothing at all.

    A timed-out run is silent. You get an answer that reads like a plan rather than a link to a pull request, and the natural reading is "it is still working". Nothing is still working — the machine is gone. Check for the pull request, not for the tone of the reply.

  3. Split it in two and ask again. Part A: the loader module plus the persona file, which became pull request #13. Part B: the first skill and the Vercel configuration that ships it, which became #14 and is lesson 14's story. Each fits inside one run with room to spare.

    This is the general fix, and it arrives here for the first time. The budget is a property of the deployment, not of the task, so the only variable you control is how much you ask for at once. "One module and its tests" is about the right size.
Not in the video. Ray does this change in local Claude Code with no time limit, so the splitting problem does not exist for him. It is a consequence of running the agent inside a serverless function, which is this workshop's choice, and it will come up again in every later lesson.
CHECKPOINTPull request #13 exists and touches api/_lib/sandbox-files.js, its call site in api/_lib/claude.js, and a test file — and nothing else.

Step 3 of 6 — Review the pull requestThree findings in thirty lines. Two of them would have shipped silently.

DO NOW

A review subagent read the diff and found three things, all fixed in one round:

FindingWhy it matters
The toolkit directory was looked up as process.cwd()/toolkit first, then <module>/../../toolkitWrong order. On Vercel process.cwd() is the repository root, not the bundle, so the first candidate can resolve to a directory that is not the deployed one. The module-relative path is the correct first guess; cwd stays as the fallback.
The "never throws" guarantee had no testRemoving the try/catch left the suite at 75 of 75 green. A promise nothing checks is a comment, and comments do not survive refactors.
A Buffer was passed where e2b's WriteEntry.data is typed string | ArrayBuffer | Blob | ReadableStreamIt happens to work today by accident of the SDK's internals. Wrapping it in a Blob at the call site makes it work on purpose.
The second finding is the one to learn from. The module's own doc comment promised that a missing toolkit, a malformed skill or an oversized payload would all degrade to "fewer files written, never a failed run". That promise was the whole safety argument for writing files on every run — and it was unverified. The mutation that deleted the guard was invisible to the tests.
CHECKPOINTAll three findings fixed in one commit, and the suite is green — 83 tests after the change.

Step 4 of 6 — Resolve the conflict by merging main in, not rebasingA branch that was squash-merged underneath you cannot be rebased past a guard that blocks force-push.

DO NOW

  1. What happened. Pull request #12 was squash-merged while #13 was open, so #13's base changed shape underneath it and the branch stopped merging cleanly.

  2. Why not rebase. A rebase rewrites the branch's commits, and publishing a rewritten branch needs a force-push. The git guard installed in lesson 08 blocks force-pushes from the sandbox on purpose — so for this bot the usual tidy answer is simply not available.

  3. Merge main into the branch instead. An extra merge commit, a slightly less tidy history, and a resolution that only adds commits. The pull request is squash-merged at the end anyway, so the untidiness never reaches main.

    The guard chose the strategy, and that is the point of a guard. It is not a suggestion the agent weighs against convenience — it removes an option, and the remaining one turns out to be fine.
CHECKPOINTThe pull request shows no conflicts and its history contains a merge of main, not a rewrite.

Step 5 of 6 — Merge it yourselfMerging is still a human action, for the same reason pushing is.

DO NOW

Where: your own terminal, in the repository root

  1. Merge from your own machine: gh pr merge 13 --squash --admin. Squash, so main gets the change as one commit with the merge commit from step 4 folded away.

  2. Remember that this deploys. A push to main runs the tests and then deploys to production, so the merge is the moment the change goes live. There is no separate release.

CHECKPOINTmain contains api/_lib/sandbox-files.js, the test suite is green at 83 tests, and the deploy has finished.

Step 6 of 6 — Check it live by asking the bot to quote the fileRay's test, and the only one available: ask for something only the file contains.

DO NOW

Where: Slack → #joestar-test

  1. In #joestar-test, ask for the first line of ~/.claude/CLAUDE.md. It came back exact: "You are Joestar, Noj's Slack agent. You answer in Slack, so be brief and concrete."

  2. Know what that proves and what it does not. It proves the file is on the machine with the right contents at the right path — the model can read a file it is told about. It is only indirect evidence that Claude Code loaded it into context automatically at user scope in headless -p mode, because a model asked for a file's first line can simply open the file.

    The stronger check, if you want it. Ask something the file answers but that you never mention — "what is running on this machine right now?" — in a run that has no reason to read files at all. A model that names the two idle servers and their start commands has loaded the persona; one that shells out to ps first has not.
CHECKPOINTThe bot quotes the first line of the persona file exactly, in a channel where nothing else could have told it.
PART 3

Keep for later

The code as merged, the file it writes, what breaks, and what on this page was actually checked.

What the code does, in the order it does itOne module that builds a list, one call site that writes it and swallows everything.

REFERENCE

api/_lib/sandbox-files.js exports sandboxFiles({ toolkitDir }), which returns an array of { path, data } entries. The persona entry is always first and is built from a constant; everything after it is lesson 14's skills, walked off disk. Four things are worth noticing:

  • It returns, it does not write. Building the payload is pure and testable; the network call lives at the call site. That split is why the guarantee below can be tested at all.
  • Every failure returns the persona alone. No toolkitDir, an unreadable skills directory, a skill with no SKILL.md, a payload over the 2 MiB cap — each one degrades to fewer files, and the persona always survives.
  • Dotfiles are skipped when walking skill directories, so an editor's stray state never rides along into the sandbox.
  • The call site wraps the whole thing in try/catch in api/_lib/claude.js, converts any Buffer to a Blob, and writes the batch in one sandbox.files.write before claude starts. A broken toolkit costs you a persona for that run, never the reply.
Five mutations were run against the tests by the reviewer: drop the SKILL.md check, drop the 2 MiB cap, move the write to after claude starts, let a rejection propagate instead of being caught, and include dotfiles. Four were caught. The fifth — the propagating rejection — was caught only after the missing test from step 3 was added. That is what a mutation check is for: it tells you which guarantees your suite is actually holding.
