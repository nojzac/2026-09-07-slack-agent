SLACK AGENTS · CHAPTER "USING YOUR AGENT" · LESSON 21

Give the bot a channel to ask for what it lacks

Ray's last idea is his smallest and his best-value: a channel called agents-feedback, one line in the system prompt telling the agent to post there whenever something would have helped it finish a job, and a habit of reading it. The agent stops failing silently and starts telling you which tool to build next. For this bot there is one wrinkle — the sandbox has no way to talk to Slack.

Ray's video: 1 min 48 s This page: 20 min At the end: a decision on the cheapest capability in the chapter, and the two mechanisms that could carry it

What you'll have at the end

The loop is three boxes. The two bands under it are what this bot adds to Ray's version.

  • The pattern: the agent reports missing capabilities as it hits them, instead of quietly doing a worse job.
  • Two mechanisms that fit this bot, since its sandbox cannot post to Slack itself.
  • A rule for reading the channel: requests are proposals, and a granted one is granted to every workspace member.
  • The chapter's cheapest change, and the one to do first if you do any of them.

Who this is for, and what it assumes

You have a persona file the bot reads on every run (lesson 13) and a bot that already posts into Slack through the Vercel function. If you read lesson 19 or lesson 20 and deferred them, this one still applies — in fact it applies more, because a bot that reports its own gaps is how you find out whether the other two are worth building.

Why this lesson exists

Ray: "sometimes they will be doing a pretty ambitious job, and they may not have the required connections, MCP servers, or just the ability to do what they want to to completion."

The gap this closes. An agent without a tool does not stop — it improvises, and the improvisation reads like an answer. The failure is invisible unless the agent is told to make it visible, and the cost of telling it is one paragraph.

Before you begin

Do not wire "grant the ability" as an action the bot can take. Ray replies "cool, add that ability for yourself" and the agent edits its own harness. Here every capability lands as a reviewed pull request, because a bot that can widen its own permissions widens them for everyone who can message it. The feedback channel is an inbox, not a switch.

PART 1

Understand what you're building

The loop itself, the mechanism it needs here, and the review rule that keeps it safe.

The loop: the agent reports its own missing toolsOne line in the persona, one channel, and a backlog that writes itself.

UNDERSTAND

The instruction lives in the system prompt: post to this channel whenever something would have helped you finish, and say why. Ray's examples are specific enough to act on — "give Percy a Google Tag Manager connection or an equivalent way to edit the container", "give Percy a read-only way to download a Slack file from its file id when the channel history exposes it".

A suggestion box that only the person doing the work can post to. Its value is not the ideas; it is that the ideas arrive attached to the moment the tool was actually missing, which is the one moment you can judge whether it was needed.
This is the chapter's best ratio by a distance. Lesson 19 costs two loop guards; lesson 20 costs a scheduler and a durable mandate. This costs a paragraph of persona text — and it produces the evidence you need to decide about the other two.
Ray's declined-requests trick: an ✗ reaction on a post means "don't ask for that again". Cheap and effective — but it only works if something remembers the ✗ between runs. Here that means the memory repo; a reaction on a message in a channel the bot does not re-read is a note to nobody.

The mechanism problem: the sandbox cannot talk to SlackVerified in the code — no Slack credential is passed into the machine, on purpose.

UNDERSTAND

The environment handed to the claude command in joestar-agent/api/_lib/claude.js contains a GitHub token when there is a repo for the channel, an Exa key, and an ElevenLabs key. There is no Slack token, and there should not be: only the Vercel function posts to Slack, which is what keeps "the bot said it" and "the model wrote it" the same statement.

const envs = {
  ...(githubToken ? { GH_TOKEN: githubToken, HOME: SANDBOX_HOME, HISTFILE: '/dev/null' } : {}),
  ...(hasExaKey ? { EXA_API_KEY: process.env.EXA_API_KEY } : {}),
  ...(process.env.ELEVENLABS_API_KEY ? { ELEVENLABS_API_KEY: process.env.ELEVENLABS_API_KEY } : {}),
};

Two carriers that do not require a Slack credential in the sandbox

CarrierHow it worksTrade
The function forwards itThe persona asks the model to end a run with a marked line — a NEEDS: block. The function strips it from the reply and posts it into the feedback channelA small, testable change in code you already own. Needs the bot invited to the channel; no new scope, since it already has chat:write
The memory repo carries itThe run appends the request to a file in nojzac/joestar-memory, which is cloned in and pushed after every runNo code at all — but it lands in a repository you have to remember to read, rather than in a channel that interrupts you
Third option, and the honest default: just say it in the thread. The bot can already end a reply with "I could have done better with X". It is less tidy than a dedicated channel and it costs nothing whatsoever — a good first week before deciding the pattern is worth wiring.

A request is a proposal, and the reviewer is youThe one way this pattern can bite, and the rule that prevents it.

UNDERSTAND

The agent asking for a capability is the agent asking to widen its own reach — and what it read during the run can motivate the request. A web page, a repository file, an alert payload: all of it is data the model consumed, any of it can suggest that a particular access would be useful, and the request arrives in your channel wearing the bot's voice.

So the rule is unchanged and unconditional. A requested capability is assessed exactly like any other: does handing its full power to every workspace member remain acceptable? A request never shortens that review, and the fact that the bot asked is not evidence — it is the thing being reviewed.
What the channel is genuinely good for. Frequency. One request is an anecdote; the same request five times is a specification, with five worked examples of why it was needed. That is the signal worth reading the channel for.
WHAT PART 1 SETTLEDA paragraph of persona text plus a carrier — the function, the memory repo, or just the thread. Requests are proposals and the capability rule does not bend for them.
PART 2

Decide

No code was written for this lesson in this workshop. These four steps are what building it looks like.

Open the channel, write the line, choose the carrierThe cheapest capability in the chapter, in about twenty minutes.

DO NOW

  1. Create the channel and invite the bot. Public, so anyone can see what the agent is asking for — the same reasoning as keeping mandates public in lesson 20. No new Slack scope is needed; posting is the chat:write it already has.

  2. Write the persona line so it names the moment, not the topic. "Whenever a missing capability, connection or credential stopped you finishing a job, or made you do it worse, say so — name the capability, the run it came from, and what you would have done with it." A vague instruction produces vague requests, which are the ones that get ignored.

  3. Pick a carrier and start with the cheapest one. The thread itself for a week; then, if the requests are worth collecting, the function forwarding a marked block into the channel. Wire the elaborate version after you have seen a few real requests, not before.

    Where this departs from Ray. Ray's agent posts to the channel directly, because his harness gives it Slack access. This one deliberately does not, so the request travels out through the function or the memory repo instead. Same loop, one less credential in a disposable machine.

  4. Decide what a "no" looks like, and where it is remembered. Ray uses a reaction. Here, a declined request belongs in the memory repo or the persona as a line — "do not ask for X again, decided on this date, because…" — since nothing else survives the sandbox being destroyed.

CHECKPOINTThe bot has raised at least one unprompted request for a capability, in a place you will see it, and you have either granted it through a reviewed pull request or recorded the refusal somewhere the next run reads.
