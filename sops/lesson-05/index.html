SLACK AGENTS · CHAPTER "0 TO 1" · LESSON 05

Give the bot a brain: Claude Code in a cloud sandbox

Lesson 04 built the pipe. This lesson changes what flows through it: your mention becomes a prompt, Claude Code answers it on a computer in the cloud, and the reply appears in the thread.

Ray's video: 8 min 30 s This page: 45–60 min At the end: a bot that can think

What you'll have at the end

  • Mention the bot with a question and Claude Code answers it, in the thread.
  • A cloud sandbox that boots per question, runs Claude, and is destroyed afterwards.
  • Two more credentials in 1Password: an E2B key and a Claude Code token.
  • An honest "thinking…" while it works, rather than silence.

Who this is for, and what it assumes

You finished lesson 04, so a mention already reaches your deployed code and gets a reply.

It assumes a Claude subscription (Pro, Max, Team or Enterprise) — the token in step 2 requires one. It does not assume you have used E2B, or know what a sandbox is; both are explained below.

Why this lesson exists

A bot that picks numbers needs nothing but a function. A bot that does work needs a computer: somewhere to check out a repo, run commands, install things and make a mess — for minutes at a time, without any of it touching your machine or anyone else's.

That is all a cloud sandbox is. This lesson rents one per question and throws it away afterwards.

It's a hotel room, not a house. You get a room for the night, you can leave towels on the floor, and housekeeping erases you completely at checkout. Nothing you do there can reach your home.

PART 1

Understand what changes

Three short sections. The wiring from lesson 04 is untouched — only what happens in the middle is different.

Why Claude needs a computer, not just a functionWhat a cloud sandbox is, and why the answer isn't "run it on Vercel".

UNDERSTAND

Your Vercel function is a good postbox and a poor workshop. It starts when a request arrives, runs briefly, and is thrown away. It has no persistent disk, no git, no place to install things.

Claude Code needs the opposite: a whole machine it can work in for minutes — read files, run commands, install packages, break things. So the function stops being the worker and becomes the dispatcher. It rents a machine, hands over the question, waits, and reports back.

The function is a receptionist; the sandbox is the workshop out the back. Reception is never where the work happens — it's where the work is taken in and handed out.
Why a sandbox rather than a server you keep running

A long-lived server would mean one machine accumulating everybody's mess, patched by you, running and billing between questions. It would also mean one Claude's changes could affect the next Claude's work.

A fresh sandbox per question is cleaner in every way: no shared state, no cleanup, nothing running when nobody is asking. And it is what makes the next point safe.

Why it's acceptable to let Claude run with all permissions

Inside the sandbox, Claude runs with --dangerously-skip-permissions — no approval prompts, it just acts. That flag would be reckless on your laptop.

It is reasonable here because of what the machine is: empty, isolated, freshly created, holding nothing of yours, with no path back to your systems, and destroyed when the answer is sent. The worst it can do is wreck a computer that was going to be deleted in ninety seconds anyway.

This is worth holding on to as a principle, because it comes back in later lessons: you get to skip the safety prompts precisely to the extent that the blast radius is already contained. Widen what the sandbox can reach — your GitHub, your database — and that trade changes.
Why E2B, when there are several of these

Vercel, Cloudflare, Daytona and others all sell sandboxes; this is a busy market because every agent needs one. Ray picks E2B for its network policy controls and because new accounts get free credit, which is enough reason for a course.

Nothing here is deeply E2B-specific. It is "make a machine, run a command, read the output, kill the machine" — about fifteen lines in api/_lib/claude.js, which is where you would swap providers.

How a message flows nowThe reply arrives in two stages, and the reason is the three-second rule from lesson 04.

UNDERSTAND

Lesson 04 could answer inside Slack's three-second window because picking a number takes no time. Claude takes minutes. If the function simply waited, Slack would give up, decide the delivery failed, and send the same mention again — and again — each one starting another sandbox.

So the reply is split in two. The function posts thinking…, tells Slack "got it", and only then starts the real work. When Claude answers, it edits that same message rather than posting a new one.

What keeps the function alive after it has answered

Normally a serverless function is shut down the moment it responds — which would kill Claude mid-thought. Vercel provides waitUntil() for exactly this: it says "I have answered, but keep me running until this finishes".

There is still a ceiling. The function asks for maxDuration = 300, five minutes. A question that takes longer than that gets cut off, and the fix is to move the work off the function entirely — a bigger change, and not this lesson's.

Why "thinking…" matters more than it looks

It is the difference between a bot that is working and a bot that is broken — which, from the outside, look identical. Two minutes of silence in a Slack channel reads as failure, and the natural response is to mention it again, starting a second sandbox.

The same reasoning is why a failure replaces the placeholder with the error text. A "thinking…" that never resolves is the worst of both worlds.

The two new credentials, and what each one pays forOne rents the machine; one buys the thinking.

UNDERSTAND
CredentialWhat it authorisesWho bills you
E2B_API_KEYCreating and running sandboxesE2B, per second of machine time. New accounts start with about $100 of credit.
CLAUDE_CODE_OAUTH_TOKENClaude Code answering as youYour Claude subscription, not per-token API pricing.

They sit alongside the two from lesson 04, so the deployment ends up with four environment variables. Same rule as before: 1Password holds the master copies, Vercel holds the runtime ones.

Subscription token or API key — and the trap if you set both

claude setup-token produces a long-lived token tied to your Claude subscription. An ANTHROPIC_API_KEY is the other route, billed per token at API prices.

If both are present, the API key wins. Claude Code checks ANTHROPIC_API_KEY before the OAuth token, so setting both means you are quietly paying API prices while believing you are on your subscription. The sandbox is given the OAuth token and nothing else, deliberately.
Also avoid --bare if you use the subscription token. The CLI's own help says bare mode makes authentication "strictly ANTHROPIC_API_KEY or apiKeyHelper — OAuth and keychain are never read", so it would break this setup with an error that looks nothing like its cause.
The token cannot be revoked from a dashboard

It is valid for a year, and there is no interface for deleting it. Anyone holding it can spend your Claude subscription. That is why it goes straight into 1Password and into Vercel as a hidden secret, and never into a file, a commit, or a chat message.

PART 2

Build it

Six steps. Steps 1 and 2 are accounts and tokens — only you can do those, and everything else waits on them.

Step 1 of 6 — Create an E2B account and an API keyThe service that rents you a machine per question. Free credit covers this course comfortably.

DO NOW

This step is optional. The two credentials have to reach Vercel, because that is where the deployed bot reads them from. Putting them in 1Password first is a convenience, not a requirement — you can paste them straight into Vercel's dashboard and skip this step entirely.

The one thing that genuinely wants a local copy is the sandbox image build in step 4, which needs E2B_API_KEY on your own machine. Without 1Password that is E2B_API_KEY=… node e2b/build.mjs, once.

See the fuller note in lesson 04, step 3, for what 1Password does and does not buy you here.

Never turn on "Integrate with 1Password CLI". It lives in the desktop app under Settings → Developer, it looks like the obvious way to make op work in your terminal, and it is the most dangerous setting involved in any of this.

It signs in every shell on the machine as you, with your entire account — your interactive terminal and the non-interactive shells your AI agent runs in, equally. It ignores service-account scoping completely, because it is a different way of authenticating altogether: having a carefully scoped service account changes nothing while the integration is on, since the wide door is still there and op reaches for it first.

On 15 September 2026, on this project, it gave the coding agent read access to five vaults — including a client's — on a machine where exactly one vault was intended. The agent then read part of a non-revocable token into its own transcript while "just checking" that the credential existed.

There is no way to grant it to your terminal but not to an agent's. It is one switch for both. Leave it off and authenticate with a service account token instead, which is what the steps below create.

How to check where you stand: run op vault list. It should return only the vaults you granted that service account — for this project, one. If vaults you never granted appear, the integration is on.

Two more things that will catch you out.

  • A service account token is shown once. At creation it appears a single time and can never be displayed again. Get it where it needs to go before you close the tab. If you lose it, delete the service account and make another — do not leave one with vault access that nobody holds the key to.
  • A helper script that fetches the token gives your agent the vault. bin/with-secrets reads the token from your Keychain without prompting, so any agent that can run that script has that vault's access. That is deliberate, and bounded to one vault, read-only. But "the agent has no access" is not a true statement while the script exists — check by running it, not by assuming.

  1. Sign up.

    Where: e2b.dev

    Click Sign up (top right). Signing in with GitHub or Google is fastest — there is no separate password to store, and you already have both.

  2. Land on the dashboard and check your credit.

    After signing in you get a dashboard showing running sandboxes and usage — all zeros for now. In the left menu, open Billing. A new account carries roughly $100 in free credits, which is far more than this course uses.

    What you are actually being billed for

    Machine time, by the second, while a sandbox exists. A question that takes Claude ninety seconds costs ninety seconds of a small VM — fractions of a penny.

    The thing that costs real money is a sandbox nobody killed, quietly running for hours. That is why the code kills it in a finally block, so it dies even when Claude throws.

  3. Create the API key.

    Where: E2B dashboard → API Keys in the left menu

    Click Create API Key, name it something you will recognise later — joestar — and create it. Copy the value now; treat it like a password.

    Leave the tab open. Step 3 puts this straight into 1Password, and it is easier to copy it once than to go looking for it again. If you do lose it, delete the key and make another — they are free and revocable, unlike the token in step 2.

  4. Note your team, if you are asked to pick one.

    E2B can put you in a personal team or an organisation. Either works, but the API key belongs to one of them — if sandboxes later fail with a permissions error, a key from the wrong team is the first thing to check.

CHECKPOINTYou have an E2B API key on your clipboard, and a dashboard showing free credit.

Step 2 of 6 — Create a Claude Code tokenOne command. It bills the bot's thinking to your Claude subscription.

DO NOW

  1. Run the setup command in a terminal.

    Where: any terminal, on your own machine

    claude setup-token

    It opens a browser to confirm who you are, then prints a long token. This requires a Claude subscription — Pro, Max, Team or Enterprise. On a free account the command refuses, and your route is an ANTHROPIC_API_KEY instead.

  2. Treat the token as unrevocable.

    There is no button to delete this token. It is valid for a year, and anyone holding it can spend your Claude subscription. Do not paste it into a chat, a file, a commit, or a screenshot. It goes from your terminal into 1Password in step 3, and nowhere else.
CHECKPOINTA token starting sk-ant-oat… is on your screen, ready to be stored.

Step 4 of 6 — Build the sandbox imageDefine the machine once: Node, Claude Code, and the tools Claude reaches for.

DO NOW

  1. Read the template before building it. It is five lines, at e2b/template.mjs:

    Template()
  .fromNodeImage('24')
  .aptInstall(['curl', 'git', 'ripgrep'])
  .npmInstall('@anthropic-ai/claude-code@latest', { g: true })

    Node because Claude Code is a Node program. git because that is what it will mostly be asked to touch. ripgrep because Claude's search shells out to rg and is slow and clumsy without it. curl because half of all install instructions start with it.

    Why the image is built once rather than installed per question

    Installing Claude Code takes a minute or so. Doing that on every mention would add a minute to every answer and burn credit doing the same work repeatedly.

    Building it into the image means a sandbox boots in a second or two with everything already present. The cost is that the image is a snapshot: @latest was resolved the day you built it, and it does not drift until you rebuild.

  2. Build it, with the key injected from 1Password.

    bin/with-secrets node e2b/build.mjs

    This uploads the definition to E2B and builds the image there. It takes a few minutes the first time. It prints a template ID when it finishes — that is what the code asks for by name.

    A stale template is the trap here. Ray hits it in the video: the bot fails, the error is unhelpful, and the cause is an image that no longer matches what the code expects. If sandboxes behave strangely later, rebuild this before debugging anything else.
CHECKPOINTE2B reports a built template, and its name matches the one the code asks for.

Step 5 of 6 — Give Vercel the two new keys and deploySame pipe-don't-type rule as lesson 04. Four environment variables when you are done.

DO NOW

  1. Pipe both into Vercel, production only.

    op read "op://SlackAgentOS/2026-09-07-slack-agent/e2b_api_key" \
  | npx vercel@latest env add E2B_API_KEY production

op read "op://SlackAgentOS/2026-09-07-slack-agent/claude_code_oauth_token" \
  | npx vercel@latest env add CLAUDE_CODE_OAUTH_TOKEN production

    Neither value passes through your clipboard or a browser form.

  2. Confirm there are now four.

    npx vercel@latest env ls production

    Expect SLACK_SIGNING_SECRET, SLACK_BOT_TOKEN, E2B_API_KEY and CLAUDE_CODE_OAUTH_TOKEN, all hidden.

  3. Push, and let the tests gate the deploy.

    git push

    The workflow from lesson 04 runs the tests and only then deploys. Watch it with gh run watch if you want to see it happen.

CHECKPOINTFour production variables, a green CI run, and a new deployment live.

Step 6 of 6 — Ask it somethingThe whole point. Expect two stages, and expect it to be slower than lesson 04.

DO NOW

  1. Mention the bot with a real question.

    @joestar who are you?

    Within a second or two you should see thinking… in a thread. Some seconds later that same message is replaced by Claude's answer. Watching it change is the proof that both stages work.

  2. If it stays on "thinking…", the sandbox or Claude failed in a way the code could not report. Pull the logs:

    npx vercel@latest logs <your-domain>

    Look for [claude] failed: — the message after it is the real cause. Part 3 lists the ones worth recognising.

That is the lesson. Everything after this is giving Claude more to work with — your repo, tools, memory — rather than changing this shape.

PART 3

Keep for later

Reference. Come back when the bot goes quiet, or when you want to change what it can do.

What the code doesTwo small files. The dispatcher, and the fifteen lines that rent a machine.

REFERENCE
api/_lib/claude.js — rent, run, read, kill

Creates a sandbox from the template, handing it only the Claude token and three settings. Runs one command. Reads the answer out of the JSON. Kills the sandbox in a finally, so it dies even when something throws.

The command is worth reading closely:

claude -p '<your question>' --dangerously-skip-permissions --output-format json
  • -p — non-interactive. No terminal, no trust dialog, no onboarding to hang on.
  • --dangerously-skip-permissions — no approval prompts. Safe only because the machine is empty and about to be destroyed.
  • --output-format json — a structured envelope; the answer is the result field.
Why the prompt is shell-quoted, and how that is tested

The question is pasted into a shell command, so a message containing backticks, $(…) or a stray quote could otherwise run as commands inside the sandbox. Every prompt is wrapped in single quotes with embedded quotes escaped.

The test does not eyeball the escaping — it round-trips hostile strings ('; rm -rf /, $(whoami), backticks) through a real shell and asserts that what comes out is byte-for-byte what went in.

The three environment settings passed into the sandbox
SettingWhy
CLAUDE_CODE_OAUTH_TOKENAuthenticates as you, billed to your subscription. Nothing else is passed in — particularly not an API key, which would silently take precedence.
DISABLE_TELEMETRY, DISABLE_ERROR_REPORTINGNothing useful to report from a machine that exists for ninety seconds.
CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MSClaude waits up to ten minutes for background tasks before exiting. The whole function budget is five, so this caps the wait at five seconds.
api/slack/events.js — what changed from lesson 04

Everything before the reply is identical: signature check, challenge, retry guard, self-mention guard. What changed is the reply itself — placeholder, acknowledge, work, edit — plus a check that names any missing variable in Slack rather than failing silently.

When it doesn't answerSymptoms and their causes, including the two that cost Ray the most time.

REFERENCE
What you seeWhat it usually is
A message naming a variableExactly what it says — that variable is not set on the deployment. Re-run step 5.
Stuck on thinking… foreverThe sandbox or Claude threw after the placeholder went up. vercel logs, look for [claude] failed:.
thinking… replaced by an auth errorThe token is wrong, expired, or an ANTHROPIC_API_KEY is also set and taking precedence.
Sandbox creation fails outrightWrong E2B key, a key from a different team, or no credit left.
Odd failures that make no senseA stale template. Rebuild it (step 4) before debugging anything else — this is the one that cost Ray the video's last five minutes.
Answer truncated, or nothing after five minutesThe function's ceiling. The work needs to move off the function, which is a larger change.
The same question answered twiceSlack retried and the retry guard did not catch it. Check the x-slack-retry-num branch still returns early.
The cheapest first move is still the ladder from lesson 04. Run bin/smoke. If all five probes pass, the Slack wiring is fine and the fault is in the sandbox or Claude — which halves the search immediately.
