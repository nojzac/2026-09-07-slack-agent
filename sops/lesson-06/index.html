SLACK AGENTS · CHAPTER "0 TO 1" · LESSON 06

Close the loop: let Claude Code test the bot itself

Until now every test of the real bot has been you, in Slack, typing a mention and reading the reply. This lesson hands that job to Claude Code: it posts the message, waits, reads what came back, and tells you whether the bot works.

Ray's video: 3 min 45 s This page: 20–30 min At the end: a bot that tests itself

What you'll have at the end

  • A channel, #joestar-test, reserved for the Claude Code on your own machine.
  • The Slack connector attached to Claude, so Claude can post as you and read replies.
  • One sentence — "verify the bot end to end" — that runs the whole test.
  • That instruction written into CLAUDE.md, so it survives the session you wrote it in.

Who this is for, and what it assumes

You finished lesson 05, so mentioning the bot gets a real answer from Claude Code in a sandbox.

It assumes a Claude account you can add connectors to on claude.ai, and that you are an admin of the Slack workspace — installing a connector needs someone who can approve an app. It does not assume you know what a connector or an MCP server is; both are explained below.

Why this lesson exists

Every feature from here on is the same shape: change the code, deploy, and find out whether the bot still answers. Doing that by hand costs a context switch to Slack, a typed mention, a wait, and your attention — each time, for eleven more lessons.

Giving Claude the ability to run that check itself means it can change something and immediately discover whether it worked, without you in the middle. That is what "closing the loop" means: the thing making the change can also see the result.

A cook who can taste. Until now Claude has been cooking blindfolded and handing you the spoon. This lesson gives it its own spoon. It doesn't make the cooking better by itself — it makes every mistake cheap to find, which over eleven lessons is the same thing.

How this page is laid out

Same shape as lessons 04 and 05. The build is short — five steps, most of them clicks in a browser.

Before you begin

You need

  • Lesson 05 finished — mentioning the bot gets a real answer today, not a placeholder.
  • A Claude account with connectors — claude.ai → Settings → Connectors.
  • Admin rights in the Slack workspace — installing the Claude app needs approval.
The Slack connector is one workspace at a time. If your Claude account already has Slack connected to a different workspace, connecting this one replaces that. Ray hits exactly this in the video and removes his existing connection to carry on. If you need both, the only way is a second Claude account. Check what you would be disconnecting before you start.
What you are handing over. The connector asks to "perform actions as you" — it can post messages in your name in any channel you can reach, and read conversations there. That is not bot access, bounded to one channel; it is your access. Grant it knowing that, and keep the testing confined to a channel that exists for testing.
PART 1

Understand what changes

Three short sections. No code changes in this lesson at all — everything here is about who can see what.

What the tests you already have do not coverThree kinds of test, and the gap at the top that only a human has been able to fill.

UNDERSTAND

There are already two ways to test this project, and both stop short of the thing you actually care about.

npm test proves the logic is right. bin/smoke proves the deployment is alive and the signing secret matches. Neither proves that Slack will send the event: event subscriptions can be off, the scope can be missing, the bot can be out of the channel, the saved URL can point at an old deployment. Every one of those passes both tests and produces a bot that says nothing.

Why the smoke test cannot be fixed to cover this

bin/smoke builds a payload itself and signs it with the signing secret, then posts it straight to the Vercel URL. It is deliberately impersonating Slack. That is what makes it fast and free of side effects — and it is exactly why it can never tell you whether the real Slack would have sent that payload. The only way to test delivery is to make Slack do the delivering.

Where this differs from Ray. Ray has no smoke script and no unit tests at this point, so for him this lesson is the first automated test of any kind. Here it is the third and outermost, and the other two stay: they are seconds to run and do not post anything in Slack.

What a connector is, and how it reaches Claude CodeYou attach it on the website; it shows up in the terminal. That surprises people.

UNDERSTAND

A connector is a set of tools Claude can call on some other service — read a Google Doc, search the web, post to Slack. Under the hood it is an MCP server: a standard way of describing "here are the actions available, here is what each one needs".

The part that catches people out: you attach the Slack connector to your Claude account on claude.ai, and it then appears in Claude Code in your terminal, because both are signed in as you. You do not install anything locally and there is nothing to configure in this repo.

A keyring, not a key cut per door. The connector goes on your account's keyring. Every place you are signed in — the website, the terminal — reaches for the same ring, so adding a key in one place makes it available in the other.

Two consequences worth knowing before you get to step 3:

  • A running Claude Code session will not see it. Connectors are read at launch. You have to quit and relaunch — this is step 3, and it is the most commonly missed one.
  • It is account-wide, not project-wide. Any Claude Code session you start, in any repo, can now post to that Slack workspace as you. Nothing scopes it to this project.

Who Slack thinks is posting, and why it has to be youThe bot cannot summon itself. The test message has to come from a person.

UNDERSTAND

The handler in api/slack/events.js answers app_mention events, and deliberately ignores any that carry a bot_id:

if (event?.type === 'app_mention' && !event.bot_id) {

That guard exists so the bot cannot answer itself into an infinite loop. It also means a test message posted by the bot's own token would be ignored — so the test has to be posted by a human account. That is precisely what the connector gives Claude: the ability to post as you.

In Slack, those messages carry a small sent using Claude label. They are your messages, posted by an app acting for you — not messages from the bot.

This is why the connector wants such broad permission. Posting as you is not a privilege Slack scopes down to one channel. It is the same access you have. Keeping the testing in a dedicated channel is a convention you hold to, not a boundary Slack enforces.
PART 2

Build it

Five steps. Steps 1 to 3 are setup you do once; steps 4 and 5 are the loop you will run for the rest of the course.

Step 1 of 5 — Create the test channel and invite the botA room Claude can make a mess in, so the noise stays out of the channels people read.

DO NOW

  1. Create the channel.

    Where: Slack → channel list → + → Create a channel

    Name it joestar-test. Public is fine and slightly better — a private channel needs the bot explicitly added and uses a different Slack scope if you ever read it programmatically. Click Next, then Create.

  2. Invite the bot into it.

    In the new channel, type /invite and pick @joestar, then press enter.

    Do not skip this. Ray's first test fails for exactly this reason: the message posts, but the bot is not in the channel, so nothing happens. A bot only receives mentions in channels it is a member of.

  3. Decide what this channel is for, and keep to it.

    This channel belongs to the Claude Code running on your own machine. Everything it posts while testing goes here, so #general stays readable and you can tell a real conversation from a robot talking to itself.

    Where this differs from Ray. This workspace already has #bot-smoke, which bin/smoke posts into. Keep them separate: #bot-smoke is for the scripted probes, #joestar-test is for Claude's conversational tests. Two channels, two audiences, neither cluttering the other.
CHECKPOINTA channel called #joestar-test exists, and joestar appears in its member list.

Step 2 of 5 — Connect Slack to your Claude accountBrowser work. This is the step that grants Claude the ability to post as you.

DO NOW

  1. Open your connectors.

    Where: claude.ai → your name → Settings → Connectors

    Ray reaches the same place through Customize → Connectors; the menu has moved around over time. If the wording differs, look for the page listing Google Drive, Gmail and similar.

  2. Check whether Slack is already connected somewhere else.

    If Slack appears as connected to a different workspace, you have to remove it first — one Slack workspace per Claude account. Be sure you know what that disconnects before you do it.

    This is a real cost, not a formality. If you use the Slack connector with a work workspace day to day, connecting this one takes that away. Ray accepts the trade in the video and mentions the alternative: a separate Claude account for the agent work.

  3. Add the Slack connector.

    Click Add → Browse connectors → choose Slack → Connect. Slack's own authorisation page opens.

  4. Pick the right workspace, then approve.

    Top right of the Slack page, confirm it says SlackAgentOS — not another workspace you happen to be signed into. Read what it asks for: it will say Claude may perform actions as you, including sending messages on your behalf. Click Allow.

    Last chance to think about it. After this click, anything signed into your Claude account can post in your name in that workspace. That is the feature. It is also the whole risk, and it is not limited to #joestar-test.
CHECKPOINTclaude.ai → Settings → Connectors lists Slack as connected, showing the SlackAgentOS workspace.

Step 3 of 5 — Confirm Claude Code can see SlackCheck before you restart anything. On this machine it arrived without a relaunch.

DO NOW

  1. Ask the running session first.

    Run:

    /mcp

    The list should include an entry for the Claude.ai Slack connector. Do this before restarting anything — you may already be finished.

    What happened here. On 15 September 2026 the Slack tools appeared in a session that had been running since before the connector was attached, with no relaunch and nothing typed. So "you must restart" is not a rule you can rely on in either direction: check, and let the answer decide.
    Where this differs from Ray. Ray quits and relaunches Claude Code before running /mcp, and describes that as necessary. It was not necessary on this machine. Relaunching is harmless, so it remains the fix if the check comes back empty — just not the first thing to do.

  2. If it is not there, relaunch and check again.

    Exit the session, start it again in the project folder, and run /mcp once more. If it is still missing, the connector did not attach in step 2 — go back to claude.ai and confirm Slack is listed as connected, to the workspace you meant.

    What /mcp is showing you

    It lists the MCP servers this session can call, connectors included, and their connection status. It is the fastest way to tell "Claude cannot do this" apart from "Claude can do this and it failed" — the first shows up as a missing entry, the second as an error when the tool runs.

CHECKPOINT/mcp lists the Slack connector as connected.

Step 4 of 5 — Run the first end-to-end testAsk Claude to post, wait, and read the reply. Watch it happen in Slack as it goes.

DO NOW

  1. Ask for the test, spelling out the three parts.

    Paste this into Claude Code:

    Post a message in the #joestar-test channel on Slack that tags @joestar and
asks it what 2 + 2 is. Wait about 60 seconds, then read the thread and tell me
whether joestar replied and what it said.
    Where this differs from Ray. Ray's first attempt is just "send a message to the joestar-test channel and see if Joestar responds" — and Claude sends a message that does not tag the bot, so nothing happens. Saying tag @joestar explicitly avoids that. Ray also waits 30 seconds; 60 is safer here, because a cold Vercel function plus a fresh E2B sandbox took about 15 seconds on a good run and can take longer.

  2. Watch it in Slack while it runs.

    Open #joestar-test. You should see, in order: your message with a sent using Claude label, the bot's thinking… placeholder in a thread under it, and then that placeholder being replaced by the answer.

    Seeing the placeholder turn into an answer is the proof. It means Slack delivered the event, the function ran, the sandbox booted, Claude answered, and the reply got edited back in — the entire chain from lessons 04 and 05, in one observation.

  3. Read what Claude reports back.

    Claude should tell you the bot replied and quote the answer. If it says there was no reply, go to When the test says nothing came back in part 3 — the failure is informative, and Claude can usually diagnose it itself if you ask it to check the Vercel logs.

You cannot read the timing off the thread. The answer replaces the placeholder rather than following it, and an edit keeps the original message's timestamp. So the reply will appear to have arrived a second after your mention however long Claude actually took. For the real figure, watch the placeholder change, or read [claude] answered in X ms in the Vercel logs.
What happened here. On 15 September 2026, asking "what is 2 + 2?" in #joestar-test produced a reply of 4 from joestar, in the thread, first try. The parent message carried the sent using Claude label; nothing was typed in Slack by hand.
CHECKPOINTClaude reports that joestar replied, and quotes the answer — and you can see the same exchange in #joestar-test.

Step 5 of 5 — Write the verification step into CLAUDE.mdSo the loop survives this session. A capability nobody remembers is not a capability.

DO NOW

  1. Ask for the rule to be recorded.

    Add a verification step to CLAUDE.md: after any change to the bot, post in
the #joestar-test Slack channel tagging @joestar, wait, and read the thread to
confirm it replied properly. Say what counts as a pass and what to do on a fail.

  2. Read what it wrote, and make it specific.

    A vague instruction produces a vague habit. The rule should name the channel, name the bot, give a wait long enough for a cold start, and say what a pass looks like — a real answer replacing the placeholder, not merely "the bot said something".

    Say when not to run it. This test costs a real sandbox and real Claude usage every time. It belongs after a deploy that changes behaviour, not after every edit — npm test and bin/smoke are the cheap checks that come first.

  3. Commit it.

    Commit CLAUDE.md along with the lesson page. The instruction is the deliverable of this lesson — everything else was configuration in other people's systems.

    Where this differs from Ray. Ray adds the step and moves on. Here CLAUDE.md already carries the project's hard rules, so the verification step joins them rather than starting a new file — and the existing rule about never pushing without explicit go still applies to the commit.
CHECKPOINTCLAUDE.md contains a verification step naming #joestar-test and @joestar, and it is committed.
PART 3

Keep for later

The prompt to reuse, the failures worth recognising, and where everything lives.

The verification prompt, to reuseOne line for every lesson from here on.

REFERENCE

The channel is #joestar-test (C0C1QB5PCNB) and the bot is <@U0C1T5AQ0G6>. Once the rule is in CLAUDE.md, this is all it takes:

Verify the change end to end on #joestar-test.

When something is wrong and you want the diagnosis too:

Verify end to end on #joestar-test. If the bot doesn't reply, check the Vercel
logs for the function and tell me which link in the chain broke.

And the cheap checks that should come first, neither of which posts anything in Slack:

npm test            # the handler's logic, no network
bin/smoke           # the deployed endpoint, a signed payload, #bot-smoke

When the test says nothing came backFive failures, in the order they are worth checking.

REFERENCE
What you seeAlmost always
Claude has no Slack tool at allThe session started before the connector was attached. Quit and relaunch, then /mcp.
Message posts, bot silent, no placeholderThe bot is not in the channel. /invite @joestar. This is Ray's failure in the video.
Message posts but does not tag the botThe prompt did not say to tag it. Slack sends app_mention only for an actual mention — a message merely containing the word "joestar" is not one.
Placeholder appears, then never changesThe sandbox or Claude failed after the 200 was sent. Vercel's logs for the function will show [claude] failed: with the reason.
Claude reports no reply, but Slack shows oneIt read the thread too early. Increase the wait; a cold start plus a sandbox boot can outrun 30 seconds comfortably.
A failed test that names the broken link is worth more than a passing one. That is the point of having levels: if npm test passes and bin/smoke passes and this fails, the fault is in Slack's delivery or the sandbox — not in the handler, which the first two just proved.
