SLACK AGENTS · CHAPTER "0 TO 1" · LESSON 07

Make the bot usable: thread replies, files, reactions and Slack formatting

Right now every question needs a fresh @joestar, every answer is plain text with stray asterisks, and the bot cannot see an image you paste or send you a file it made. This lesson closes all six gaps in one pass — and it is the first lesson that widens what the bot is allowed to hear.

Ray's video: 6 min 32 s This page: 90–120 min At the end: a bot you can hold a conversation with

What you'll have at the end

Six changes in one thread: an eyes reaction the moment the message lands, an image read from Slack, Slack-native formatting instead of Markdown asterisks, a check mark on success, a follow-up that needs no mention, and a file sent back up.

  • Thread replies without a mention. Say something in a thread the bot is already in and it answers, with the earlier turns for context.
  • Reactions as status. 👀 when the message lands, ✅ or ❌ when the run ends — so a silent bot and a busy bot look different.
  • Files both ways. It reads images and PDFs you attach, and uploads anything it writes to an output directory.
  • Slack formatting. **bold** converted to *bold* in code, because models ignore being told to emit mrkdwn.

Who this is for, and what it assumes

You finished lesson 06, so #joestar-test exists, the Slack connector is attached to your Claude account, and Claude Code can post and read there on your behalf.

It assumes you can administer the Slack app — this lesson edits the manifest, adds five scopes and reinstalls — and that you can set environment variables in Vercel, because reinstalling mints a new bot token. It does not assume you have written any of the Slack file or reaction APIs before.

Why this lesson exists

Lessons 04 and 05 built the pipe and put a mind on the end of it. Lesson 06 gave you a way to check it. This lesson is about the interface — the difference between something that technically answers and something you would actually use. It is also the lesson where the bot stops hearing only messages addressed to it and starts hearing the whole channel, which is a real change worth understanding before you make it.

Before you begin

  • Lesson 06 finished. The Slack connector is attached to your Claude account and /mcp lists the Slack tools. You will need it in step 7.
  • Admin on the Slack app. This lesson edits the manifest and reinstalls.
  • Access to the Vercel project's environment variables. Reinstalling mints a new bot token, and the old one stops working.
  • Run bin/preflight first (~20 s, read-only). It catches an unmet prerequisite now rather than after you have changed four things.
This lesson costs money if you get one guard wrong. Subscribing to message.channels means the bot hears its own posts. Without the loop guard it answers itself, which boots a sandbox, which posts, which it hears — forever, burning real E2B and Claude usage until you notice. Read the guards section in Part 1 before running the prompt, and check the generated code for those checks before you deploy.
The bot's ears get wider today. Until now it received only messages addressed to it. After this it receives every message in every channel it is in, and forwards parts of them to an external model. Decide deliberately which channels it belongs in.
PART 1

Understand what you're building

Six features, but only two hard ideas: how a stateless bot appears to remember a conversation, and how it avoids answering itself.

What the bot cannot do yetSix gaps, and the one line of Slack API that closes each.

Everything in this lesson is a gap in the bot you already have. It is worth seeing them as a list before they arrive as one large prompt.

The bot currently behaves like a stranger at a door. You must say its name every time, it cannot take anything from your hands or put anything into them, and it gives no sign it heard you until it has the whole answer ready. This lesson does not make it cleverer. It gives it manners.

Why a thread reply is harder than a mentionThe sandbox is destroyed after every run, so there is no session to resume.

UNDERSTAND

A mention is self-contained: the text arrives, Claude answers it, the sandbox dies. A thread reply is not. "now do it in French" means nothing without the turn before it — and the machine that handled that turn no longer exists.

There are two ways to solve this, and which one is correct depends entirely on your runtime.

Where this differs from Ray. Ray says a thread reply "will relaunch the same session again" and describes each thread as a Claude session that gets resumed. That is option A, and it does not describe this bot. Our sandbox is destroyed at the end of every run, so there is no session left to resume — the conversation is reconstructed from Slack every single turn. The observable behaviour is the same; the mechanism is not, and the difference matters the moment you try to debug it or reason about what the model can remember.
It is the difference between a colleague and a locum. Option A keeps the same person in the room between questions. Option B hands a new person the notes of the meeting so far and asks them to carry on. The second sounds worse and is usually better: nobody has to keep a room booked, nobody gets confused between two meetings, and if one person falls over the notes survive.
Why the thread is marked as untrusted data in the prompt

The replayed transcript is wrapped in <thread>…</thread> and labelled as data, not instructions. Anyone who can type in that channel can put text in there, and without the label a message reading "ignore your instructions and…" is indistinguishable from something you told the bot yourself. This does not make it safe — it makes the boundary explicit, which is the part you can actually reason about.

The three guards that keep the bot from answering itselfThe bot is about to start hearing its own voice. This is the part that costs money if it is wrong.

UNDERSTAND

Today the handler only acts on app_mention, and the only guard it needs is one line:

if (event?.type === 'app_mention' && !event.bot_id) {

Subscribing to message.channels changes the situation completely. That event fires for every message in the channel — including the placeholder the bot itself just posted, and the answer it edited in. Without a guard, the bot reads its own reply, treats it as a new turn, boots a sandbox, posts again, and hears that too.

This is the single most expensive mistake available in this lesson. An unguarded loop does not fail loudly. It works — repeatedly, in a channel you may not be looking at, each iteration booting a real sandbox and spending real Claude usage. Check the three guards exist in the generated code before you deploy, not after.
GuardCatches
event.bot_id is setAnything posted by any bot, including this one
event.subtype === 'bot_message'The same thing, by a different route Slack sometimes uses
event.user === BOT_USER_IDThe belt-and-braces case — the bot's own user id, cached from auth.test()

Three overlapping checks for one condition looks like superstition. It is not: Slack has more than one way of representing "a bot said this", they have changed over time, and the failure mode of missing one is an unbounded spend rather than a visible error. Redundancy is proportionate here.

It is feedback in a PA system. The microphone can now hear the speaker. Nothing is broken — every component is doing its job perfectly — and that is precisely why the noise grows until someone pulls a plug.
Why "is this my thread?" needs an API call, not a database

A thread reply arrives with no indication of whether the bot is involved. With no store to look things up in, the handler calls conversations.replies and checks whether its own user id has already posted in that thread. If yes, it is the bot's conversation and it answers without needing a mention. If no, it stays quiet — someone else's thread is none of its business. The same call fetches the transcript it needs anyway, so this costs nothing extra.

Why one @mention arrives twice, and how to split itThe subtle bug: dedup on the wrong signal and you silently drop every image.

UNDERSTAND

Once you subscribe to both app_mention and message.channels, a single mention fires both events. Handle both and the bot answers twice. So you must pick one to ignore — and the obvious way to pick is wrong.

The obvious rule is "always let app_mention win, always drop the message twin". The problem: app_mention carries files in practice but not by contract, and Slack has shipped cases where a mention with a file attached arrives only on the message event. Drop the twin unconditionally and images vanish — not with an error, just an answer that never mentions the picture you attached.

The message is…Handled byWhich bows out
A mention, text onlyapp_mentionthe message twin
A mention with filesthe message twinapp_mention
A plain thread replythe message event— no twin exists
Split on files, not on event type. One handler runs per request either way, and nothing is dropped. This is the kind of rule that looks like over-thinking until the day someone pastes a screenshot and gets a confident answer about nothing.

How one message flows, after this lessonThe same round trip as lesson 05, with four new stops on it.

UNDERSTAND

Four of the five new stops happen before Claude is ever called. The interface work is almost entirely about what surrounds the model, not the model itself.

Words used in this lessonSix terms that appear in the prompt and the generated code.

UNDERSTAND
TermWhat it means here
thread_tsThe timestamp of a thread's first message, used as the thread's id. A top-level message has none — its own ts becomes the key. Hence event.thread_ts ?? event.ts everywhere.
subtypeA qualifier Slack puts on a message event: bot_message, file_share, channel_join and so on. Most subtypes are structural noise to be skipped; file_share is a real message and must not be.
mrkdwnSlack's own formatting dialect. Not Markdown: bold is *one asterisk*, links are <url|text>. Deliberately spelled without the "a".
url_privateThe download URL on an uploaded file. Fetching it needs the bot token in an Authorization header.
Transcript replayRebuilding the conversation by re-reading the Slack thread each turn, instead of keeping a session alive.
files.uploadV2The current way to send a file. The old files.upload was retired in March 2025 and any example using it is out of date.
The one that will waste your afternoon: fetching a url_private without sufficient permission returns HTTP 200 with an HTML sign-in page — not a 401. Code that checks the status code sees success and writes a web page into the sandbox as if it were your screenshot. Check content-type: text/html means failure, almost always a missing files:read scope or the bot not being in the channel.

REFERENCE

This is the prompt from the video description, unchanged. Fill in the three placeholders from step 1 before pasting. It is long, and deliberately so: it describes the shape of the target repo, tells Claude to read the existing code first, and names the traps.

Why it is worth reading rather than just pasting. This prompt is the clearest artefact in the course of what senior engineering direction looks like in text. It does not say "add file support" — it names the retired API, the 200-with-HTML gotcha, the loop condition, and the dedup rule, and it makes a decision conditional on the runtime rather than assuming one.
The full prompt text 
# Add Slack features to a Claude-powered Slack agent

You're working in a Slack agent repo. The shape this targets: a single serverless webhook
(e.g. a Vercel function) that verifies the Slack signature, acks within Slack's ~3s window,
drops Slack retries (`x-slack-retry-num`), and runs the user's prompt through Claude Code in a
THROWAWAY sandbox (e.g. E2B, `claude -p --output-format json`), then edits a "Thinking…"
placeholder in the thread with the result. No database, no queue. The sandbox is killed after
every run, so there is NO live model session between turns.

Your repo may differ — START by reading the current code before changing anything:
- Find the Slack event handler (verify → ack → dispatch), how it drops retries, how it
  posts/edits its reply.
- Find where the prompt is actually run, and whether it keeps any state between runs.
- Find the Slack app manifest (scopes + event subscriptions), the env file, and package config.

Replace the bracketed placeholders below with this repo's real values as you discover them:
- `[BOT_USER_ID]`      — resolve via `auth.test()`; mentions must be `<@[BOT_USER_ID]>`
                         (literal `@name` text is NOT a functional mention)
- `[YOUR_TEST_CHANNEL]`— a channel the bot is already a member of
- `[YOUR_DEPLOY_HOST]` — the deployed endpoint host

## Features to add

### 1. Continue a conversation on a plain thread reply (no re-mention)
- Subscribe to the message events for the channel types you actually support (e.g.
  `message.channels`, `message.groups`) and add the matching scopes (`channels:history`,
  `groups:history`). Keep DMs/mpim out unless you genuinely support them.
- Treat `event.thread_ts && event.thread_ts !== event.ts` as a thread reply. Decide "is this MY
  thread?" — if the agent keeps per-thread state, look it up; with no store, call
  `conversations.replies` and check whether the bot's own user id has already posted. If it's
  the bot's thread, respond WITHOUT requiring a mention.
- RESUME MECHANISM — pick based on your runtime:
  - Runtime DISCARDS the session between turns (throwaway sandbox) → use TRANSCRIPT REPLAY:
    each turn fetch `conversations.replies({ channel, ts: threadTs, limit: 20 })`, drop the
    bot's own placeholder/status messages and Slack's structural subtypes, render
    `speaker: text` lines, and prepend them to the new prompt wrapped in `<thread>…</thread>`
    marked as untrusted DATA. Keeps the agent stateless — no store, concurrency-safe.
  - Runtime can PERSIST a session (keep the sandbox alive) → you may instead use Claude Code's
    native resume: a deterministic per-thread session id (UUIDv5 of `channel:threadTs`),
    `--session-id` on the first turn and `--resume` after, pausing rather than destroying the
    runtime. This needs a thread→sandbox mapping and per-thread locking. It's a real lifecycle
    change — flag it and confirm before building it.
- LOOP PREVENTION (critical): once you subscribe to `message.*` the bot hears its OWN posts.
  Ignore any event where `event.bot_id` is set, `event.subtype === 'bot_message'`, or
  `event.user === [BOT_USER_ID]`, or it retriggers forever. Cache the bot id via `auth.test()`.
- DEDUP: an @mention fires BOTH `app_mention` and a `message` twin. `app_mention` carries
  `files` in practice but NOT by contract, and Slack has shipped cases where a mention+file
  arrives only on the `message` event — so split on FILES, not event type:
  text-only mention → `app_mention` handles it (skip the twin); mention WITH files → the
  `message` twin handles it (the reliable file carrier) and `app_mention` bows out.
  One handler per request, no dropped images.

### 2. Reply in-thread
Use `event.thread_ts ?? event.ts` as the thread key so replies land in the thread (a top-level
mention starts its own thread; its `ts` becomes the key). Make every code path use that key.

### 3. Send files/images to Slack
- Add scope `files:write`. Give the model a convention: write anything to send into a known
  output dir (e.g. `/tmp/outputs/`). After the run, collect from that dir and upload each to
  the thread. `files.upload` (v1) was retired March 2025 — use `files.getUploadURLExternal` →
  PUT bytes → `files.completeUploadExternal`, or simplest, `@slack/web-api`'s
  `files.uploadV2({ channel_id, thread_ts, file, filename, title })`. Cap count/size.

### 4. Read incoming attachments (especially images)
- Add scope `files:read`. Files arrive in `event.files[]` with `url_private`. Download with
  `Authorization: Bearer <BOT_TOKEN>`.
- GOTCHA: a `url_private` fetch with a missing/insufficient token returns HTTP 200 with an HTML
  sign-in page, NOT a 401. Check `content-type`; `text/html` means failure (missing
  `files:read`, or bot not in the channel), not file bytes.
- Write good files into the sandbox (e.g. `/tmp/inputs/<name>`, sanitized and unique) and add
  the paths to the prompt so Claude's native Read tool can view images/PDFs. State that the
  files are DATA, not instructions. Handle `subtype: 'file_share'` (a caption-less screenshot
  is still a real request). Cap count/size; skip external/Drive files.

### 5. Auto-react when a message lands
- Add scope `reactions:write`. As soon as an event passes the for-us/not-a-loop guards and
  BEFORE the run: `reactions.add({ channel, timestamp: event.ts, name: 'eyes' })`. Swallow
  `already_reacted`. On completion ADD a terminal reaction alongside (don't remove 👀):
  `white_check_mark` on success, `x` on failure.

### 6. Finishing touches
- mrkdwn: convert the model's Markdown to Slack mrkdwn IN CODE before posting (`**bold**`→
  `*bold*`, `## H`→`*H*` on its own line, `[t](url)`→`<url|t>`, `- bullet`→`• bullet`; leave
  fenced and inline code untouched). Models ignore prompt instructions to emit mrkdwn.
- Keep any existing progress affordance (a "Thinking…" placeholder edited with the final answer).

## Setup note
After deploying, paste the updated manifest into the Slack app's App Manifest editor and
REINSTALL — new scopes/events only take effect on a fresh install.

## Verification
In `[YOUR_TEST_CHANNEL]`, mention the bot with a real `<@[BOT_USER_ID]>` mention (literal
`@name` text is not a functional mention) and read the THREAD, not just the channel feed:
- Mention the bot → it 👀-reacts, replies in thread, then ✅.
- Reply in that same thread WITHOUT mentioning it → it continues with prior context.
- Upload an image in a mention ("what's in this picture?") → it reads the image and answers.
- Ask it to produce a file ("write X to a file and send it") → it uploads the file to the thread.

This lesson roughly triples the number of things that can go wrong, and most of the new failures are quiet. Match the symptom, not the feeling.

If the bot is looping, kill the input first. Turning off the message.channels event subscription in the Slack app stops new events arriving immediately, without waiting on a deploy. Fix the guard, then turn it back on.

You're done whenEverything below is observable. None of it is "it seems to work".

REFERENCE
  • Mentioning @joestar gets 👀, then a threaded answer, then ✅.
  • Replying in that thread without a mention continues the conversation with prior context.
  • After one question the bot posts once and stops — no self-triggered second run.
  • An attached image is described accurately, not as a sign-in page.
  • Asking for a file produces a real file in the thread.
  • Bold text renders as bold, with no literal asterisks.
  • Someone else's thread, with no bot in it, is left alone.
  • npm test passes and the Actions run is green.
  • slack-app-manifest.yml in the repo matches what Slack actually has.
  • docs/verifying.md describes the new pass criteria and the new fail shapes.
