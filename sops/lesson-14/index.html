SLACK AGENTS · CHAPTER "0 TO 1" · LESSON 14

Give the bot reusable procedures: a skills folder that ships with the deploy

Lesson 13 gave the sandbox a persona — a few paragraphs about the machine it wakes up on. This lesson gives it procedures: folders of Markdown, each one a way of doing a recurring job properly, copied into ~/.claude/skills/ before the model reads a word of your message. The interesting part is not the copying. It is that these live in the bot's own repository, so a new skill is a pull request and a deploy — not a rebuild of the machine image.

Ray's video: 3 min 20 s This page: 45–90 min At the end: ~/.claude/skills/ populated on every run

What you'll have at the end

The one line that makes this work in production is includeFiles, and it is the one line you cannot test before deploying.

  • A toolkit/skills/ folder in the bot's repository, one directory per skill, each with a SKILL.md.
  • A loader that writes them all into ~/.claude/skills/ on every run, in the same batched call that writes the persona from lesson 13.
  • One line of vercel.json that keeps the folder in the deployed bundle.
  • A first real skill — task-lifecycle — telling the bot how to run a job end to end inside a four-minute budget.

Who this is for, and what it assumes

You finished lesson 13, so the sandbox already gets a ~/.claude/CLAUDE.md written into it on every run, and you know where that write happens. This lesson adds files to that same call. If lesson 13 is not done, do it first — the loader here is an extension of it, not a separate mechanism.

You also need to be able to open, review and merge a pull request against the bot's own repository, which you have had since lesson 09. Nothing here touches the E2B template, so no image rebuild is involved at any point.

Why this lesson exists

Every later lesson that adds a capability also adds a skill telling the bot how to use it. Lesson 16's Codex CLI and lesson 17's voice notes both arrive this way.

A persona is what the bot is; a skill is what it knows how to do. The persona is loaded always and therefore has to stay short. A skill is a folder the model opens only when the job calls for it, so it can be long and specific — eight numbered steps, a budget, a list of things never to do. That difference in loading is the whole reason both exist.

Before you begin

Do not ask for lessons 13 and 14 in one message. That is what was tried here, and the run hit the 255-second sandbox deadline with nothing pushed — the work was real and it was lost. The loader and the first skill are two pull requests, and the second is based on main rather than stacked on the first, so a stall in either does not take the other down with it.
  • Lesson 13 merged and deployed, so a persona file is already written into every sandbox.
  • A skill in mind. Write the procedure you keep repeating in the channel, not a generic one.
  • Nothing to rebuild. If you find yourself running e2b/build.mjs in this lesson, you have taken a wrong turn.
PART 1

Understand what you're building

Three things: what Claude Code means by a skill, why a skill belongs in the bot's repository instead of its machine image, and why one line of vercel.json is the difference between working locally and working at all.

What a skill is, and where Claude Code looks for oneA folder, a Markdown file and a front-matter description. That is the entire format.

UNDERSTAND

A skill is a directory whose name is the skill's name, containing a SKILL.md with YAML front matter — a name and a description — followed by prose. Anything else in the directory (scripts, reference files, examples) comes along with it. User-level skills live in ~/.claude/skills/<name>/, which is exactly where this lesson puts them inside the sandbox.

The persona is the induction; a skill is the manual on the shelf. You do not read the manual to every new hire on their first morning — you tell them it exists and where it is. The model reads the description lines, and opens the body only when a job matches one.

That last sentence is the part to hold lightly. It is how skills are documented to work, and it is why the description is the most load-bearing line in the file. Whether it reliably fires unprompted in a headless claude -p run is listed as untested in Part 3 — what was confirmed here is that the files arrive and the model can read them.

Ray reaches for an official skill; this page writes its own. He starts with Anthropic's code-review skill plus a task-lifecycle one adapted from another class. The first thing worth writing yourself is the procedure you have already had to repeat in Slack — here that was the clone-branch-test-push-PR loop and its four-minute budget.

Why skills live in the bot's repository, not in its machine imageThe one design rule of this lesson, and the reason it is not a template change.

UNDERSTAND

Everything the sandbox has arrives by one of two routes, and they behave completely differently.

RouteHow you change itWhat that costs
The E2B template — Node, git, gh, Chromium, Postgres, the Codex CLIEdit e2b/template.mjs, then rebuild and register the image by handMinutes of build, no review, no CI, deployed the instant it finishes
The function's own files — the persona, and now the skillsEdit a file, open a pull request, merge itA review, a test run and a deploy — the ordinary path
Skills are words, not software. They change often, they are worth reviewing as prose, and they need no binaries. Putting them in the repository means a wrong instruction is caught in a diff and fixed by a revert, instead of being baked into an image that nothing rolls back. Capability goes in the image; procedure goes in the repo.

The same rule explains a split later in the course: lesson 16 installs the Codex CLI in the image and ships a codex skill in the repo saying how to call it. Two halves of one feature, deliberately shipped by different routes.

Why Vercel will not ship a folder nobody importsThe failure that cannot happen locally, only in production, and only silently.

UNDERSTAND

Vercel does not upload your repository to the function. It traces the imports from each entry point and bundles only the files it can prove are reachable. A folder of Markdown read at run time through a path built with path.join is reachable by nothing, so it is left out — and the function still deploys, still runs, and still answers. It just has no skills.

This failure is invisible until it is live. Locally the folder is simply on disk beside the code, so every test passes. In production the loader finds no toolkit/, degrades to writing the persona alone exactly as designed, and logs nothing alarming. The only proof is asking the deployed bot what it has.
"functions": {
  "api/slack/events.js": {
    "includeFiles": "toolkit/**"
  }
}

That block sits beside the existing git block in joestar-agent/vercel.json. The glob is relative to the Vercel project root, which is joestar-agent/ and not the repository root — easy to get wrong, and it produces exactly the same silent nothing.

Same line, same reason. Ray hits this too and adds includeFiles: "toolkit/**" for the same bundler behaviour. It is one of the few places in the course where the fix is a configuration line rather than a prompt.
PART 2

Build it

Five steps. One decision made before typing, two requests to the bot that were deliberately kept apart, a review of the diffs, and a live check that doubles as the only possible proof the deploy line works.

Step 1 of 5 — Decide whether the skills are written once or on every runRay's loader and this one differ here, and the reason is a property of your sandbox, not a preference.

DO NOW

  1. Answer one question: does your sandbox survive between messages? Here it does not — it is created and destroyed around every single message, and the thread is replayed into the prompt instead. So there is no "first run" to seed and no state to check. The skills are written on every run.

  2. Price it before worrying about it. The whole payload is a handful of Markdown files sent as one batched sandbox.files.write call, alongside the persona that is already being written. It is not a second round trip and it is not measurable against a four-minute budget.

    Ray gates his on the box being new. His loader writes the skills only when the sandbox was just created, which is the right answer for a design that reuses sandboxes across messages. Copy his gate only if you copied his lifecycle; with a per-message sandbox the gate is a branch that is always true.

  3. Write the decision into the code as a comment, not just into your head. "Written on every run because the sandbox is destroyed after each one" is the sentence that stops a future reader adding a cache that can never hit.

CHECKPOINTYou can say why there is no "first time" in this design, and that the cost of writing the files every run is one batched call.

Step 2 of 5 — Ask for the loader on its ownPart A: walk the folder, write the files, never fail the run. No skills yet, deliberately.

DO NOW

  1. Post the request in the development channel, mentioning the bot. Ask for the mechanism only — the loader, its guard rails, and the write into the existing call. Naming the failure modes up front is what stops the loader being a five-line readFileSync that throws on a missing folder.

    Where: Slack → #joestar-dev → mention @joestar

    Add a loader that copies a toolkit/skills/ folder from this repo into
~/.claude/skills/ in the sandbox, in the same batched files.write call that
already writes the persona. Every run — the sandbox is destroyed each time.

Rules: recurse into each skill directory so sub-files come too; skip dotfiles;
skip any skill directory with no SKILL.md and warn; cap the total payload at
2 MiB and fall back to persona-only if it is exceeded; if there is no toolkit
directory at all, write the persona and carry on. This must never fail a run.

Loader only in this PR. No skills, no vercel.json — those are the next one.

  2. Expect a question about where toolkit/ is at run time, and answer it honestly: you do not know. On Vercel the task root is not the module's own directory and is not necessarily process.cwd(), so the loader resolves two candidates and takes the first that exists.

  3. Let it open the pull request and stop there. This is PR #13 in this workshop, and it changes nothing observable — the folder it looks for does not exist yet, so every run still writes the persona alone. That is the correct state at the end of step 2.

    Splitting is the load-bearing part of this step. Asked for as one job together with lesson 13, this work ran to the 255-second sandbox deadline and pushed nothing. Two requests, the second based on main so it does not stack on an unmerged branch, and each one fits.
CHECKPOINTA pull request exists containing api/_lib/sandbox-files.js and its call site, and the bot still answers in Slack exactly as it did before.

Step 3 of 5 — Add the first skill and the deploy linePart B: the folder that was missing, plus the one line of vercel.json that gets it into production.

DO NOW

  1. Choose the procedure you have already had to repeat. Here that was task-lifecycle: shallow-clone, branch, read only what you were told to read, change, test, push the moment it passes, open the PR, report what you did not get to. Eight numbered steps, a four-minute budget written into the file, and three flat rules — never force-push, never delete branches, and say out loud when a change needs a human to rebuild the image.

    Write it as a checklist, not an essay. The reason the budget sentence works is that it says what to do when time runs out — push partial work and name what is left — rather than telling the model to be quick.

  2. Ask for the skill, the vercel.json block, and nothing else, based on main rather than on the branch from step 2.

    Where: Slack → #joestar-dev, branched from main

    Branch from main. Add toolkit/skills/task-lifecycle/SKILL.md — I'll paste the
content. Then add a "functions" block to joestar-agent/vercel.json giving
api/slack/events.js includeFiles "toolkit/**", beside the existing git block,
with the path relative to the joestar-agent project root.

That, plus any prompt line this makes redundant. Nothing else.

  3. Take the chance to delete anything the skill now says better. One line of the system prompt was duplicating what the skill says about the run budget, so it went in the same pull request — that is PR #14, three files, exactly as asked.

    Ray hits a name conflict here; this page did not. His code-review skill was reported by Claude Code as clashing with a built-in of the same name, so he moved it into a toolkit-disabled/ folder and shipped only task-lifecycle — then said at the end of the video that the warning had looked wrong. Treat skill-name conflict detection as unverified either way, and pick a name nothing else uses.
CHECKPOINTA second pull request exists with exactly three files changed: the new SKILL.md, vercel.json, and the prompt trim.

Step 4 of 5 — Read the diffs and mergeShort diffs, but one of them had its two path candidates in the wrong order.

DO NOW

  1. Read both diffs in full. They are small enough that there is no excuse not to.

    Where: gh pr diff 13 and gh pr diff 14, or the pull request pages

  2. Check the two things a reviewer can actually catch here. First, that every degradation path returns the persona rather than throwing — a missing folder, a skill without a SKILL.md, an over-cap payload. Second, the order of the two candidate toolkit/ roots: the module-relative path must be tried before process.cwd(), because cwd is the one that is not guaranteed on Vercel. It came back the other way round and was corrected in review.

    One type detail worth not losing. The files are read as Buffers, and e2b's WriteEntry type wants a Blob — so the call site wraps each buffer before writing. If that wrapper disappears in a later refactor, the symptom is a write failure, not a compile error.

  3. Merge them, in order, and let CI deploy. Here that was a squash merge by hand.

    Where: your terminal

    gh pr merge 13 --squash --admin
gh pr merge 14 --squash --admin
CHECKPOINTBoth pull requests are merged, CI is green, and the deploy has finished. Nothing has been rebuilt or re-registered.

Step 5 of 5 — Ask the deployed bot what it hasThe only possible proof that includeFiles worked, because nothing local can tell you.

DO NOW

  1. Ask a question only a bot holding the files can answer. "What skills do you have?" is half a test — a model can guess plausibly. Ask for something checkable as well.

    Where: Slack → #joestar-test → mention @joestar

    List the skills in ~/.claude/skills/, and tell me how many numbered steps the
task-lifecycle skill has.

  2. Read the answer as two facts at once. Here it came back with task-lifecycle and 8 steps. The name proves the loader ran; the step count proves it read the real file; and both together are the only evidence that includeFiles put toolkit/ into the deployed bundle — a claim that could not be checked before the deploy.

    Every skill from here on is one pull request. Drop a folder into toolkit/skills/, merge, done. In this workshop codex followed in PR #15 at 55 lines, and voice notes in PR #16.

  3. Note what you have not proved. You have shown the files are present and readable. You have not shown that a skill fires on its own from its description in a headless run — that needs a task which matches a skill without naming it.

CHECKPOINTThe deployed bot names your skill and answers a detail question about its contents that it could not have guessed.

What the loader does, decision by decisionEvery branch in api/_lib/sandbox-files.js exists to make a bad toolkit harmless.

REFERENCE

The function's whole job is to return an array of { path, data } entries for one batched write. It is built so that nothing it can find on disk is able to fail a run.

DecisionWhy
No toolkitDir resolved → return the persona entry aloneThe production case if includeFiles is missing. Degrading to lesson 13's behaviour is right; throwing would take the bot down over a documentation folder
Recursive walk of each skill directoryA skill is a folder, not a file. Scripts and reference files under it are part of it
Dotfiles and dot-directories skipped.DS_Store and editor droppings are not skills, and a sandbox is not the place to find out
A directory with no SKILL.md is skipped, with a console.warnSkipping silently hides a mistyped filename for weeks. The warning is the whole difference
Total payload over 2 MiB → persona only, with a warningA runaway folder should cost you your skills, not your run. The cap counts the persona too
Two candidate roots, module-relative firstVercel's task root is neither this module's directory nor reliably process.cwd(). Order matters: the guessable one goes second
The call site wraps the whole thing in try/catchBelt and braces. A loader that cannot read its own files still leaves a working bot
Read the shape of this and you have the pattern for lesson 17 too. Anything you want in every sandbox — persona, skills, later a config file — is another entry in the same array, written by the same call, degrading the same way.
