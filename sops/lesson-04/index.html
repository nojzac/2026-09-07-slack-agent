00 — WHERE THIS FITS

The random number is a placeholder. The wiring is the lesson.

Nothing here cares about random numbers. What you are building is a round trip: Slack notices a mention, hands it to code you control, your code decides something, and pushes an answer back. Lesson 05 replaces the "decides something" step with Claude Code in a sandbox. Every lesson after that replaces it with something richer. The pipe you build now stays.

So the thing worth owning at the end of today is not the file. It is being able to answer: when I type a mention, what happens, in what order, and what would break it?

01 — THE CAST

Five platforms, and why each one is there

The most common reaction to this lesson is "why does a bot that picks a number need five accounts?" Fair. Each one exists because of a constraint that becomes obvious once you name it.

PlatformIts one jobThe constraint that forces it
Slack Owns the conversation. Detects the mention, sends it to you, and displays your reply. You cannot poll Slack for mentions. Slack pushes events to a URL — so something of yours must be reachable at a URL.
Vercel Runs your code at a public HTTPS address, on demand, without a server you maintain. Slack needs somewhere to POST. Your laptop is not it — the URL must be public, always up, and TLS.
GitHub Holds the source of truth for the code, privately, with history. Vercel deploys something. Better that it deploys a reviewed commit than a folder on one laptop.
1Password Holds the two secrets, and hands them out to a command that asks. A bot token lets anyone post as your bot. It must not live in a file, a repo, a screenshot or a chat log.
GitHub Actions Runs the tests on every push, and only then deploys. Once a push deploys automatically, "it compiles on my machine" is the only thing standing between a typo and production.
Why serverless, rather than a small server somewhere?

A bot that answers mentions does nothing at all between mentions. A rented server would sit idle burning money and asking to be patched. A serverless function is a piece of code with a URL: the platform starts it when a request arrives and throws it away afterwards. You pay per request, you patch nothing, and there is no process that can quietly die at 3am.

The cost is cold starts (the first request after a lull is slower) and statelessness — nothing you keep in memory survives to the next request. Both are irrelevant here and stay irrelevant for most of the course. When state matters, it goes in a database (lesson 12), not in a variable.

Why not Socket Mode, which needs no public URL at all?

Slack offers Socket Mode: your bot opens an outbound websocket and receives events through it, no public endpoint needed. It is genuinely easier to start with — and it means your bot only runs while some process of yours is running. That is a laptop-shaped bot.

The course deploys instead, so the bot is up when you are asleep. The price of that choice is exactly one thing: because your endpoint is publicly reachable, anyone can POST to it, so you must prove each request really came from Slack. That is the signing secret, and it is why it matters so much here and not at all in Socket Mode.

Why a private repo for a bot that picks numbers?

Today it is trivial. By lesson 15 this repo contains your prompts, your CLAUDE.md, the shape of your internal tooling, and the wiring of an agent with access to your systems. Repos rarely get made private later; make it private now and stop thinking about it.

02 — MECHANISM

How one message flows

Read it in order. Slack holds no code of yours — it holds a URL. Everything you configure today exists to make that one round trip legal and reachable.

The three-second rule, and why it shapes the code

Slack expects HTTP 200 within three seconds. Miss it and Slack assumes failure and redelivers the same event, up to three times. A handler that does slow work before answering therefore gets run repeatedly and posts duplicate replies.

Two consequences you will meet later: every retry carries an x-slack-retry-num header, which is how you recognise and ignore duplicates; and from lesson 05, when the work takes far longer than three seconds, you must acknowledge first and do the work afterwards.

The two credentials, and why one is not enough

They point in opposite directions, which is the whole reason there are two.

Signing secret — inbound. Shared only between Slack and your function. Slack hashes the request body and timestamp with it and sends the result in a header; your code recomputes the same hash and compares. Mismatch means it wasn't Slack, and you answer 401 without doing anything. It exists because your URL is public and anyone can POST to it.

Bot token — outbound. A bearer token proving to Slack that you may post as this bot. It belongs to the app installed into one workspace — install elsewhere and you get a different token. Anything holding it can post as your bot, so treat it exactly like a password.

Neither substitutes for the other: the signing secret cannot post, and the bot token cannot prove an inbound request was genuine.

Why the reply lands in a thread, and the one line that decides it

Slack threads by a timestamp. A message's own id is ts; a reply carries thread_ts pointing at the root. So:

thread_ts: event.thread_ts ?? event.ts

If the mention was already inside a thread, thread_ts exists and you reply in that same thread. If it was a top-level message, there is no thread_ts yet, so you use the message's own ts — which creates the thread. Get this backwards and your bot either starts a new thread every time or replies at top level and buries the channel.

03 — GLOSSARY

Terms this lesson assumes

Event subscription
Standing instruction telling Slack "when this happens, POST it to this URL". Yours is app_mention. It is inert until you save it — see section 07.
Scope
One named permission on the app. You need exactly two: app_mentions:read to receive the mention, chat:write to post. That is the entire permission surface — your bot cannot read channel history or see DMs.
App manifest
Your Slack app's configuration as one YAML/JSON document: bot user, scopes, events, request URL. Config as code — it can be pasted to create an app, and later diffed.
Request URL
Where Slack POSTs events. Your deployed function, ending /api/slack/events.
URL verification challenge
A one-off POST Slack makes when you set the URL, carrying a random challenge string your endpoint must echo back. Passing it turns the field green.
Serverless function
Code with a URL and no server. Started per request, discarded after. Keeps nothing in memory between requests.
Environment variable
A value handed to your code by the platform at runtime rather than written in the code. How secrets reach a deployment without entering the repo.
Service account (1Password)
A non-human identity with a token, granted access to specific vaults only. Lets a script read one vault without unlocking your whole account.
04 — BEFORE YOU START

Check the ground first — this is where the hours go

Read this even if you skip everything else. On the run this page is written from, most of the lost time was a prerequisite that was missing and silent. Not a bug. Not a hard step. A box that was never ticked, failing quietly hours later.

Accounts

  • A throwaway Slack workspace (lesson 03) where you can install apps.
  • GitHub, and gh logged in.
  • Vercel — with GitHub connected as a login connection. See below.
  • 1Password, if you are doing secrets properly. A Teams/Business account if you want a service account.
  • Claude Code, in a terminal. Node 20+.

Connect Vercel to GitHub before you start

If your Vercel account has no GitHub login connection, two things happen, neither obviously:

  • vercel link refuses with "You need to add a Login Connection to your GitHub account first."
  • Far worse: CLI deploys are blocked. They sit at status UNKNOWN forever — no build logs, no CLI error, nothing. The reason appears only in a dashboard modal: "the commit email … could not be matched to a GitHub account."

That message sends you to the wrong fix. It suggests changing git config user.email. Check before you touch anything — if GitHub already attributes your commits to you, your email is fine:

gh api repos/<owner>/<repo>/commits --jq '.[] | "\(.commit.author.email) \(.author.login)"'

author.login showing your username means the email is verified and correct. The real fix is on Vercel: account settings → Login Connections → Add Connection → GitHub, namespace = your GitHub user, and scope repository access to this repo only.

If you have this project's scripts, one command checks all of it 
bin/preflight

Fifteen read-only checks — Node, gh, the 1Password token and both secret references, the Slack token and its scopes, Vercel login, project link, production env vars, the live endpoint, and the last CI run. About twenty seconds, changes nothing. The CI check is the cheap proxy for "is Vercel still connected to GitHub", which has no command of its own.

05 — BUILD IT

Six phases

Phases A and B run in parallel — start Claude writing, then go and click in Slack while it works. That is what makes the video look fast.

Phase A · The code

Claude writes it. You read it in section 06.

  1. Make a folder, launch Claude Code, paste the prompt.

    Where: your terminal

    Can we make a really simple Slack bot here that we will be deploying to
the Vercel whereby when I tag it, then it will automatically reply to the
message in the thread with a random number.

    Do not watch it work — go do Phase B.

    This workshop differs: the folder and git repo already exist, so skip git init. Everything else stands.

  2. Ask for the manifest. While it is still working:

    give me a manifest for the Slack API
    Before you paste that manifest anywhere, check it for a placeholder request URL like https://<deployment>/api/slack/events. Nothing is deployed yet, so it cannot contain a real one. Either delete the event_subscriptions block entirely and add the URL by hand in Phase E, or leave it and expect Slack to reject it. Pasting the placeholder verbatim produces "Your URL didn't respond" and five minutes of confusion.

Phase B · The Slack app

Create it from the manifest, install it, collect two secrets.

  1. Create the app from the manifest.

    Where: api.slack.com/apps → Create New App → From a manifest

    Pick your test workspace, paste the manifest, Next, Create. The two scopes shown should be exactly app_mentions:read and chat:write.

  2. Install it into the workspace — sidebar → Install App → Install to <workspace>.

    Slack now shows a Bot User OAuth Token starting xoxb-. That token exists only because the app is installed; that is why it lives here and not with the other credential.

  3. Collect the signing secret — sidebar → Basic Information → App Credentials → Signing Secret → Show.

Phase C · The secrets

Into 1Password first, then to Vercel. Never into a file.

  1. Create one 1Password item holding both values.

    Where: the 1Password app

    Vault of your choice, title matching your project, two password-type fields: signing_secret and bot_token. Use the app, not the CLI — a value passed as a command argument lands in your shell history.

  2. Point the repo at them with references, not values. A committed .env.op:

    SLACK_SIGNING_SECRET=op://<Vault>/<item>/signing_secret
SLACK_BOT_TOKEN=op://<Vault>/<item>/bot_token

    Then any command that needs them runs as op run --env-file=.env.op -- <command>, and the values exist only inside that one process.

    Ray does it differently: he keeps a .env.example with blank values and pastes the real ones into Vercel's dashboard by hand. Same end state; the difference is whether a secret ever passes through your clipboard and a browser form.

  3. Optional but recommended: scope the access. 1Password's desktop integration unlocks your whole account to any command you run. A service account is narrower — read-only, one vault:

    security add-generic-password -U -a "$USER" -s op-<name> \
  -w "$(op service-account create <name> --vault <Vault>:read_items --raw)"

    One command: create the token and put it straight in the Keychain, never on screen or in a file.

    Do not paste that token into an interactive prompt. security add-generic-password -w without a value prompts you — and truncates at 128 characters. Real tokens are ~830. The result is silent corruption that surfaces later, in a different tool, as "failed to DecodeSACredentials … unexpected end of JSON input".

  4. Give Vercel its own copy, piped rather than typed:

    op read "op://<Vault>/<item>/signing_secret" \
  | npx vercel@latest env add SLACK_SIGNING_SECRET production

op read "op://<Vault>/<item>/bot_token" \
  | npx vercel@latest env add SLACK_BOT_TOKEN production

    Production scope only — Vercel pre-ticks all three environments if you use the dashboard.

    Never run vercel env pull. It writes a real .env.local full of live secrets into your project — the exact thing this arrangement avoids. Note that vercel link and vercel dev also create that file (with a harmless OIDC token), so gitignore .env* as a backstop.

    Two copies now exist by design: 1Password is the source of truth, Vercel holds the runtime copy. A serverless function cannot call op, so this split is unavoidable — the aim is only that the value never rests anywhere else.

Phase D · Deploy

Get a public URL with your code behind it.

  1. Private repo, then link the project.

    gh repo create <name> --private --source=. --remote=origin --push
npx vercel@latest link --yes
    If your app is in a subfolder of the repo (ours is joestar-agent/), set the Vercel project's Root Directory to that folder: Settings → Build & Deployment → Root Directory. Otherwise a git-triggered build looks at the repo root, finds no api/, and deploys an empty site over your working bot.

  2. Deploy to production.

    npx vercel@latest deploy --prod --yes

    Note the production domain it prints. A healthy deploy reaches Ready in seconds; one that sits at UNKNOWN is blocked, not slow — go back to section 04.

  3. Prove it is alive before involving Slack.

    curl -i https://<your-domain>/api/slack/events

    Expect 405 (the endpoint accepts POST only) or 200 if your version answers GET. A 404 means the route path is wrong — usually the Root Directory above. A redirect to vercel.com/sso-api means Deployment Protection is on for that URL; use the plain production alias, which is public.

Phase E · Wire the event

Two fields and one button. The button is the part everyone misses.

  1. Set the Request URL.

    Where: your Slack app → Features → Event Subscriptions → Enable Events (on)

    https://<your-domain>/api/slack/events

    Click outside the box; within a second or two you get a green ✓ Verified.

  2. Subscribe to the event. Expand Subscribe to bot events → Add Bot User Event → app_mention.

  3. Click Save Changes. The green bar at the very bottom of the page.

    This is the trap. ✓ Verified means Slack could reach your endpoint. Save Changes is what makes Slack send you events. They are different things, the save bar sits below the fold, and the failure is completely silent: your endpoint is verified and provably healthy, the bot is in the channel, the token works — and mentioning it does nothing at all, with no error anywhere.

  4. Reinstall if Slack asks. A yellow banner appears when scopes changed. If the scopes were already right, no banner, nothing to do.

  5. Invite the bot, then mention it.

    /invite @yourbot
@yourbot give me a number

    Installing granted permissions workspace-wide; it did not put the bot in any channel. A bot only receives mentions for channels it belongs to — which is what makes a workspace-wide install safe.

    A threaded number is the whole deliverable. Everything after this point, for the rest of the course, is changing what goes in the reply.

Phase F · Make it hold up

Optional for the video. Not optional once pushes deploy themselves.

  1. Tests that need no network. Stub fetch and assert the handler's contract: a forged signature gets 401, the challenge is echoed, the number lands in range, an existing thread is not re-rooted, a retry posts nothing, a missing env var gives 500.

  2. CI on every push, then deploy only if it passed. Turn off Vercel's own git trigger (vercel.json → git.deploymentEnabled.main: false) so the workflow is the single path to production.

    Running vercel deploy in CI? Run it from the repo root. Vercel applies the project's Root Directory on top of the working directory, so deploying from inside the subfolder resolves to app/app and fails — while working fine on your machine.

  3. A smoke script that probes each link in the chain after any config change. See section 07.

06 — THE CODE

What Claude wrote for you, in five jobs

One file does everything: api/slack/events.js. Read it in this order — it is the shape you will edit for the next fourteen lessons.

1 · Read the raw body, not a parsed object

The signature is a hash of the exact bytes Slack sent. Re-serialising a parsed JSON object produces different bytes — different whitespace, different key order — and every check fails. So the handler takes the body as text first and parses afterwards.

2 · Verify the request came from Slack

Rebuild Slack's signature as HMAC-SHA256 over v0:<timestamp>:<body> with the signing secret; reject timestamps older than five minutes (replay protection); compare with a timing-safe comparison. Anything failing gets 401 and nothing else happens.

Two details worth understanding. Timing-safe compare: a normal string comparison returns faster when the first character differs, and that timing difference leaks the expected value to a patient attacker. And the order matters — because the check runs before the challenge branch, and Slack signs the challenge too, a wrong signing secret means the URL never verifies. Your green tick therefore proves the secret is right. If your generated file puts the challenge first, Verified tells you less.

3 · Answer the URL verification challenge

If payload.type === 'url_verification', echo challenge straight back. One-off, and the reason the field turns green.

4 · Ignore retries, ignore itself

Any request carrying x-slack-retry-num gets an immediate 200 and no reply — otherwise one slow response becomes three identical numbers in the thread. Events carrying bot_id are skipped too, or a bot that mentions itself answers itself forever.

5 · Post the reply, and never fail loudly at Slack

chat.postMessage with channel, text, and thread_ts. Two non-obvious bits: Slack returns HTTP 200 even when the call failed, so you must check ok in the body; and if the post fails you log it and still answer 200, because a 500 makes Slack retry an event that will fail the same way.

One more distinction worth copying: a missing environment variable should return 500, not 401. Both mean "no reply", but 401 says "someone forged a request" and sends you hunting for an attacker when you actually mistyped a variable name.

07 — WHEN IT DOESN'T WORK

Test one link at a time

"Nothing happened" is not a diagnosis, and guessing is expensive. The chain has five testable links plus one you cannot test. Walk them in order; the first failure is your answer.

#ProbePassing proves
1curl the endpointThe deployment is alive and the route path is right.
2Hand-signed url_verificationThe signing secret in the deployment matches the vault's.
3Deliberately bad signature → 401The check is real, not decorative.
4Direct chat.postMessageToken valid, chat:write granted, bot is in the channel.
5Hand-signed app_mention at productionThe deployed handler works end to end.
—A human typing a mentionNot testable by script. See below.
If 1–5 pass and a real mention still does nothing, the fault is upstream in Slack's dispatch — and unsaved Event Subscriptions is the first thing to check, app-needs-reinstall the second. Nothing your code can do will surface this; only the ladder above tells you it is not your code.
Why a script cannot close the last link

Your bot could post a message mentioning itself — but that event arrives carrying bot_id, and job 4 above deliberately ignores it. Faking a human mention needs a user token (xoxp-), which is a new scope and a new secret. Not worth it. Accept that one link is human-tested and make the other five automatic.

08 — DONE

You are finished when

  • Mentioning the bot in a channel it belongs to produces a threaded number.
  • Mentioning it inside an existing thread replies in that thread, not a new one.
  • curling the endpoint with no signature is refused.
  • No secret exists in any file, any commit, or any screenshot — only in 1Password and Vercel's environment.
  • You can say out loud what each of the five platforms does, and what breaks without it.
  • You can name what the signing secret protects, and what the bot token authorises.
The last two matter more than the first four. Lesson 05 changes what goes in the reply and nothing else. If the round trip is a model in your head rather than a sequence of clicks you performed, the rest of the course is editing one function.
