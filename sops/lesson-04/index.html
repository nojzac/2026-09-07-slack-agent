SLACK AGENTS · CHAPTER "0 TO 1" · LESSON 04

Connect a Slack bot to code you control

A step-by-step guide to wiring Slack to a deployed function, written after doing it rather than before — so it also explains what each piece is for and where the silent failures are.

Ray's video: 4 min 14 s This page: 60–90 min the first time At the end: a working bot

What you'll have at the end

  • A Slack bot that replies in a thread when you mention it.
  • A deployed endpoint of your own that Slack sends events to, and that refuses anything not from Slack.
  • Both Slack credentials stored in 1Password, in no file and no commit.
  • Tests that run on every push, and a deploy that only happens when they pass.

Someone following Ray Amjad's Slack-agents course who has finished lesson 03, and who would rather understand the system than reproduce a sequence of clicks.

It assumes you can use a terminal and have used git before. It does not assume you have used Slack's developer site, Vercel, or 1Password — those are explained as they come up, click by click.

Before you begin

If you read nothing else, read this section. On the run this page comes from, most of the lost time was a prerequisite that was missing and silent. Not a bug. Not a difficult step. A setting that had never been switched on, failing quietly, hours later, while we looked somewhere else entirely.
It's the keys-wallet-phone check at the front door. Five seconds there saves you the walk back.

Accounts you need

  • Slack — a throwaway workspace from lesson 03, where you're allowed to install apps.
  • GitHub — with the gh command logged in.
  • Vercel — with GitHub connected to it. This is the one that silently costs you an evening; the box below says how to check.
  • 1Password — a Teams or Business account if you want the read-only agent login in step 3.
  • Claude Code — in a terminal, with Node 20 or newer.

Connect Vercel to GitHub before you start anything

If your Vercel account has no GitHub connection, two things happen and neither says so plainly:

  • vercel link refuses: "You need to add a Login Connection to your GitHub account first."
  • Much worse — deploys are blocked. They sit at UNKNOWN forever. No build log, no error from the command, nothing. The reason exists in one place only: a dialog in the Vercel dashboard saying "the commit email … could not be matched to a GitHub account."

And that message points you at the wrong fix. It suggests changing your git email. Check before you touch anything — if GitHub already links your commits to you, your email is fine:

gh api repos/<owner>/<repo>/commits --jq '.[] | "\(.commit.author.email) \(.author.login)"'

Seeing your username in the second column means the email is verified and correct. The real fix is on Vercel: account settings → Login Connections → Add Connection → GitHub, pick your GitHub username, and give it access to this repo only.

One command that checks all of it (if you have this project's scripts) 
bin/preflight

Fifteen checks, about twenty seconds, changes nothing: Node, gh, your 1Password token and both secrets, the Slack token and its permissions, Vercel login, the project link, the live endpoint, and the last CI run.

That last check is doing something sneaky and useful. There's no command that asks "is Vercel still connected to GitHub?" — so a green deploy job stands in for it, because without the connection nothing deploys at all.

What you are building: one mention, one replyThe round trip this lesson creates, and why the random number is beside the point.

UNDERSTAND

Nobody needs a bot that picks numbers. What you're building is a round trip: Slack notices someone said your bot's name, hands that over to code you control, your code decides something, and pushes an answer back into the conversation.

Lesson 05 swaps "decides something" for Claude Code running in a sandbox. Later lessons make it richer still. The pipe you build today doesn't change.

Think of it like a doorbell. Today it rings and a light comes on. Later it rings and the house makes you coffee. Wiring the doorbell to something is the job — the coffee is a detail.

So the thing worth walking away with isn't the file. It's being able to answer, without looking: when I type a mention, what happens, in what order, and what would stop it?

The five services you'll use: Slack, Vercel, GitHub, 1Password and GitHub ActionsWhat each one does, and the constraint that makes it necessary.

UNDERSTAND

It's a fair question, and each one is there because of a constraint that's obvious once someone says it out loud.

ServiceIts one jobWhy you can't skip it
Slack Owns the conversation. Spots the mention, sends it to you, shows your reply. You can't sit and ask Slack "anything for me yet?" — Slack pushes events out to a web address. So you need a web address.
Vercel Runs your code at a public address, on demand, with no server for you to look after. Slack needs somewhere to send that push. Your laptop isn't it: the address has to be public, always answerable, and encrypted.
GitHub Holds the code, privately, with a history of every change. Vercel has to deploy something. Better a recorded commit than whatever happens to be on one laptop.
1Password Holds the two secrets, and hands them to a command that asks for them. One of those secrets lets anyone post as your bot. It must not sit in a file, a repo, a screenshot or a chat log.
GitHub Actions Runs your tests on every push, and only lets the deploy through if they pass. Once pushing deploys automatically, the tests are the only thing standing between a typo and production.
One way to hold it in your head: Slack is the receptionist who pages you when someone says your name. Vercel is the phone that rings — it has to have a number, and it has to be answerable at 3am. GitHub is the filing cabinet. 1Password is the safe. GitHub Actions is the colleague who checks your work before it goes out.
Why "serverless"? Why not just rent a small server?

Between mentions, this bot does nothing at all. A rented server would sit there anyway — costing money, needing security updates, and able to quietly die at 3am without telling you.

A serverless function is just code with a web address. The platform starts it when a request arrives and throws it away afterwards. You pay per request, you patch nothing, and there's no process to keep alive.

It's a motion-sensor light. No one's asking you to leave the lights on all night in case someone walks past.

Two prices you pay. The first request after a quiet spell is a little slower ("cold start"). And nothing you keep in memory survives to the next request — each one starts fresh. Neither matters here, and when state does matter it goes in a database (lesson 12), not a variable.

Slack has a mode that needs no public address at all. Why not use it?

It's called Socket Mode: your bot opens an outgoing connection to Slack and events come down that pipe, no public endpoint needed. It's genuinely easier to start with.

The catch is that your bot only exists while some process of yours is running. That's a laptop-shaped bot — close the lid and it's gone.

The course deploys instead, so the bot is up while you sleep. That choice costs you exactly one thing: because your address is public, anyone can send things to it, so your code has to check that each request really came from Slack. That's the signing secret in section 02 — and it's why it matters here and not at all in Socket Mode.

Why a private repo for a bot that picks numbers?

Today, it genuinely doesn't matter. By lesson 15 this repo holds your prompts, your instructions to Claude, the shape of your internal tooling, and the wiring of an agent that can reach your systems.

Repos rarely get made private after the fact — someone has to notice and decide. Make it private now and never think about it again.

How one message travels from mention to replyThe three-second rule, the two credentials, and the line that puts the reply in a thread.

UNDERSTAND

Slack holds no code of yours. It holds an address. Everything you set up today exists to make this one round trip legal and reachable.

Why your code has three seconds, and how that shapes everything

Slack expects a "got it" within three seconds. Miss it and Slack assumes you failed and sends the same event again — up to three times.

It's someone repeating themselves because you didn't nod. You have to nod first, then do the thing.

That has two consequences you'll meet. Every repeat carries a header saying it's a repeat (x-slack-retry-num), which is how you spot one and ignore it — otherwise the same number gets posted three times. And from lesson 05, when the real work takes far longer than three seconds, you'll nod first and work afterwards.

The two secrets, and why one wouldn't do

They point in opposite directions. That's the whole reason there are two of them.

Signing secret — for things coming in

Known only to Slack and your code. Slack scrambles the message with it and sends the result along; your code scrambles the same message the same way and checks it matches. If it doesn't, the request didn't come from Slack, and you refuse it without doing anything.

It exists purely because your address is public and anyone can send things to it.

Bot token — for things going out

Proof to Slack that you're allowed to post as this bot. It belongs to the app installed in one workspace — install it somewhere else and you get a different one. Anything holding it can post as your bot, so treat it exactly like a password.

Neither does the other's job: the signing secret can't post, and the bot token can't prove an incoming request was genuine.

Why the reply lands in a thread, and the one line that decides it

Slack identifies every message by a timestamp. A message's own id is ts. A reply carries thread_ts, pointing at the message it hangs under. So the whole behaviour comes down to:

thread_ts: event.thread_ts ?? event.ts

Read it as: "the thread it's already in, or failing that, this message itself."

Like stapling your reply to a receipt number. If the customer already has a receipt, staple to that. If not, the message you're answering becomes the receipt.

Get it backwards and your bot either starts a fresh thread every single time, or answers at top level and buries the channel.

Words used in this lessonPlain-English definitions of the eight terms that appear in the steps.

UNDERSTAND
Event subscription
A standing order: "whenever this happens, send it to this address." Yours is app_mention — someone said your bot's name. It does nothing until you save it.
Scope
One named permission. You need two: app_mentions:read to hear the mention, chat:write to speak. That's the bot's entire power — it can't read channel history or see DMs.
App manifest
Your app's settings as a document instead of a screen full of switches. Paste it to create the app; keep it in the repo to see what changed.
Request URL
The address Slack sends events to. Your deployed code, ending /api/slack/events.
URL verification challenge
Slack ringing the number once to check someone picks up. It sends a random word and your endpoint has to say the same word back. Passing turns the field green.
Serverless function
Code with an address and no server. Started per request, discarded after, remembers nothing in between.
Environment variable
A value handed to your code when it runs, instead of written inside it. How a secret reaches a deployment without ever entering the repo.
Service account (1Password)
A login for a script rather than a person, allowed into specific vaults only. Lets a command read one vault without unlocking your whole password manager.

Step 3 of 6 — Put the two secrets in 1PasswordOptional. A vault, an item, a read-only login for your agents — every click, from nothing.

DO NOW

This whole step is optional. Nothing that runs unattended needs 1Password. The deployed bot reads its secrets from Vercel's own environment variables, CI reads its own from GitHub Actions secrets, and the tests use no secrets at all. You can skip this step, paste the values straight into Vercel, and the bot works identically.

What 1Password is actually used for here — all of it local, and none of it often:

  • Building the E2B sandbox image (lesson 05) needs E2B_API_KEY. Once, and again only when you change the image. Without 1Password: E2B_API_KEY=… node e2b/build.mjs.
  • bin/smoke needs the Slack bot token to post a test message. Without it, mention the bot yourself in Slack — same test, one more keystroke.
  • bin/preflight uses it for five of its fifteen checks. Without the token it skips those five and runs the other ten.

What you get for the effort: no secret values sitting in plaintext on your Mac, and one place to change a token instead of three. That is worth real money once you have several projects. For one project with four secrets, it is a preference, not a requirement.

Never turn on "Integrate with 1Password CLI". It lives in the desktop app under Settings → Developer, it looks like the obvious way to make op work in your terminal, and it is the most dangerous setting involved in any of this.

It signs in every shell on the machine as you, with your entire account — your interactive terminal and the non-interactive shells your AI agent runs in, equally. It ignores service-account scoping completely, because it is a different way of authenticating altogether: having a carefully scoped service account changes nothing while the integration is on, since the wide door is still there and op reaches for it first.

On 15 September 2026, on this project, it gave the coding agent read access to five vaults — including a client's — on a machine where exactly one vault was intended. The agent then read part of a non-revocable token into its own transcript while "just checking" that the credential existed.

There is no way to grant it to your terminal but not to an agent's. It is one switch for both. Leave it off and authenticate with a service account token instead, which is what the steps below create.

How to check where you stand: run op vault list. It should return only the vaults you granted that service account — for this project, one. If vaults you never granted appear, the integration is on.

Two more things that will catch you out.

  • A service account token is shown once. At creation it appears a single time and can never be displayed again. Get it where it needs to go before you close the tab. If you lose it, delete the service account and make another — do not leave one with vault access that nobody holds the key to.
  • A helper script that fetches the token gives your agent the vault. bin/with-secrets reads the token from your Keychain without prompting, so any agent that can run that script has that vault's access. That is deliberate, and bounded to one vault, read-only. But "the agent has no access" is not a true statement while the script exists — check by running it, not by assuming.

Phase C · The secrets

A vault of their own, an item inside it, then a read-only login for your agents. Every click below.

Three nested things, in order: a vault is the room, an item is the box in it, and a service account is a key cut for one room only — the one you hand to a script. Make them in that order and none of it is confusing.

  1. Make a vault just for this project.

    Where: the 1Password desktop app

    In the sidebar, hover over Vaults and click the + that appears (or menu bar → File → New Vault). Name it after the project — no spaces makes life easier later, e.g. SlackAgentOS. Leave the icon and description as you like, then Create Vault.

    If you have more than one 1Password account (a personal one and a work one), the sidebar groups vaults under each. Create this vault in a Teams or Business account if you have one — the read-only agent login in step 4 only exists there, and it can never be granted access to a Personal or Private vault. Putting the vault in the wrong account is the single most annoying thing to discover later.
    Why a whole vault for two little secrets?

    Because the vault is the unit of access. When you give a script permission, you give it permission to a vault — not to an item, not to a field.

    So if these two secrets live in your everyday personal vault, your only options are "the script can read everything you own" or "the script can't read anything". A vault per project makes "read exactly these two values and nothing else" a thing you can actually express.

    It's why hotels give cleaners a floor key, not a master key.

  2. Create one item inside it, holding both values.

    Where: the 1Password desktop app

    1. Select your new vault in the sidebar first, so the item lands in the right place.
    2. Click + New Item → choose API Credential. (Secure Note or Login work too — the category only changes which fields it suggests.)
    3. Title: name it after the project, e.g. 2026-09-07-slack-agent. Check the vault selector at the top still says your new vault.
    4. Scroll to the bottom of the item and click add more (1Password 8) or Add another field. Choose type Password.
    5. The field has two boxes: the left one is the label, the right one is the value. Label it exactly signing_secret and paste the Slack signing secret in.
    6. add more again, another Password field, labelled exactly bot_token, and paste the xoxb-… token.
    7. Save.
    The labels have to match exactly — lower case, underscores, no spaces. They are half of the address your code uses to find the value. Signing Secret and signing_secret are different fields as far as 1Password is concerned.
    Use the app, not the command line, for this bit. A secret typed into a terminal command gets written to your shell history file in plain text, and is briefly visible to anything that can list running processes.
    Why "Password" type rather than a plain text field?

    Password fields are hidden until you click to reveal, excluded from 1Password's own previews, and get a copy button instead of being selectable text. A plain text field shows the secret to anyone glancing at your screen or watching you share it.

  3. Write the address of each value into the repo — not the value.

    A committed .env.op file containing only signposts:

    SLACK_SIGNING_SECRET=op://SlackAgentOS/2026-09-07-slack-agent/signing_secret
SLACK_BOT_TOKEN=op://SlackAgentOS/2026-09-07-slack-agent/bot_token

    Read the pattern as op://<vault>/<item title>/<field label> — the room, the box, the thing in the box. Those three names are exactly what you typed in steps 1 and 2.

    The file is a luggage tag, not the luggage. It says where the thing is kept. It isn't the thing, so committing it is fine.

    Anything needing the real values then runs as:

    op run --env-file=.env.op -- <your command>

    The values exist inside that one running command and nowhere else.

    Ray does this differently: he keeps an example file with blank values and types the real secrets into Vercel's dashboard by hand. Same destination — the difference is whether a secret ever passes through your clipboard and a web form.

  4. Cut a key for your agents: a read-only service account.

    Where: your terminal (needs a Teams or Business 1Password account)

    Without this, the normal way a script reads 1Password is your desktop unlock — which opens your entire account to any command that runs while it's unlocked. A service account is a separate login that can read one vault, read-only, and nothing else.

    Use exactly the command below. It creates the account and stores its token in one step, so the token never appears on screen, in a file, or in your clipboard — which is what avoids the truncation trap explained after it.

    # macOS: create the account and put its token straight into the Keychain
security add-generic-password -U -a "$USER" -s op-slackagentos \
  -w "$(op service-account create slack-agent --vault SlackAgentOS:read_items --raw)"

    Approve the Touch ID prompt when it appears. Reading it back is then one line, which is what wrapper scripts like bin/with-secrets do for you:

    export OP_SERVICE_ACCOUNT_TOKEN="$(security find-generic-password -a "$USER" -s op-slackagentos -w)"
    Why that one-liner, and not a paste. If you run security add-generic-password -w with no value it asks you to type one — and silently cuts your input off at 128 characters. Real tokens are around 830. You get no warning at all; it surfaces much later, in a different tool, as "failed to DecodeSACredentials … unexpected end of JSON input". The one-liner above avoids this entirely because the token never passes through a prompt or your clipboard.
    Prove the key only opens the one room 
    export OP_SERVICE_ACCOUNT_TOKEN="$(security find-generic-password -a "$USER" -s op-slackagentos -w)"
op vault list

    It should print your project vault and nothing else. That's the whole point of the exercise — don't take it on trust, it costs one command to check.

    Things about service accounts that aren't obvious
    • They need a Teams or Business account. Personal and Families plans don't have them — in which case skip this step and use the normal desktop unlock, knowing it's broader.
    • They can never be granted your Private or Personal vault. That's a feature, and another reason step 1 made a dedicated vault.
    • The CLI can only create them. There's no list or delete — manage them in the browser, under Developer Tools → Service Accounts, on the account that owns the vault. If the list looks empty, you're probably signed into your other account.
    • op whoami with the token set tells you which account it belongs to.
    • The token prints exactly once. Lost it? Just make another — they're free and revocable.

  5. Check the whole chain before moving on. This prints the length of each secret, never the value:

    op run --env-file=.env.op -- node -e \
  'console.log("signing:", process.env.SLACK_SIGNING_SECRET?.length,
               "token:", process.env.SLACK_BOT_TOKEN?.length)'

    Two numbers means vault, item, field labels and references all line up — the signing secret is 32 characters, the bot token is longer. An error naming an item or field means a typo in a name somewhere; compare it against what you typed in steps 1 and 2.

  6. Give Vercel its own copy — piped, not typed.

    op read "op://SlackAgentOS/2026-09-07-slack-agent/signing_secret" \
  | npx vercel@latest env add SLACK_SIGNING_SECRET production

op read "op://SlackAgentOS/2026-09-07-slack-agent/bot_token" \
  | npx vercel@latest env add SLACK_BOT_TOKEN production

    Production only. Vercel's dashboard pre-ticks all three environments, so set it deliberately.

    Two copies now exist on purpose: 1Password is the master, Vercel holds the one your running code reads. A serverless function can't call 1Password, so this split is unavoidable — the point is that the value rests nowhere else.

    So is 1Password even used once Vercel has a copy?

    Not by the deployed bot, no. In production your code reads Vercel's copy — a serverless function has no desktop app to unlock and no Touch ID to press, so it cannot call 1Password. That pipe was a one-time transfer, not a live link.

    1Password is still doing three jobs:

    • It holds the readable master copy. Vercel stores these as hidden Secrets — you cannot read them back out. If you ever need to know what the value actually is, the vault is the only place that can tell you.
    • Everything on your machine reads it live. The smoke test, the preflight check, any script run through a wrapper — those fetch from the vault every single time.
    • It's where a change starts. Rotate in 1Password, then push the new value to Vercel.
    The copies can drift, and nothing tells you. Change the secret in 1Password alone and production carries on happily with the old one. 1Password is the source of truth by your discipline, not because the system enforces it. When you rotate, do both.
    Like a spare key you had cut. The original still lives on your keyring, but the spare is what's in the neighbour's drawer — change the lock and you have to hand over a new spare too.
    Never run vercel env pull. It writes your live secrets into a .env.local file in your project — precisely what all of this avoids. Note that vercel link and vercel dev also create that file (with a harmless token), so add .env* to .gitignore as a backstop.
CHECKPOINTThe length check prints two numbers, and both values are set in Vercel's production environment. No secret exists in any file.

Step 4 of 6 — Deploy to VercelPrivate repo, linked project, and a live address to hand to Slack.

DO NOW

Phase D · Deploy

Get a public address with your code behind it.

  1. Private repo, then link the project.

    Two commands, then one setting.

    gh repo create <name> --private --source=. --remote=origin --push
npx vercel@latest link --yes

    Now set the project's Root Directory, in Vercel → Settings → Build & Deployment: if your code sits in a subfolder of the repo, that folder's name; otherwise leave it. Getting this wrong means a push-triggered build looks at the top of the repo, finds no code, and deploys an empty site over your working bot.

  2. Deploy.

    npx vercel@latest deploy --prod --yes

    Note the address it prints. A healthy deploy is Ready in seconds. One that sits at UNKNOWN isn't slow — it's blocked. Go back to section 04.

  3. Prove it's alive before you involve Slack.

    curl -i https://<your-domain>/api/slack/events

    405 is good (the endpoint takes POST only), as is 200 if your version answers GET. 404 means the path is wrong — usually that Root Directory setting. A redirect to vercel.com/sso-api means that particular address is protected; use the plain production one.

CHECKPOINTFetching /api/slack/events returns 405 — the endpoint is live and refusing anything that is not a POST.

Step 5 of 6 — Point Slack at your deploymentTwo fields and one button. The button is the one everybody misses.

DO NOW

Phase E · Wire the event

Two fields and one button. The button is what everyone misses.

  1. Set the Request URL.

    Where: your Slack app → Features → Event Subscriptions → Enable Events (on)

    https://<your-domain>/api/slack/events

    Click outside the box and you should get a green ✓ Verified within a second or two.

  2. Subscribe to the event. Expand Subscribe to bot events → Add Bot User Event → app_mention.

  3. Click Save Changes — the green bar at the very bottom of the page.

    This is the trap that cost us an evening. ✓ Verified means Slack can reach you. Save Changes is what makes Slack start sending. Different things. The save bar sits below the fold, and the failure is completely silent: your endpoint is verified and provably healthy, the bot is in the channel, the token works — and mentioning it does absolutely nothing, with no error anywhere.
    It's a change-of-address form. Verified is the post office confirming the new address exists. Save is actually handing the form in. Skip it and your post keeps going to the old place, and nobody writes to tell you.

  4. Reinstall if Slack asks. A yellow banner appears if the permissions changed. If they were already right, there's no banner and nothing to do.

  5. Invite the bot, then mention it.

    /invite @yourbot
@yourbot give me a number

    Installing gave it permissions across the workspace; it didn't put it in any channel. A bot only hears mentions in channels it's actually in — which is what makes a workspace-wide install safe.

    A number in a thread is the whole deliverable. Everything else in this course is changing what goes in that reply.
CHECKPOINTMentioning the bot in a channel it belongs to produces a number in a thread. That is the deliverable of the lesson.

Step 6 of 6 — Add tests and a deploy gateOptional for the video. Not optional once pushing deploys by itself.

DO NOW

Phase F · Make it hold up

Optional for the video. Not optional once pushing deploys by itself.

  1. Tests that need no network. Fake Slack's API and check the promises: a forged signature is refused, the challenge is echoed, the number is in range, an existing thread isn't re-rooted, a repeat posts nothing, a missing setting gives a clear 500.

What the code does, in five jobsThe one file you will be editing for the next fourteen lessons.

REFERENCE

The file is api/slack/events.js. Read it in this order — each job exists for a reason, and the reasons are the interesting part.

1 · Take the message exactly as sent, don't tidy it first

The signature Slack sends is calculated from the exact characters in the request. If your code parses the message into an object and then rebuilds it — different spacing, different order — the calculation no longer matches, and every check fails.

Like checking a signature on a photocopy you retyped. Same words, wrong document.

So the handler reads the body as raw text first, checks it, and only then parses.

2 · Check the request really came from Slack

Scramble v0:<timestamp>:<body> with the signing secret, compare with what Slack sent, and refuse anything that doesn't match. Also refuse anything older than five minutes, so a captured request can't be replayed later.

Two details worth understanding:

The comparison is deliberately slow and even. A normal text comparison stops as soon as it finds a difference, so it answers faster for a wrong guess that starts correctly. That timing difference leaks the answer, one character at a time, to someone patient. A timing-safe comparison always takes the same time.

The order of these checks is load-bearing. Because the signature is checked before the challenge is answered, and Slack signs the challenge too, a wrong signing secret means the URL never verifies. So your green tick is also proof the secret is right. If your generated file answers the challenge first, the tick proves less.

3 · Answer the one-off challenge

When Slack sends url_verification, send its challenge value straight back. That one exchange is what turns the field green, and it never happens again.

4 · Ignore repeats, and ignore itself

Anything arriving with a repeat header gets an immediate "got it" and no reply — otherwise one slow response becomes three identical numbers in the thread.

Events from bots are skipped too. Without that, a bot that mentions itself answers itself, forever.

5 · Post the reply — and never fail loudly at Slack

Send the message with the channel, the text, and the thread id from section 02. Two non-obvious bits:

Slack answers "200 OK" even when your call failed, with the real outcome inside the response body. So you have to look inside rather than trust the status.

And if posting fails, log it but still tell Slack you're fine. Reporting an error makes Slack retry an event that's going to fail exactly the same way.

One distinction worth copying: a missing setting should return 500, not 401. Both mean "no reply appeared", but 401 says "someone forged a request" and sends you hunting for an attacker when you actually just mistyped a variable name.

When the bot doesn't reply: find the broken linkFive things a script can test, one it cannot, and a table of symptoms with their real causes.

REFERENCE

Guessing is expensive — we lost an hour to two confident, wrong theories. The chain has five links you can test with a script, and one you can't.

If 1–5 pass and a real mention still does nothing, the problem is upstream in Slack, not in your code. Check the Event Subscriptions settings were actually saved first, and whether the app needs reinstalling second.
Why a script can't test that last link

Your bot could post a message that mentions itself — but that event arrives marked as coming from a bot, and job 4 above ignores it deliberately. Faking a human mention needs a different kind of token with more access, which is more risk than the test is worth.

Accept that one link is human-tested, and make the other five automatic. Their real value is telling you the fault isn't in your code.

Checklist: how to know you're finishedFour things that work, and two things you should be able to explain.

REFERENCE
  • Mentioning the bot in a channel it's in produces a number in a thread.
  • Mentioning it inside an existing thread replies there, not in a new one.
  • Poking the endpoint without a signature gets refused.
  • No secret sits in any file, any commit, or any screenshot — only in 1Password and Vercel's settings.
  • You can say what each of the five services does, and what breaks without it.
  • You can say what the signing secret protects, and what the bot token permits.
