If I did lesson 04 again

What went wrong, what genuinely surprised me, and five ways to redesign this — cheapest first.

The one pattern behind everything. Not a single failure announced itself. Vercel blocked deploys and reported UNKNOWN with no logs. Slack accepted settings it never saved. The Keychain silently truncated a token at 128 characters. Every hour lost went to a system that failed quietly and let us keep working on the wrong hypothesis. So every redesign below is really the same idea: make failures loud, and check them early.

What I'd do differently

1. Preflight before writing any code

Every prerequisite failure hit us mid-flow, hours after it could have been found. The whole set is checkable in about 20 seconds — Vercel login, GitHub↔Vercel connection, op access, gh auth, the Slack app's existence. I wrote code first and discovered the environment later, which is backwards.

2. Never hand over a placeholder

I gave you a manifest containing https://<deployment>/api/slack/events and you pasted it, reasonably. Anything a person will copy should either contain a real value or refuse to exist yet.

3. Verify each step as it's made, not at the end

I did the five-probe diagnosis (curl, signed challenge, bad signature, direct post, synthetic mention) after an hour of silence. Run as a smoke test right after configuration, it would have isolated the fault in a minute.

4. Prefer pipes to prompts for secrets

Two of the three secret-handling failures came from asking a human to paste into an interactive prompt. op … --raw | … straight into its destination has no truncation limit, no clipboard, no history.

5. Say "I don't know" faster

I offered two confident wrong diagnoses — concurrent builds, then app-needs-reinstall — before finding the real causes. Both were plausible and both sent you off to do work that didn't help. The evidence at the time supported "something upstream is silent", not a specific cause.

Edge cases the code now handles

Most were anticipated rather than discovered — worth listing because lesson 05 keeps all of them:

  • Slack retries — without the x-slack-retry-num check, one slow response posts the number three times.
  • Threading — thread_ts ?? ts: reply inside an existing thread, otherwise start one on the message.
  • Self-mentions — ignore events carrying bot_id, or a bot that mentions itself loops forever.
  • Replay window — reject signatures older than five minutes.
  • Timing-safe compare — length check first, then timingSafeEqual.
  • Raw body integrity — the signature covers exact bytes, so a re-serialised parse would fail every time.
  • Misconfiguration vs forgery — a missing env var returns 500, not 401, so it can't masquerade as an attack (adopted from Ray).
  • Never 500 at Slack — a failed post logs and still acks, or Slack retries into the same failure.

Five redesigns, cheapest first

A. bin/preflight ~20 min

One script that checks every prerequisite and prints a pass/fail table: vercel whoami, the GitHub↔Vercel connection, op vault reachability, gh auth, Node version, whether the Slack app exists and which scopes its token carries. Run it at the start of every lesson.

Buys: the largest single time sink, found in 20 seconds instead of 3 hours. Costs: almost nothing. My pick if you do only one thing.

B. bin/smoke ~30 min

The five-probe chain as a single command, ending with a real threaded reply in a test channel. Run after any config change, and after every deploy.

Buys: turns "nothing happened" into "link 4 of 5 is broken". Reusable unchanged through lesson 15. Costs: it posts to Slack, so it wants a dedicated #bot-smoke channel.

C. Prerequisites and traps baked into the lesson pages ~1 h

Amend course/LESSON-PAGE-RULES.md so every page opens with a runnable preflight block and marks the silent-failure steps inline — "Verified is not Saved" next to the step, not in a debrief afterwards. The information existed in the lesson 04 page; it wasn't in front of you at the moment it mattered.

Buys: compounding across 13 remaining lessons. Costs: a rules change plus a pass over each page as you build it.

D. Slack configured by API, not by clicking ~2 h

Slack app configuration tokens plus apps.manifest.update let the manifest be applied programmatically. The manifest in the repo becomes the source of truth, and bin/apply-manifest pushes it.

Buys: eliminates the entire Save-Changes class of bug — there is no unsaved state. Scope changes in later lessons become a diff instead of a click-hunt. Costs: config tokens expire every 12 hours and must be refreshed, which is its own small trap.

E. bin/bootstrap — the whole environment from one command ~1 day

Create the Vercel project, set Root Directory via API, push env vars from 1Password, connect the repo, apply the Slack manifest, run the smoke test, print what's left for a human. Everything we did by hand tonight, encoded.

Buys: the course becomes reproducible — a second workspace, a fresh machine, or a clean re-run costs minutes. Real proof the setup is understood. Costs: a day, and it only pays back if you actually re-run it. Honest take: premature unless you plan to teach this, demo it, or run a second environment.

F. The ambitious one worth naming

Per-branch preview environments: every PR gets its own Vercel preview and its own Slack app in a scratch workspace, so a change is exercised by a real mention before it can reach production. This is what "properly engineered" would look like for a bot that later runs Claude Code with repo access — at that point a bad deploy stops being cosmetic. Worth revisiting around lesson 09, not now.

If I could keep only two

A and B. They are an hour together, they cover the two failure modes that actually cost us the evening — unmet prerequisites and silent breakage mid-chain — and they stay useful unchanged for the rest of the course. C is the natural follow-up because it compounds. D is genuinely good engineering with a nagging token-refresh cost. E is a day spent proving a point you may not need to prove.
