SLACK AGENTS · CHAPTER "0 TO 1" · LESSON 11

Let the bot show you: put a browser in the sandbox

The bot can already change code and open a pull request. What it cannot do is show you the change working — you have to take its word for it. This lesson puts a real browser in the sandbox so it can drive the app, record what happens, and send the recording back. The hard part is not Playwright. It is how a forty-megabyte video gets out of a machine that is about to be destroyed, without handing that machine a credential it should not have.

Ray's video: 4 min 24 s This page: 90–150 min At the end: screenshots and recordings arriving in the thread

What you'll have at the end

The route the bytes take is the design decision of this lesson. Everything else — installing Chromium, writing a Playwright script — is ordinary work the bot does for you.

  • Playwright and Chromium in the sandbox image, so every future run has a browser with nothing to install.
  • A file route that does not pass through the function, so the size cap stops being about memory.
  • A screenshot and a recording in a Slack thread, sent by the bot, of the bot's own work.
  • Instructions the bot will actually read next time — which is a different thing from instructions it wrote down.

Who this is for, and what it assumes

You finished lesson 10, so the bot has MCP tools, opens pull requests against its own repository, and you have merged several. You can rebuild the E2B template locally — that is bin/with-secrets node e2b/build.mjs, and this lesson is the first since lesson 08 that needs it.

This is a longer lesson than 10. The browser install is the easy half; the second half is a change to how files leave the sandbox, and one deliberate refusal of something Ray's own agent offers to build.

Why this lesson exists

Lessons 08 to 10 all widened what the bot may touch. This one widens what it can prove — the first lesson whose output is evidence rather than capability.

The point is not screenshots. It is that "I made the change and it works" stops being a claim you either trust or re-check by hand. Ray puts this at the end of his task lifecycle: the last thing every job does is drive the thing it just built and send back the recording. That only works if getting a video into Slack is boring, which is why most of this page is about the video and not about the browser.

How this page is laid out

  2. Part 2 · Build it DO NOW Eight steps: one decision, one request to the bot, its questions, a review, a template rebuild, a merge, a live test, and the instructions it will actually read. 90–150 min.

Before you begin

Do not put the Slack bot token in the sandbox. Ray's prompt asks the agent to verify it can send recordings "directly from the sandbox rather than passing through" the function, and the obvious way to do that is to pass SLACK_BOT_TOKEN in. Resist it. That token does not expire, is not scoped to a channel, and lets anything running in that machine post as the bot anywhere it is a member — while this is precisely the lesson that teaches the machine to open arbitrary web pages.

There is a direct route that needs no token at all, and Ray's own agent suggests it on screen: a single-use upload URL. Step 1 is deciding this before you ask, because once the bot has built the token version you will be reviewing a diff instead of making a choice.
  • Lesson 10 finished, and #joestar-dev with the repository in its topic.
  • The ability to rebuild the E2B template — bin/with-secrets node e2b/build.mjs, last needed in lesson 08.
  • Ten minutes of patience for the first build. Chromium and its ninety-odd system libraries are not a small layer.
PART 1

Understand what you're building

Four things: what a browser costs in a machine that is thrown away every message, the three routes a large file can take out of that machine, where the famous "8 MB limit" actually comes from, and what having a browser does to everything lesson 10 said about the blast radius.

What Playwright is, and what it costs in a throwaway machineThe library is small. The browser is not, and where it goes decides whether this is usable.

UNDERSTAND

Playwright is a library for driving a real browser from a script: open a page, click, type, wait for something, take a screenshot, record a video. Nothing about it is agent-specific. What makes it matter here is that the model can write a Playwright script as easily as it writes a test, and the output is a file a human can look at.

It comes in two halves, and only one of them is small:

HalfSizeWhere it has to be
The playwright npm packagea few MBAnywhere Node can require it
The Chromium build it drives, plus system librarieshundreds of MBOn disk before the run starts, or you pay for it every message
This is the same argument as lesson 10's transport choice, in a different costume. There, stdio MCP servers lost to remote HTTP because npx re-downloads on a machine that is new every time. Here, installing Chromium at run time loses to baking it into the image for exactly the same reason. A fresh sandbox per message turns every install into a per-message cost — once you have that sentence, most of this course's infrastructure decisions answer themselves.

Which means the E2B template, and the template has no branch

The sandbox image is built by e2b/build.mjs and registered under a name — joestar-claude. Sandbox.create() asks for that name. There is no version in the request.

Rebuilding the template deploys it immediately, to production, from whatever branch you are standing on. The image is not reviewed, not gated by CI, not tied to the pull request that changed template.mjs, and not rolled back when you revert the commit. The moment the build finishes, the next message anyone sends the bot boots the new image.

This is the opposite of how the code path works, where a merge to main runs the tests and then deploys. Two different deployment models for two halves of the same change — and step 5 of this page walks you into it deliberately, so it happens while you are watching.
The lesson-08 trap still applies. A stale image of the same name silently shadows your change: if you edit template.mjs and do not rebuild, the bot keeps booting yesterday's machine and every symptom points at your code. Check the build output for a new build id, not just the absence of errors.

Three routes a 40 MB recording can take out of the sandboxToday's route buffers it in the function. Two alternatives do not. Only one of them is safe.

UNDERSTAND

Since lesson 07 the bot has been able to send files back. The route has always been the same: after the run, the function reads each file out of the sandbox into memory, then posts those bytes to Slack. For a 60 KB Markdown file nobody notices. For a screen recording it is the whole problem.

B and C are both "direct from the sandbox". They differ only in what the sandbox is holding while it does it — and that is the entire security difference.

RouteWhat the sandbox holdsBlast radius if the model is talked into misusing it
A · Relay (today)nothingNone. It cannot reach Slack at all
B · Bot tokenA non-expiring credential for the whole workspacePost as the bot in any channel it is in, read history, upload anything, indefinitely
C · Single-use URL (chosen)One pre-signed URL, bound to one filename and one byte lengthUpload that one file. The URL is spent afterwards and grants nothing else
Why C works at all: the upload step is unauthenticated by design. Slack's modern upload is three calls — ask for a URL, POST the bytes to it, then tell Slack the upload is complete and where to share it. Only the first and third carry the token. The middle one is a pre-signed URL, and it does not care who POSTs to it. So the bytes can come from anywhere, and the sandbox is an "anywhere".

The code in api/_lib/slack.js has been doing all three steps since lesson 07. This change moves one of them.
A courier and a key. Route B hands the courier the key to the building so they can drop off one parcel. Route C gives them a locker number that opens once. Both get the parcel delivered; only one of them still matters tomorrow.
The honest cost of C. The sandbox must stay alive while the upload happens, which means the upload competes with the same five-minute budget as everything else — where route A uploads after the sandbox is dead. It also adds a round trip per file. If a run is already at 4 minutes 50, route C is the thing that will fail.

Where the "8 MB limit" actually comes fromRay attributes it to Vercel. Checked against Vercel's own limits page: it is not Vercel's, and 8 is not the number.

UNDERSTAND

In the video, the agent reports back that there is "an 8 megabyte file upload limit because currently any output is passed into the Vercel function's memory". Ray accepts it and asks for the cap to be raised. It is worth knowing which parts of that sentence are true, because three different numbers are getting mixed together.

LimitReal valueDoes it apply here?
Vercel request/response payload4.5 MB, error FUNCTION_PAYLOAD_TOO_LARGENo. It governs bodies the function receives or returns. Uploading to Slack is an outbound request the function makes, and is not covered
Vercel function memory2 GB on Hobby, 4 GB on ProYes, and this is the real ceiling on route A — the file is buffered, twice over, in that 2 GB
Vercel max duration300 s, hard on HobbyYes, and it binds long before memory does. Lesson 09 already proved this is the constraint that actually bites
Slack's own file size1 GB per fileYes, but it is nowhere near binding
MAX_OUTPUT_BYTES in api/_lib/claude.js8 MiBThis is the one that is stopping you. It is our own constant, written in lesson 07, and nothing outside this repository knows it exists
Ray says the 8 MB comes from Vercel; it does not. Vercel's documented 4.5 MB payload limit is about bodies in and out of the function, not about files the function uploads elsewhere, and 8 is not one of Vercel's numbers at all. In this repository the 8 MiB is a constant one of us wrote. Ray's agent almost certainly told him the same thing about his — an agent explaining a constant it chose itself, in terms of the platform, is a very ordinary way for a false fact to enter a codebase.

Verified 2026-09-17 against Vercel's Functions Limits page. The practical consequence is the same as Ray's — raise the cap — but the reason matters, because "Vercel forbids it" would have meant the relay route was a dead end, and it is not.
What to do with that. Raise MAX_OUTPUT_BYTES to something honest for a recording, and put the real constraint in the comment: not "Vercel's limit" but "this many bytes has to move twice inside 300 seconds". A cap with a true reason beside it survives the next person who wonders why it is there.
Why cap it at all, then? Because a model that decides to record four hundred megabytes of video should hit a wall with a clear message rather than a timeout with none. The cap's job is to convert an obscure failure into an obvious one — it was never a platform constraint, and pretending it was cost this page an afternoon of reading Vercel's documentation to find out.

What a browser does to the blast radiusLesson 10 put untrusted text, a credential and write access in one pot. This adds an unlimited supply of untrusted text.

UNDERSTAND

Lesson 10's warning was that a web search result is a page someone else wrote, arriving in a session that can open pull requests. A browser is that, without the search engine in between and without a result count.

Before this lessonAfter
Untrusted text arrives from a Slack thread, a cloned repository, and MCP tool output…and from any URL the model decides to visit, including ones a page it visited told it to visit
Text onlyText the model chose to fetch, rendered by a browser that runs the page's JavaScript
What it can do about it: commit, push, open a PR, call MCP toolsUnchanged — and that is the point. The inputs widened; the powers did not shrink
The rule from lesson 10 has a second half now. That rule was about what the bot may reach. This is about what may reach it: from here on, treat any page the sandbox loads as hostile input with the same standing as a message from a stranger. The protections are the ones already in place and they are structural, not behavioural — the repository scoping from lesson 09, the withheld workflows permission from lesson 08, the branch ruleset that means nothing merges without you, and the fact that the machine is destroyed afterwards.

None of those depend on the model being careful, which is the only kind of protection worth counting.
And this is the argument against route B in one line. The lesson that gives the sandbox an unlimited supply of attacker-authored text is the worst possible lesson in which to also give it a permanent credential for your workspace. Those two changes arrive in the same pull request if you let them.
THE DECISION THIS PAGE MAKESChromium goes in the template, not in the run. Files leave by single-use URL, not by handing the sandbox a token. The cap stays, with a true reason written next to it.
PART 2

Build it

Eight steps. One is a decision you make before typing anything, four are the usual ask–answer–review–merge loop from lesson 09, one is a local build that deploys itself, and two are about proving it works and making sure it keeps working.

Step 1 of 8 — Decide how the bytes get to SlackBefore you ask. Afterwards you are reviewing someone's answer instead of choosing.

DO NOW

  1. Read the three routes in Part 1 and pick one. This page picks C, the single-use upload URL. If you pick A, the relay, you are choosing to raise the cap and stop there, which is a perfectly good answer for screenshots and short clips.

    Do not pick B. Nothing on this page is written for a sandbox holding SLACK_BOT_TOKEN, and the reason is in Part 1: it is a non-expiring, workspace-wide credential arriving in the same change that teaches the machine to open web pages.

  2. Write the choice into the request you are about to send. The prompt in step 2 names the route explicitly. That is the difference between this lesson and Ray's: he asks the agent to "verify you can send recordings directly", and lets it come back with a proposal.

    Ray's agent proposes the right thing anyway. On screen it asks him: "do you want me to build a single-use upload URL approach?" — which is route C. Naming it up front is not a disagreement with Ray, it is skipping a round trip, and it means the security choice is made by a person rather than accepted from a suggestion.

  3. Decide the cap, and why. The number matters less than the reason beside it. Something in the tens of megabytes is honest for a screen recording; the constraint to write in the comment is the 300-second budget, not a platform rule.

CHECKPOINTYou can say, out loud, what the sandbox will be holding while it uploads — and it is not a token.

Step 8 of 8 — Put the instructions where the bot will read themRay's last ask, and the one with a trap in it: writing them down and loading them are different jobs.

DO NOW

Ray's prompt ends: "save a set of instructions for yourself so you can do this faster next time". The obvious reading is "write a document". The useful version has a second half.

A file the model never opens is a diary, not instructions. The sandbox is empty every message. Nothing in the repository is in the model's context unless it clones the repository and something points it at that file. A beautifully written docs/playwright.md that nothing loads will be silently ignored for months, while you believe the bot has been briefed.

  1. Write the instructions. Short and specific: where Chromium is, what environment variables it needs, where to write output so it gets uploaded, how to record video and the fact that the file only exists after the context is closed, and the cap.

  2. Then make something load them. There are two places that actually reach the model, and they are not the same:

    WhereWhen it is readGood for
    CLAUDE.md in the cloned repositoryAutomatically, but only once the model is working inside that cloneRepository-specific practice — how this project uses Playwright
    The prompt the function builds, in api/slack/events.jsEvery run, before anything is clonedFacts about the machine itself, which are true whether or not a repository is involved

    Capabilities of the sandbox belong in the second. The function already does exactly this for GitHub — a short block telling the model where the walls are, so it does not spend minutes finding them by walking into them. Playwright deserves the same treatment: it is a capability of the machine, not of the repository.

  3. Prove it landed. Ask the bot, in a channel with no repository in its topic, what it can do with a browser. No repository means no clone, so a correct answer can only have come from the prompt.

    That test separates the two mechanisms. If it answers correctly with nothing cloned, the briefing is in the prompt. If it only knows once it has cloned the repo, what you wrote is repository documentation — useful, but it will not help on the runs that do not clone anything.
CHECKPOINTThe bot describes its own browser capability in a channel where it cloned nothing.

The template additions, and the three lines that are not obviousThe shape to expect in the diff, and why each awkward part is there.

REFERENCE

The E2B template is an SDK definition in e2b/template.mjs, not a Dockerfile. Adding a browser is three ideas:

IdeaWhy it is not just "install playwright"
Install the browser to a shared path, with PLAYWRIGHT_BROWSERS_PATH set on the imageBy default Playwright puts browsers in the installing user's cache directory. The install needs root (system libraries); the run happens as user. Without a shared path those are two different directories, and the run fails with "Executable doesn't exist" while the files are plainly there
Install system dependencies as root, via Playwright's own --with-depsChromium needs around ninety shared libraries that are not in a Node base image. Playwright knows the list for your distribution; you do not want to maintain it
Make the package resolvable from anywhereA globally installed npm package is not on the module search path for a script sitting in /tmp. The model will write scripts in /tmp. Either set NODE_PATH on the image or install into a fixed directory the instructions name
Pin the Playwright version, and keep the two halves in step. The npm package and the browser build are versioned together; a floating latest in the image means a rebuild months from now can pick up a browser your scripts have not seen. The rest of this template pins deliberately — fromNodeImage('24'), a dated GitHub CLI repository — and this is no different.
Everything that is a capability of the machine belongs in the template; everything that is a secret does not. That line was drawn in lesson 10 for the Exa key and it holds here unchanged: browsers in the image, credentials never.

When something doesn't workEvery entry is a case where the error names the wrong thing, or there is no error at all.

REFERENCE
What you seeWhat it usually is
"Executable doesn't exist at …/ms-playwright/chromium-…"Installed as one user, run as another. The path in the message is the one it looked in, not the one the files are in. Fix with a shared PLAYWRIGHT_BROWSERS_PATH set for both
"Cannot find module 'playwright'"Global install, script outside any project. Module resolution, not installation — the package is there

The file silently never arrives, run otherwise fineOver the output cap. It is logged and skipped, not thrown — check the function logs for the skip line

The bug worth the whole lesson

Template.setEnvs applies only during the build. The browsers installed to /opt/ms-playwright correctly and the variable was gone by the time a sandbox ran anything, so the image looked perfect and failed at first launch — with an error whose own suggested fix (npx playwright install) would have hidden the cause and cost 114 MB per message forever after.

It was proved, not argued. Booting the finished image and withholding those variables reproduces the exact failure; supplying them makes it work. That counter-test needed an E2B key and a sandbox created from outside — which is to say the sandbox cannot test the sandbox, and this is one of the things that could not be delegated to the bot.

The green number that measured nothing

PR #7 reported "57/57 pass" while touching no test file: the same suite as before the change, none of it reaching the new path. Six tests later, breaking each one on purpose, a leaked Slack token in the sandbox command turned 63/63 into 62 pass and 1 fail. Ask what would have gone red.
