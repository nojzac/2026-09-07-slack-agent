01What you are actually building

Four moving parts. If you can name all four and say what would break without each, you own this lesson.

The four things that must line up

  • The manifest — declares the bot user, the scopes app_mentions:read and chat:write, and the app_mention event.
  • The request URL — where Slack POSTs events. Your deployed Vercel endpoint.
  • The signing secret — how your code proves the request really came from Slack.
  • The bot token — how your code proves to Slack that it may post as the bot.

Before you start

  • The test Slack workspace from lesson 03.
  • Claude Code, in a terminal, on your machine.
  • A GitHub account (the repo will be private).
  • A Vercel account, ideally already linked to GitHub.
  • A name for your bot. Ray uses Joestar; pick your own and substitute it everywhere below.
Read this before you build. You are going to ask Claude Code to write this bot from a one-line prompt. Your code will not be character-for-character identical to Ray's, and that is fine — the lesson is the wiring, not the file. The finished version from the video is published, so if your run stalls you can take Ray's copy and keep moving. Section 3 walks through that published code so you know what a good result looks like.

02Build it

Eight steps. Tick them off as you go — the page remembers. Each step says what to do, where you are when you do it, and (behind the toggle) why it exists.

  1. Where: your terminal

    Make a folder for the agent (Ray makes joestar-agent on the Desktop), cd into it, launch Claude Code, and paste the prompt from the lesson page:

    Can we make a really simple Slack bot here that we will be deploying to
the Vercel whereby when I tag it, then it will automatically reply to the
message in the thread with a random number.

    Press enter and let it work. Do not sit and watch it — step 2 happens in parallel.

    Why a dedicated folder, and why that phrasing

    The folder becomes the repo, the Vercel project, and later the home of the whole agent. Everything from lessons 05 to 17 lands here, so give it the agent's name, not something like test.

    Three constraints are doing the work in that prompt: deploying to Vercel (so Claude writes a serverless function, not a long-running server), when I tag it (so it subscribes to the mention event rather than reading every message), and in the thread (so the reply is threaded, not dumped in the channel).

  2. Where: api.slack.com/apps

    While Claude writes code, go to api.slack.com/apps and press Create New App. Choose From a manifest, pick your test workspace, press Next. Slack now waits for you to paste a manifest — leave it open.

    Why the manifest route

    The alternative is clicking through Slack's settings screens one by one. A manifest is the same configuration as a file, so your app's setup is text you keep in the repo, review, and re-paste if you break something.

    It also means the app's shape stays under Claude's control. As the bot grows new abilities in later lessons, the manifest changes with it.

  3. Where: terminal → editor → Slack

    Back in Claude Code:

    give me a manifest for the Slack API

    It writes slack-manifest.json. Open the project in your editor, copy the file's contents, paste into the Slack page, press Next. Slack shows a summary of the scopes it is about to grant. Press Create.

    Ray's finished manifest, for comparison:

    {
  "display_information": {
    "name": "Joestar",
    "description": "Tag me and I'll reply in the thread with a random number.",
    "background_color": "#4a154b"
  },
  "features": {
    "bot_user": { "display_name": "Joestar", "always_online": true }
  },
  "oauth_config": {
    "scopes": { "bot": ["app_mentions:read", "chat:write"] }
  },
  "settings": {
    "event_subscriptions": {
      "request_url": "https://joestar-agent.vercel.app/api/slack/events",
      "bot_events": ["app_mention"]
    },
    "org_deploy_enabled": false,
    "socket_mode_enabled": false,
    "token_rotation_enabled": false
  }
}
    Chicken and egg. That request_url is the finished state. Right now the app is not deployed, so the URL does not exist yet and Slack may reject or drop it. Ignore that for now — you set the URL by hand in step 7, once there is something at the other end.
    Read the manifest — two scopes and one event

    app_mentions:read lets the app receive the mention. chat:write lets it post. That is the entire permission surface: this bot cannot read your channels' history, cannot see DMs it is not in, cannot do anything but answer when spoken to. Later lessons add scopes deliberately; keeping the list this short now means you notice when it grows.

    socket_mode_enabled: false is the counterpart of deploying to Vercel. Socket mode is for a bot running on your laptop holding a websocket open. You are running a public HTTPS endpoint instead, which is why the signing secret matters so much.

  4. Where: terminal

    Claude will offer to initialise git and set up the Vercel project. Say yes, and be specific:

    yeah, set up git init and then push it to a private GitHub repo
and then set up the Vercel project for me

    It works through those stages and then tells you which environment variables you need to set on Vercel for the bot to work: a signing secret and a bot token.

    Why private, and why the secrets are not in the repo

    Private because the repo will eventually carry your prompts, your CLAUDE.md, and the shape of your internal tooling. Nothing here is dangerous today, but this repo grows for seventeen lessons.

    The two secrets live only in Vercel's environment variables. The repo carries a .env.example naming them with blank values, and a .gitignore that excludes .env. That split — names in git, values in the platform — is the pattern to keep as you add more keys in lesson 05.

  5. Where: Vercel project → Environment Variables

    Open your new project on Vercel, search for Environment Variables, and add one scoped to Production. Get the value from the Slack app's Basic Information → App Credentials: find Signing Secret, press Show, copy it, paste it as the value, Save.

    Watch the environment scope. Vercel pre-ticks Production, Preview and Development. Ray catches himself doing this and re-saves as production only. Set it deliberately rather than accepting the default.
    What the signing secret actually prevents

    Your endpoint is a public URL. Anyone who learns it can POST anything to it. The signing secret is a shared key known only to Slack and your function: Slack hashes the request body and timestamp with it and sends the result in a header, and your code recomputes the same hash. Mismatch means the request did not come from Slack, and the function answers 401 without doing anything.

    Because the check is the first thing the handler does, a wrong or missing secret makes the endpoint look dead from Slack's side. There is no message in Slack explaining why. The evidence is a 401 in the Vercel function logs, which is why knowing where those logs are is worth two minutes now.

  6. Where: Slack app → Install App, then Vercel

    In the Slack app's sidebar open Install App and press Install to <your workspace>. Slack then shows a bot token starting xoxb-. Copy it, go back to Vercel, add a second environment variable named SLACK_BOT_TOKEN, paste, scope it to Production, save.

    Then tell Claude Code, so it knows the deployment is now viable:

    I also set the environment variables too
    Why the token only exists after installing

    The signing secret belongs to the app, and exists as soon as the app does. The bot token belongs to the app installed into one workspace, and is what actually carries the granted scopes. Install the app somewhere else later and you get a different token. That is why it appears under Install App rather than in App Credentials.

    Treat it like a password. It is a bearer token: anything holding it can post as your bot.

  7. Where: Slack app → Event Subscriptions

    Once the project is deployed, Claude gives you the endpoint URL — it ends in /api/slack/events. If it does not offer one, ask for it.

    In the Slack app sidebar go to Event Subscriptions (below the MCP Servers entry), paste the URL into the Request URL field, and wait for the green Verified. Press Save Changes.

    What “Verified” is testing

    The moment you paste the URL, Slack POSTs a one-off challenge to it: a body of type url_verification carrying a random challenge string. Your endpoint has to echo that string straight back. If it does, you get Verified.

    So Verified proves the deployment is live, the route path is right, and the handler recognises Slack's payload format. In Ray's version it proves one thing more: the signature check runs before the challenge branch, and Slack signs the challenge request too, so a wrong signing secret would return 401 and never verify. It still says nothing about the bot token, which is only exercised when the bot tries to post.

    Worth checking in your own generated file which order those two checks are in. If the challenge branch comes first, Verified tells you less than it does here.

  8. Where: Slack

    In your test workspace, in the channel you want to use, invite the bot by typing /invite @yourbot. Then post a message tagging it. It replies in the thread with a random number.

    That reply is the whole deliverable of the lesson. Everything after this point is replacing what goes in the reply.

    Why the invite is a separate act

    Installing the app grants it permissions across the workspace; it does not put it in any channel. A bot only receives mention events for channels it is a member of, which is what makes a workspace-wide install safe. If you tag it somewhere you have not invited it, nothing happens.

03Read the code you now own

One file does everything: api/slack/events.js. Ray's finished version is about a hundred lines and has five jobs. Read them in order — this is the shape you will be editing for the next fourteen lessons.

1

Read the raw body, not a parsed object

The signature is a hash of the exact bytes Slack sent, so the handler collects the request stream itself. Re-serialising a parsed JSON object would produce different bytes and every signature check would fail.

2

Verify the request came from Slack

It rebuilds Slack's signature as an HMAC-SHA256 over v0:<timestamp>:<body> using the signing secret, rejects anything with a timestamp more than five minutes old, and compares with a timing-safe comparison. Anything that fails gets a 401.

3

Answer the URL verification challenge

If the payload type is url_verification, echo the challenge value back and stop. This is the branch that turns the Slack settings page green in step 7.

4

Ignore Slack's retries and the bot's own messages

Slack re-sends an event if you are slow to answer, so the handler returns early when it sees a retry header, otherwise one mention would produce several numbers. It also skips events carrying a bot_id, so the bot cannot trigger itself into a loop.

5

Do the work and reply in-thread

On an app_mention, generate the number and POST to Slack's chat.postMessage with the bot token as a bearer credential.

api/slack/events.js — the part that decides the reply
const event = payload.event;
if (event?.type === "app_mention" && !event.bot_id) {
  const number = crypto.randomInt(MIN, MAX + 1);
  // Reply inside the existing thread if there is one, otherwise start one.
  await postThreadReply(
    event.channel,
    event.thread_ts ?? event.ts,
    `🎲 ${number}`,
  );
}

return send(res, 200);

The threading trick is worth a second look. event.thread_ts ?? event.ts means: if the mention was already inside a thread, reply into that same thread; if it was a top-level message, use the message's own timestamp, which starts a new thread hanging off it. One expression, both cases.

The reply call itself 
async function postThreadReply(channel, threadTs, text) {
  const res = await fetch("https://slack.com/api/chat.postMessage", {
    method: "POST",
    headers: {
      "Content-Type": "application/json; charset=utf-8",
      Authorization: `Bearer ${BOT_TOKEN}`,
    },
    body: JSON.stringify({ channel, thread_ts: threadTs, text }),
  });

  const data = await res.json();
  if (!data.ok) console.error("chat.postMessage failed:", data.error);
}

Note what is not here: no Slack SDK, no framework, no dependencies at all. Ray's package.json has no dependency block — the whole bot is the platform's fetch and Node's built-in crypto. Fewer moving parts to understand, and nothing to keep updated.

Also note the failure mode: a rejected post does not throw, it logs. If Slack refuses the call you will see nothing in Slack and a chat.postMessage failed line in the Vercel function logs.

.env.example — the names, never the values
# Slack app credentials (Basic Information → App Credentials)
SLACK_SIGNING_SECRET=
# OAuth & Permissions → Bot User OAuth Token (starts with xoxb-)
SLACK_BOT_TOKEN=

# Optional — inclusive range for the random number (defaults 1..100)
RANDOM_MIN=1
RANDOM_MAX=100

04When it does not work

Diagnose by symptom. The useful habit is to ask which of the four moving parts a symptom implicates, rather than re-doing all of them.

SymptomWhat it points atWhat to do
Request URL will not verify in Slack Deployment or route. The challenge branch never ran. Confirm the deployment succeeded and the URL path matches the file, ending /api/slack/events. Ask Claude for the exact deployed endpoint rather than typing one from memory.
Verified, but tagging the bot does nothing Signing secret, bot token, or channel membership. Check the Vercel function logs. A 401 means the signature check failed, so the secret is wrong or missing. A chat.postMessage failed line means the token or the channel is the problem — confirm you invited the bot to that channel.
Function returns 500 immediately Environment variables absent at runtime. The handler bails with a 500 if either variable is unset. Check they are scoped to Production and that the project was redeployed after you added them.
Several replies to one mention The retry guard. Slack retried because the first response was slow. Confirm your handler returns early when the retry header is present.
Your generated code differs a lot from Ray's Nothing. That is expected. Compare against the five jobs above. If yours does all five, it is fine. If you are stuck, take the published code for this lesson and move on — the point is the wiring.

Ray's own move when something misbehaves is to screenshot the failure and hand it back to Claude Code. That is the intended loop: you are the one who can see Slack and Vercel, so your job is describing symptoms accurately, not reading stack traces.

05The seam that lesson 05 opens

Everything you just built stays. One block changes.

Look again at job 5. The handler receives a mention and decides what to say. Right now that decision is one line of arithmetic. In lesson 05 the same block instead boots a cloud sandbox, runs Claude Code inside it with the text of your message as the prompt, and posts back what Claude says.

Nothing before that block changes: the manifest, the signature check, the challenge branch, the retry guard, the threading logic all carry over untouched. The lesson adds two more environment variables next to the two you set today — a sandbox API key and a Claude Code token — using the same names-in-git, values-in-Vercel pattern. If you understood today's four moving parts, lesson 05 is one substitution.

06Check yourself

Answer before opening. If two or more of these are shaky, re-read section 3 rather than pressing on.

Slack says Verified, but tagging the bot produces no reply. What has Verified already ruled out, and what has it not?

Answer

Verified rules out a dead deployment, a wrong URL path and a handler that does not understand Slack's payloads. In Ray's code it also rules out a wrong signing secret, because the signature check sits above the challenge branch and Slack signs the challenge too. What it cannot rule out is the bot token or the channel invite, since nothing has tried to post yet.

Why does the handler read the request body as raw bytes instead of using a parsed JSON object?

Answer

The signature is computed over the exact bytes Slack sent. Parsing and re-serialising would change whitespace and key order, so the recomputed hash would never match.

You want the bot in a second channel. What do you have to do?

Answer

Invite it there. Installation is workspace-wide but a bot only receives mentions in channels it belongs to. No code, manifest or credential change is needed.

Where would you add a capability like reading message history, and what else would that force?

Answer

A new scope in the manifest. Changing scopes means re-applying the manifest to the app and reinstalling it to the workspace, which issues a new bot token that you then have to update in Vercel.

Which of the four moving parts would you have to change to point the same bot at a different Slack workspace?

Answer

The bot token, since it is issued per installation. The code, endpoint and signing secret belong to the app and the deployment, not to a workspace.

07If you want to go further today

Optional. None of this is required for lesson 05, but each one is a cheap way to test whether you can actually edit what you built.

  • Set RANDOM_MIN and RANDOM_MAX in Vercel and confirm the range changes without touching code. That is your proof that environment variables reach the running function.
  • Have the reply echo back the text you tagged it with. It is a one-line change in job 5, and it is exactly what lesson 05 needs the message text for.
  • Deliberately break the signing secret, tag the bot, and read the 401 in the Vercel logs. Then fix it. Now you have seen the most common failure with your own eyes.
  • Read your generated events.js against the five jobs and ask Claude Code to explain anything it does that Ray's version does not.
